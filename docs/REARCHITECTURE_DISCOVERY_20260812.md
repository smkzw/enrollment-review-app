## 1. 本轮目标与边界

本轮先完成四件事：

1. 恢复桌面双击启动，并验证打开的是入排审核系统本身，而不是同端口上的其他服务。
2. 重新盘点代码、项目文档、历史会话、测试记录、运行产物和真实页面。
3. 从临床事实、证据来源、时间逻辑、分期审核、行动分流和可恢复运行等维度，判断现有系统是否适合继续迭代。
4. 形成 Patient Journey 与多 Agent/Graph 工作流的设计前提，通过多轮用户确认后再定稿和实施。

本阶段不修改研究方案、受试者原始资料、人工 IE 表或既有审核报告，也不启动全量临床重跑。

## 2. 桌面入口故障

- `127.0.0.1:8900` 已被另一套本地服务占用。
- 旧启动脚本只判断 `/api/health` 是否返回 HTTP 200，没有校验返回的服务身份。

- LaunchAgent 历史记录还存在反复的配置退出，但它不是这次假阳性判断的唯一根因。

### 2.2 已修复

- 入排服务健康响应新增稳定身份：`service=enrollment-review-app` 和版本号。
- 启动器默认从 `8901-8910` 选择可用端口，并将实际端口写入持久化端口文件。
- 启动器只有在健康响应的服务身份匹配时才接受已有进程。
- 仓库脚本与桌面入口已同步。

### 2.3 验证

- 当前地址：`http://127.0.0.1:8901`
- 健康响应：`service=enrollment-review-app`、`version=2.0.0`、`status=ok`。
- 三个启动脚本通过 `zsh -n`。
- 桌面入口与仓库入口逐字节一致。

## 4. 当前系统的真实定位

当前系统已经具备可保留的原型能力：

- DOCX/PDF/图片等上传与路径安全处理；
- 最多 8 路 OCR 的适配层和页面级 Markdown 缓存；
- 方案元信息提取、II/III 期拆分、阶段锚点、中心和受试者管理；
- 按筛选期/基线期生成审核结果；
- 个人、中心、项目报告和部分审计日志；
- 大量来自真实错误案例的回归测试与临床安全经验。

但它仍然是**文件驱动的可运行原型**，不是一套可审计、可恢复、可形成纵向个例画像和明确行动建议的多阶段临床事实平台。继续在现有审核器里增加项目或受试者特异的正则补丁，会进一步放大不可解释性和回归风险。

## 5. 根因级问题

### 5.1 没有独立的临床事实层

当前受试者模型主要保存 ID、中心、日期、状态和一个顶层结论；没有以下一等实体：

- 人口学和疾病状态；
- 疾病、症状、诊断、手术、检查、检验、评分等临床事件；
- 既往史和社会史；
- 用药/治疗暴露区间；
- 否认、未知、不确定、互相冲突等事实状态；
- 原始来源、页码、坐标、原文摘录和文档版本；
- 单用户校对记录、研究者判断来源和待办闭环。

因此现有“病历摘要”只能是一次 LLM 文本生成，不能稳定支持 Patient Journey、阶段增量、证据冲突和点击回原文。

### 5.2 规则没有可执行的逻辑结构

方案解构后的主要真相仍是 Markdown。复杂规则中的 `AND / OR / NOT`、阈值、单位、时间锚点、时间窗、例外、研究者判断和证据要求没有成为结构化组件。

这正是既往错误反复出现的共同根因：

- 把“且”弱化成“或”；
- 用 GGT 代替 ALT/AST/总胆红素；
- 把尿糖或潜血异常迁移到感染条款；
- 把特异性梅毒抗体阳性误套非特异性抗体例外；
- 推理写“未触发”，结论却写“不通过”；
- 用筛选日期或报告日期代替随机/基线锚点。

现有代码已经积累了针对这些问题的提示词与正则纠偏。这些测试和临床知识应保留，但应迁移为**通用结构化规则校验器和确定性门控**，不再作为模型输出后的文本修补。

### 5.3 证据来源不足以支撑审计

- OCR 缓存当前主要按修改时间判断是否可复用，没有源文件内容哈希、OCR 模型版本和不可变文档版本共同组成的指纹。
- 证据包保留文件名、页码和文本，但没有稳定的页内坐标与原图区域锚点。
- 无法区分“患者自述/病历转述”“处方”“实际给药”“检查结果”“研究者评价”的证据等级。
- “OCR 成功”仍容易被误认为“证据充分”；两者必须分开。

### 5.4 分期是标签，不是受试者生命周期

- 阶段来自流程表和 JSON 列表，但不是有状态转移、证据截止时间和重开规则的工作流。
- 新阶段报告会覆盖顶层 `overall_verdict`，项目列表难以直观看到各阶段独立结论。
- 阶段状态通过扫描报告文件再解析推断，缺少明确的 ReviewEpisode 和 ReviewRun。
- 批量处理主要由浏览器顺序循环受试者并保持 SSE 请求，刷新、断网和服务重启后的恢复能力有限。

### 5.5 “待补证/需研究者”没有形成可执行行动

当前系统大多停留在状态标签或报告文案，没有稳定记录：缺的是哪一个规则组件、需要哪一方补什么、可接受的证据形式是什么、应在什么节点前完成、补充后应重跑哪些事实和规则。新系统不承担最终入排决策，但必须把每个未决点转成具体、可执行、可关闭的 ActionRequest。

### 5.6 单机单用户目标与旧权限模型不一致

下一阶段已确认以单台 Mac、本地单用户为主，并删除登录流程，双击后直接进入。现有注册、超级管理员、项目所有权和跨用户只读逻辑不再属于目标架构，迁移时只保留必要的历史来源字段，不继续维护账户权限行为。

## 6. 入排 Patient Profile 目标模型

本产品的 Patient Profile 不应是一段不可验证的摘要，而应是“截至当前入排节点的 Patient Journey”在结构化事实层上的可视化投影。

### 6.1 核心实体

| 实体 | 关键字段 |
|---|---|
| Subject | 受试者标识、中心、项目、出生日期/年龄、性别 |
| ReviewEpisode | 预筛/筛选/基线等阶段、锚点日期、证据截止时间、状态 |
| SourceDocumentVersion | 文件哈希、上传者、上传时间、版本、页数、处理状态 |
| EvidenceSpan | 文件、页码、页内坐标、原图区域、原文、OCR 置信度/版本 |
| ClinicalFact | 值、单位、否定、时态、确定性、证据来源、冲突状态 |
| ClinicalEvent | 诊断、症状、病程、手术、检查、检验、评分、社会史事件 |
| MedicationExposure | 报告/处方/给药类型、药物、剂量、途径、频次、起止日期、适应证 |
| EligibilityRiskLink | 事实/事件、对应规则组件、风险类型、阶段、证据充分性 |
| ActionRequest | 未决规则组件、目标责任方、需补内容、可接受证据、最晚节点、状态 |
| ResolutionRecord | 新增证据/说明、处理时间、受影响事实与规则、重跑记录 |

### 6.2 展示原则

- 保存所有抽取事件，默认视图只突出与本项目当前阶段入排相关的事件；允许切换“完整时间轴”。
- 疾病进程、既往史、用药/治疗可叠加在同一时间轴，也可按泳道分开。
- 每个风险标记必须说明：关联规则、风险性质、当前阶段、缺失组件、下一步动作。
- 每个事实和判断均可点击到原始文件、页码、原图区域和原文；如启用单用户校对，保留原 OCR、校对文本和重算记录。
- “未提供”“患者否认”“病历转述”“源文件明确”“研究者判断”必须视觉和语义分开。

## 7. 规则与审核的目标数据模型

### 7.1 方案侧

- Project、ProtocolVersion、QAArtifact、RuleSetVersion。
- Rule 保留方案官方 IN/EX 编号和父子层级。
- RuleComponent 显式保存：`ALL/ANY/NOT`、指标/概念、比较符、阈值、单位、时间锚点、时间窗、例外、研究者判断要求和证据类型。
- 展示给用户的方案版本号严格来自方案本身。修订案是唯一可改变标准的来源；Q&A、澄清函、邮件和医学解释只能解释方案模糊处，不能改变或覆盖方案/现行修订案。
- 每个解释来源绑定对应方案版本、来源文件和日期。若解释与方案或现行修订案明显冲突，系统必须警示并仍以方案/修订案为基座。
- 内部可保存抽取算法修订号，但不得伪装成新的方案版本号；历史审核必须明确绑定当时使用的 `Vx.x`。

### 7.2 受试者侧

- 每次上传产生新的 SourceDocumentVersion，不覆盖已审证据。
- 每次审核产生 ReviewRun，绑定阶段、规则集版本、证据截止和模型/提示版本。
- EligibilityAssessor 作为 AI lead 产生结构化判断、风险和行动建议；系统输出不是最终入排决定。
- Deterministic Gate 校验逻辑、数值、单位、时间窗、例外组件、证据完整性和结论一致性。
- 独立 QC 只能接受、否决或升级，不能静默重写原判断。
- 对不满足、模棱两可、证据不足和待后续节点核实的条目，必须生成明确 ActionRequest，而不是只给状态标签。

## 8. Graph engineering 与多 Agent 结论

### 8.1 结论

**适合采用 Graph 组织工作流，但不适合构建自由自治的 Agent 群。**

Graph 应管理状态、分支、重试、暂停、补充资料、版本和恢复；数据库中的结构化临床事实、规则、行动建议和处理记录才是业务真相。LLM Agent 只在需要语义理解的节点工作，不能让同一次自由文本生成同时完成抽取、规则计算、QC 和报告定稿。

### 8.2 最小 Agent 组合

1. **Evidence Normalizer**：从 OCR/原生文本生成 ClinicalFact、ClinicalEvent、MedicationExposure 和冲突候选。
2. **Eligibility Assessor**：针对一个阶段、一个规则集和检索到的证据生成逐组件候选判断。
3. **Safety & Provenance Critic**：使用独立上下文检查逻辑、时序、证据引用、否定词和结论矛盾，只能否决、降级确定性或生成复核行动，不能静默重写原判断。

其余步骤优先使用确定性代码：文档指纹、规则编号、单位换算、时间窗计算、状态迁移、权限、审计和最终报告投影。

### 8.3 两条工作图

**方案初始化图**

`文件校验 -> 元信息提取 -> 期别识别/用户选择 -> 结构化规则抽取 -> 编号/逻辑/覆盖校验 -> 流程节点抽取 -> 人工对照编辑 -> 发布规则集版本`

**受试者审核图**

`上传/版本化 -> OCR/原生抽取 -> 页面完整性与否定词QC -> 事实/事件标准化 -> 冲突与来源门控 -> 阶段证据准备度 -> 逐规则评估 -> 确定性门控 -> 独立QC -> 行动建议 -> Patient Profile/报告投影`

分支包括：资料不足转补充队列、研究者判断转研究者队列、OCR/冲突转人工校对、新增文件产生新版本并增量重跑受影响节点。

### 8.4 框架初选，不在本阶段锁定

| 候选 | 优点 | 主要限制 | 当前判断 |
|---|---|---|---|
| LangGraph OSS | MIT；checkpoint、interrupt、恢复和 HITL 适配 Agent 图 | 仍需自建临床数据层、权限和运行治理 | 本地/早期服务化首选候选 |
| Temporal Python SDK | MIT；长任务、重试、恢复和分布式耐久性强 | 基础设施和运维成本较高 | 团队服务器/规模化时再评估 |
| Prefect | Apache-2.0；数据任务、重试和并发成熟 | 细粒度临床人工裁决语义较弱 | 更适合作为 OCR/ETL 子流水线候选 |
| Pydantic AI | MIT；结构化 Agent 输出和类型约束好 | 不是独立的耐久工作流真相层 | 可与显式状态机或 LangGraph 组合 |

已确认的技术方向是：**结构化领域模型 + 本地关系数据库 + 显式状态机/Graph + 版本化证据 + AI lead 行动建议**。单机单用户场景优先考虑 SQLite/WAL 和本地后台任务，不引入 PostgreSQL 或 Temporal 的部署负担；LangGraph OSS 与更轻的显式状态机仍需在原型阶段对比。

## 9. Demo 截图评估与界面方向

### 9.1 值得吸收

- 固定左侧项目导航，让用户始终知道自己处于项目配置、患者资料、初筛还是精筛。
- “患者概况/用药/异常值”与原始病历同屏，减少反复跳页。
- 逐条规则、识别文本、病历原文三栏联动，适合证据核对。
- 批量状态、筛选和人工操作入口清晰。

### 9.2 不应照搬

- 三栏同时常驻会导致小屏文字过小、嵌套滚动和视线跳跃。
- Demo 没有充分显示 AI 判断的确定性、证据强度和下一步行动。
- 如果规则、识别文本和源页不做同步选中/定位，三栏只会增加信息密度，不会增加可验证性。

### 9.3 建议的信息架构

- 全局：固定项目导航、项目/阶段/队列上下文和未处理任务。
- 项目看板：受试者按预筛、筛选、基线列出独立状态、结论、风险和待办，不再只有一个顶层结论。
- 个例工作台顶部：紧凑显示人口学、疾病状态、阶段、锚点、证据截止和未决行动数量。
- 主标签：`Patient Journey`、`入排审核`、`证据`、`审计记录`。
- Patient Journey：时间轴/泳道、风险筛选、完整事件切换、点击回源。
- 入排审核：可折叠规则树 + 结构化事实/组件判断 + 原图/原文查看器；选择规则或事实时同步定位。
- 使用 CSS Grid 的 `minmax()`、容器查询、可收起/可拖动面板和响应式断点，避免固定像素宽高和全局横向滚动。

当前页面实测截图位于 `output/product_audit_20260812/`。当前系统的主要 UI 差距不是色彩，而是缺少项目看板、Patient Journey、证据联动和人工任务队列，规则管理也仍是大段 Markdown 文本区。

## 10. 保留、替换与迁移原则

### 10.1 保留并封装

- 文件上传和路径安全机制；
- OCR 适配器与最多 8 路准入控制；
- 现有方案/受试者样本、历史报告和临床错误回归测试；
- 现有 Markdown/HTML 报告作为兼容投影；
- 研究期别与审核节点分层、受试者级阶段锚点、中心等已确认产品规则；II/III 无缝设计边界等待第二轮澄清。

### 10.2 逐步替换

- JSON/Markdown 作为业务真相；
- 一个顶层 `overall_verdict`；
- 模型自由文本表格作为审核接口；
- 项目/受试者特异正则作为主要安全层；
- 浏览器请求持有整个批任务；
- 原型认证、URL 凭据和不完整审计。

### 10.3 迁移策略

新模型不承接旧项目写状态，也不把旧 `overall_verdict`、Markdown 报告或人工修补结果导入为新业务真相。旧项目、旧报告和典型错误病例保持只读，作为反面锚点、知识提炼来源和回归对照；V2 使用同一原始方案和代表性资料从头新建项目，完整重跑方案解构、上传、OCR、事实抽取和审核流程。若需要统一查看，只能使用与 V2 业务库隔离的只读比较适配器，不得形成可继续写入的迁移副本。

## 11. 第一轮确认结果

1. **部署：** 单台 Mac、本地单用户为主。
2. **产品责任：** 系统不直接作出最终入排决定，采用 AI lead。对于明确不满足、模棱两可或证据不足的条目，必须细化指出需要哪一方补充什么资料或描述，才能进一步明确。
3. **上传：** 同一受试者同时支持增量上传和全量上传；二者的快照/替换语义在第二轮确认。
4. **研究边界：** 不同研究分期原则上属于不同研究；II/III 无缝设计作为例外边界，需进一步明确产品行为。
5. **Patient Profile：** 仅指从最早可追溯时间点到预筛/筛选/基线节点的历时性个例画像，不等同于另一个监查系统的 Patient Profile。
6. **用户：** 单用户，不构建多人审批或修订权限链。
7. **规则效力：** 方案是基座，修订案是唯一授权的标准更改形式；其它来源只可解释模糊处。任何受试者审核必须绑定当时使用的正式方案版本 `Vx.x`。

## 12. 入排 Patient Profile 深化设计

### 12.1 时间边界与信息组织

Patient Profile 的纵向范围从现有资料可证明的最早事件开始，到本次预筛、筛选或基线审核节点的证据截止时间为止。后台保存全量结构化事实，前端用主题泳道和风险过滤器组织，避免把所有内容压成一段摘要或一条拥挤时间轴。

建议的主题泳道如下：

| 泳道 | 需要呈现的元素 |
|---|---|
| 研究节点 | ICF、预筛、筛选、导入/洗脱、基线/随机、关键检查及资料补充日期 |
| 人口学与基线特征 | 性别、出生日期/各节点年龄、身高、体重、BMI；仅在方案相关时展示种族、职业等 |
| 目标疾病历程 | 最早症状、首次诊断、诊断依据、病程长度、表型/分型、严重度/活动度、控制状态、复发/急性发作、住院、并发症、历次关键治疗及反应 |
| 症状与体征 | 与目标疾病或排除风险相关的症状起止、频率、严重度、功能影响、体格检查和变化 |
| 既往史/现病史 | 每项疾病的起止、持续/已解决、稳定性、严重度、治疗状态、最近一次活动和对应源记录 |
| 用药暴露 | 原始药名、通用名/药物类别、适应证、剂量、途径、频次、起止、是否持续、实际使用/处方/患者自述、疗效和停药原因 |
| 非药物治疗与操作 | 手术、介入、放疗、免疫治疗、脱敏、器械、康复及其它方案限制的治疗，保留起止和效果 |
| 检验检查与评分 | 实验室、影像、心电图、肺功能、内镜、生命体征、疾病评分/量表；保存全量值，默认突出入排相关、异常、临界或趋势变化 |
| 过敏/感染/免疫 | 药物和食物过敏、过敏原、感染史与活动状态、结核/肝炎/HIV/梅毒等筛查、疫苗史 |
| 生育相关 | 妊娠/哺乳、绝经/手术绝育、妊娠检测、避孕承诺及方案规定时间窗 |
| 社会与暴露史 | 吸烟、饮酒、药物滥用、职业/环境暴露、旅行或动物接触等，仅在方案相关时突出 |
| 家族史与特殊经历 | 方案相关家族史、既往临床研究、研究药物暴露、献血/输血、器官移植等 |
| 证据与冲突 | 患者否认、病历转述、既往源文件、检查原件、研究者判断、日期不完整、OCR低置信度和资料间冲突 |

### 12.2 事件级结构

每个事件至少保存：事件类别、原始名称和标准化名称、发生/开始/结束日期、日期精度、持续状态、严重度/活动度、否定状态、确定性、记录时间与事件时间的区别、所处审核阶段、证据新鲜度、证据类型、文件/页码/区域/原文、关联规则组件、风险和建议行动。

日期必须允许 `明确日 / 仅年月 / 仅年份 / 相对时间 / 未知`。部分日期不得伪造成精确日期；涉及洗脱期或病程阈值时，显示可计算上下界，并在上下界会改变结论时生成风险。

### 12.3 风险与入排契合标记

一个事件可同时关联多个规则组件，但风险必须逐组件表达：

- **明确契合：** 证据直接支持纳入条件或不触发排除条件。
- **明确障碍：** 已有证据完整触发排除，或明确不满足纳入条件。
- **临界/时间窗风险：** 数值接近阈值、洗脱期可能不足、锚点缺失或部分日期导致区间跨越阈值。
- **证据不足：** 缺少原始报告、具体数值、日期、用药细节、诊断依据或应到节点资料。
- **需专业判断：** 事实存在，但方案还要求临床意义、稳定性、可接受风险、适合参与等专业判断。
- **证据冲突：** 不同文件、不同时间或不同来源的事实不一致。
- **溯源提醒：** 筛选病历仅转述既往史，而更早既往源文件未提供；不因此自动降为不通过。
- **后续节点关注：** 当前节点可继续，但方案要求在基线/随机/给药前再次满足或完成。

### 12.4 AI lead 的行动建议合同

每个非明确项必须生成结构化行动，而不是一句“请补充资料”：

| 字段 | 示例含义 |
|---|---|
| `target_party` | 研究者方、CRC、CRA、申办方医学/项目组 |
| `missing_component` | 尚未证明的具体规则组件 |
| `requested_action` | 需要补问、补录、补文件、复测、计算、确认或解释的具体动作 |
| `acceptable_evidence` | 可接受的病历原件、检查报告、处方/给药记录、研究者判断文字等 |
| `due_stage` | 应在预筛、筛选结束、导入期、基线/随机或给药前完成 |
| `blocking_level` | 当前是否阻断进入下一审核节点，或仅为重点关注 |
| `source_and_rule` | 触发行动的证据位置和方案规则组件 |

责任边界按动作性质决定，而不是按账户权限决定：研究者负责病史询问和记录，以及临床意义/稳定性/适合性判断；CRC 负责收集、补录和核对现场资料；CRA 负责源数据一致性与问题闭环核查，但不能代替研究者作临床判断；受试者只作为信息来源，不作为独立行动责任方；申办方医学/项目组处理方案解释冲突。

## 13. 第二轮确认结果

1. **研究边界：** 独立 II 期、独立 III 期以及同一方案中非无缝的 II/III 均建立不同项目；只有方案明确为 seamless/adaptive II/III 且同一受试者队列连续过渡时，作为一个项目并在项目内区分研究部分。
2. **上传语义：** 增量上传自动去重并合并新文件，只重跑受影响事实/规则；全量上传建立新的完整证据快照并停用旧快照，但不物理删除旧资料和旧报告。
3. **阶段历史：** 基线新增资料不得静默改写原筛选结果；保留原筛选快照，并提供显式的“基于新增资料回顾重审筛选期”。
4. **证据优先级：** 直接原始检查、处方/给药记录和既往同期病历优先于后来的筛选病历转述；发生冲突时并列展示、生成核实行动，不自动选边。
5. **单用户校对：** 采用推荐方案。原始文件和原 OCR 不变，校对文本/结构化事实另存，并自动重跑受影响部分。
6. **登录：** 删除注册、管理员、多账户、项目所有权和登录流程，双击后直接进入。
7. **阶段判断：** 不再用单一最终入排式结论；可使用 `未发现明确障碍 / 发现明确入排障碍 / 关键证据不足 / 需专业判断 / 存在证据冲突 / 后续节点关注`。
8. **责任方：** 检验检查的安排、完成和临床记录属于研究者方，不单列“检验检查执行方”。缺口还必须区分记录描述不完整和客观资料/操作确实缺漏。
9. **Patient Profile 首屏：** 默认只突出入排相关、异常、临界和趋势变化的检验检查；后台仍保存全部结果，完整正常结果进入明细。

## 14. 缺口类型与行动路由深化

### 14.1 两个正交维度

系统不能再把所有未明确情况压缩成“证据不足”。每条规则同时保存两个维度：

1. **条款判断状态：** 明确契合、明确障碍、暂不能明确、需专业判断、存在冲突、后续节点关注。
2. **缺口原因：** 为什么暂不能明确，以及应由谁完成什么动作。

缺口原因不会自动决定条款结论。例如“病历未记载筛选前某病史”不等于存在该病史，也不等于排除标准已触发；它表示当前病历采集或记录不完整，无法确认该历史条件。

### 14.2 通用缺口分类

| 缺口类型 | 判定边界 | 建议责任与动作 |
|---|---|---|
| 病历记录不完整 | 本次节点病历按常规或方案应询问/记录，但完全未提及，不能把沉默当否认 | 研究者补充询问并完善病历；CRC协调记录完整性 |
| 临床描述不充分 | 已提到疾病/症状/用药，但缺起止、严重度、活动性、治疗反应或持续状态 | 研究者补充具体临床描述，必要时向受试者核实 |
| 既往源文件未取得 | 当前病历转述了既往事实，规则需要或风险较高，尚无同期既往病历/报告支撑 | CRC协助获取既往机构原始病历/报告；保留溯源提醒 |
| 已知原始资料未上传 | 病历明确引用某报告、处方或检查结果，但证据包缺少该已存在文件 | CRC补充上传明确文件；CRA核对来源一致性 |
| 必做检查/评分未完成 | 研究流程表要求当前节点完成，但没有实施或没有结果 | 研究者安排并完成检查/评分，CRC补录和上传 |
| 结果要素缺失 | 有报告但缺数值、单位、参考范围、日期、签名或关键页 | 研究者方补齐/更正完整报告，CRC核对文件完整性 |
| 时间锚点/日期不足 | 缺少基线/随机/给药锚点，或只有部分日期，无法计算病程/洗脱期 | 研究者/CRC补充准确日期；系统展示可计算上下界 |
| 需专业判断 | 客观事实已有，但方案还要求临床意义、稳定性、不可接受风险或适合性判断 | 研究者形成针对该条款的明确病历判断 |
| 资料冲突 | 病历、报告、处方、患者陈述或不同日期记录互相不一致 | 研究者核实临床事实；CRC/CRA完成源数据一致性核查 |
| OCR/解析不可靠 | 否定词、数值、单位、日期或页面结构低置信度/疑似误识别 | 用户在源图旁校对，系统仅重跑受影响事实和规则 |
| 方案解释冲突 | Q&A/邮件/医学解释与方案或现行修订案冲突 | 申办方医学/项目组澄清；系统保持方案优先并警示 |
| 后续节点尚未到期 | 基线/随机/给药前要求在当前筛选节点尚未到期 | 当前节点显示关注项，在到期节点自动升级为必核项 |

### 14.3 “没有资料”的语义决策

系统需先判断方案要求的事实性质，再决定提示：

- **病史询问型规则：** 若筛选病历完全未提及，优先判为“病历记录不完整”，要求研究者补充询问和记录，而不是笼统要求既往源文件。
- **明确否认已经记录：** 这是已有证据，不能因缺少单独的合并用药表或既往文件自动降为证据不足；可根据规则风险保留溯源提醒。
- **阳性既往事实/病程时长：** 筛选病历的转述可作为当前证据，但既往同期病历优先级更高；当规则依赖长期病程、最早诊断或既往治疗时间窗时，应标记来源强度并给出溯源行动。
- **客观检查型规则：** 当前节点应完成却没有结果，属于“必做检查/评分未完成”，不是病历描述不足。
- **已引用文件缺失：** 若病历写明“见某报告/检查”，但文件未上传，属于“已知原始资料未上传”。
- **方案未要求客观源文件：** 不得自行把“必须取得既往原始病历”升级成额外入排条件；只按证据强度提示。

### 14.4 行动责任方收敛

- **研究者方：** 病史采集、病历描述、临床意义/稳定性/适合性判断、检查检验安排及结果临床解释。
- **CRC：** 资料收集、既往记录获取、上传、页面完整性、日期/字段补录和待办协调。
- **CRA：** 源数据一致性核查、缺口追踪与问题闭环；不得代替研究者进行临床判断。
- **受试者：** 作为信息来源提供病史、机构线索、实际用药和依从性信息；行动表述应优先写为“研究者向受试者补充询问并记录”，而非把临床记录责任推给受试者。
- **申办方医学/项目组：** 处理方案解释、跨材料冲突和需形成权威澄清的问题。

## 16. 第三轮确认结果

1. **病史证据：** 明确否认属于已有证据；完全未提及属于病历记录不完整；阳性既往史或长期病程仅由筛选病历转述时可作为当前证据，但必须给出加强的溯源提醒。只有方案明确要求客观证明或资料矛盾时，才升级为关键证据缺口。
2. **行动主语：** 取消“受试者”作为独立责任方。即使信息来源是受试者，补充询问、记录、收集、分析和闭环仍由 `研究者方 / CRC / CRA / 申办方医学或项目组` 承担。
3. **项目看板：** 使用“主状态 + 各类数量”的组合展示，并按临床处理优先级排序。
4. **行动关闭：** 系统可在新增资料、校对或重跑后自动关闭待办；用户可人工 override。自动和人工变更均记录前后状态、触发证据、理由、时间和受影响规则。
5. **旧项目定位：** 旧项目保留为只读反面锚点和经验来源，不作为新模型的迁移写入基座。新模型从头创建新项目并完整走通方案解构、上传、OCR、事实抽取和审核流程。
6. **实施顺序：** 先制作可交互的项目看板、Patient Profile、规则/证据联动工作台视觉原型，确认信息密度和操作路径，再实施数据层和 Graph。

## 17. 设计冻结前会商范围

最终设计和实施计划需经过独立会商，至少挑战：

- AI lead 下“当前证据 + 加强溯源提醒”是否会被误读为证据充分；
- 病历记录不完整、客观资料缺失、检查未完成和需专业判断之间能否稳定分类；
- 单机单用户是否需要 LangGraph，还是显式状态机已足够；
- 自动关闭与人工 override 是否具备可逆、可解释、幂等的状态记录；
- 旧项目只读锚点、新项目从零创建是否会遗漏可复用规则和回归证据；
- 视觉原型是否覆盖项目看板、Patient Profile、规则树、证据定位、行动列表和阶段快照的完整主流程。
