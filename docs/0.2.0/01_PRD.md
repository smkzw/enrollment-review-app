## 1. 为什么有 0.2.0

### 1.1 截至 0.1.x 的事实

- 后端约 24 万行、测试约 22.7 万行、前端约 6.4 万行；方案链占后端约 40%（约 9.4 万行）。
- **从未针对一份已发布的规则集，为任何受试者产出一份含真实结论的审核结果。** 唯一接近的一次（2026-09-11，旧规则）81 条中 55 条"无法判定"，`IN-01 年龄 18–75 岁` 也是无法判定。
- 2026-10-06 至 10-11 共 164 次提交，代码改动的约 92% 在方案链（跨章控制深审），审核链约 0.1%；同期约 27 个方案 Job 全部 `failed_final`，跨章 90 组深审停在约一半。

### 1.2 根因（0.2.0 要消除的四个设计缺陷）

| # | 缺陷 | 表现 | 0.2.0 的处理 |
|---|---|---|---|
| G1 | **既不让人确认，也不让 AI 自动采用** | 0.1.x PRD 禁止"让用户逐条确认模型输出"；代码中 `authorized_clinical_adoption: Literal[False]`；所有门禁失败即关闭。结论只可能来自"AI 一次全对" | 人在两个点上介入：规则包审定（每个方案版本一次）、问题卡片处理（每例少数几个点）。其余由 AI＋程序自动完成，**总是给出结论＋置信＋原因** |
| G2 | **方案范围膨胀为"编译整本方案"** | 跨章控制覆盖 2765 段、1927 单元，延伸到 AE/SUSAR、IRB、发表、参考文献 | 范围限定为四块（§4.1），由医学经理在审定时确认 |
| G3 | **规则与事实没有共享词汇** | 规则谓词 116 种 vs 事实类型 910 种，交集 0；绑定被推给 LLM，输出约 28 万字符 | 引入**变量字典**：规则包声明"需要哪些变量"，取证只针对这些变量定向抽取，匹配按 `variable_id` 确定性完成 |
| G4 | **"审对了"没有外部标准** | 门禁只证明自洽；4600+ 测试全绿而 ReviewRun 为 0 | 测试期以人工 IE 表为金标准逐例逐条对照（§9）；正式使用期以"低置信提示"的准确性为目标 |

### 1.3 0.2.0 的一句话目标

**医学经理审定一次规则包后，对任一受试者的任一审核节点，系统自动给出每条条款的结论、置信和依据；医学经理只处理被标出的少数问题，更正或补证后系统自动重算并保留历史。**

## 2. 产品定位

### 2.1 使用场景（D1）

**前瞻把关为主**：受试者在预筛／筛选／导入／基线（随机前）各节点，随资料到达逐节点审核；审完前不应随机。已入组受试者的历史资料与人工 IE 表，在测试期作为验证集使用。回顾性批量核查（如 CFDI 自查）不是 0.2.0 的设计重心，但同一引擎天然支持逐例回放。

### 2.2 用户

主要用户是中文母语、有临床研究背景的医学经理（MM）。MM 熟悉方案、对入排解读负责，不写代码、不读 JSON、不排查模型。

### 2.3 运行环境

本地单台 Mac、单用户、直接启动、无登录。界面面向最大化桌面宽屏（1080P／2K／4K 及合理缩放），沿用现有康哲视觉系统，不做移动端。

### 2.4 在医学经理工作台中的位置

本子系统是"医学经理工作台"的入排模块。与共享工作台的路由／项目身份对接（见 `archives/trellis-tasks/09-11-e2e-eligibility-review/WORKBENCH_ADAPTATION_20261007.md`）**不在 0.2.0 范围**，在 0.2.0-M3 之后单独立项。

## 3. 核心原则

| 编号 | 原则 | 含义（可执行的判断标准） |
|---|---|---|
| P1 | 先闭环，再扩展 | 任何工作只要不推进"规则包→资料→结论→更正→重算"这条链，就排到闭环之后 |
| P2 | 人只在两处介入 | ① 规则包审定（每个方案版本一次）；② 问题卡片（每例少数几个）。其他环节不设人工确认 |
| P3 | 降级，不阻断 | 某一步失败或不确定时，相关条款降为"低置信"或进入"系统问题"栏，其余条款照常出结论。只有身份类错误（错受试者／错项目／错方案版本／文件哈希损坏）才整体停止 |
| P4 | 全出处 | 每个结论可点回方案原文与病例原件页；有坐标才画框，无坐标显示页级定位并说明 |
| P5 | 只追加，不覆盖 | 原件、OCR 原文、旧事实、旧审核结果、旧报告永不改写；更正产生新版本 |
| P6 | 临床状态与系统问题分开 | "方法不支持""读取失败""模型输出不合法"属于系统问题，不得以临床状态（如"证据不足""需研究者判断"）出现 |
| P7 | 系统不做最终入组决定 | 系统给工作稿；签发是 MM 的单独动作，签发不改变底层结论 |
| P8 | AI 起草与判读，程序核对与计算 | 语义理解（起草规则、抽取数值、读语义条款）交给 LLM；逐字核对、单位换算、日期计算、逻辑组合、结论组装由确定性代码完成 |

## 4. 范围

### 4.1 方案范围：四块（D3）

| 块 | 内容 | 例子 | 在规则包中的形态 |
|---|---|---|---|
| S1 | 官方入选／排除标准全文，保留官方编号与父子逻辑 | IN-01…IN-07，EX-01…EX-16 | `Rule`（IN/EX）及其 `RuleComponent` |
| S2 | IN/EX **明确引用**的章节、附录、表格 | "见附录 3 避孕方法""见表 2 实验室检查正常值范围""第 9.2 节所列药物" | 引用内容作为对应条款的定义依据挂在条款上，原文可展开 |
| S3 | 研究流程表（SoA）中当前节点及之前应完成的检验检查 | 筛选期应做：血常规、sIgE、肝肾功能、心电图… | `Rule`（REQ-xx，`RuleKind.REQUIRED_PROCEDURE`），判断"是否做了、结果是否齐全、是否在时间窗内" |
| S4 | 禁用药、合并用药、伴随治疗章节中与入组资格相关的限制 | "筛选前 4 周内使用过全身糖皮质激素者不得入组" | 禁用药条目（药物或药物类别＋洗脱窗＋方向＋原文），按用药史计算 |

**不纳入**：方案正文其余部分（统计、AE/SAE 报告流程、伦理、数据管理、发表、参考文献等），以及 0.1.x 中"全方案跨章控制发现／深审"的全部范围。如 MM 在审定时发现某条资格要求藏在其他章节，可手工把该段加入 S2（§6 R-A2）。

### 4.2 审核节点

沿用现有 `ReviewStage`：`pre_screening`（预筛）、`screening`（筛选）、`run_in`（导入／洗脱）、`baseline`（基线／随机前）。节点由该版方案决定，不按示例项目写死。随机节点作为独立 stage 不在 0.2.0 范围（随机仍作为时间锚点 `AnchorType.RANDOMIZATION_DATE` 可用）。锚点日期（知情同意、筛选、基线、随机、首次给药等）取自现有 `ReviewEpisode.anchor_dates`。

### 4.3 病例资料

几十至一百余页的多文件扫描件：检验单、病历、手写批注、手机照片、屏幕翻拍、邮件。文件／页面未能读取时必须显式记录为系统问题，不得静默省略。

### 4.4 0.2.0 使用的数据

| 用途 | 方案 | 受试者 | 说明 |
|---|---|---|---|
| 开发 | MG-K10-SAR-001 临床研究方案 V2.1（20250919） | 中心 31（河北省中医院）`31001`：5 份 PDF、24 页 | 已有 OCR、Profile v3、官方 IN/EX 草稿 rev21 |
| 测试期验证 | 同上 | 中心 31 其余已入组／筛败受试者 | 与人工 IE 表逐条对照 |
| 留出（不得用于调参） | CMS-D001 银屑病方案 v1.0（2025-12-21） | 22 例筛败受试者（v1 时期已有人工对照） | 0.2.0-M3 才首次运行，验证换方案后的规则包上手和泛化 |

留出集的限制：D001 方案在 0.1.x 中已用于方案解构开发（30 余个测试与代码文件引用 D001），因此它**不是方案起草器的干净留出**；它对 0.2.0 新增部分（变量字典、定向抽取提示、置信规则、结论组装）和 22 例受试者资料仍是留出。M3 报告须如实注明这一点。

真实资料、数据库、`.env` 不入库（存放在本机 `data_v2/` 或 `ENROLLMENT_V2_DATA_DIR`）。

## 5. 主流程

```
F1 方案上线（每个方案版本一次）
   上传方案 DOCX → AI 起草 IN/EX＋列出引用章节/SoA/禁用药 → MM 确认范围
   → MM 逐条审定（可改写）→ 全部审定后发布规则包 vN

F2 受试者节点审核（每例每节点）
   选项目/受试者/节点 → 上传资料（全量或增量）→ 自动：OCR → 定向抽取 → 逐字核对 → 判定
   → 进入"问题卡片"页：只列需要 MM 处理的点；其余条款已自动判定，一键展开

F3 处理问题
   点卡片 → 三栏核对（条款队列｜判定详情｜原件）→ 更正数值 / 上传补证 / 标记已核 / 引用研究者书面判断
   → 系统自动重算受影响条款 → 生成新版工作稿（旧版保留）

F4 历史与报告
   版本列表、前后对比、打印版报告；签发（0.2.0 只留入口与记录，不做电子签名合规）
```

## 6. 功能需求

需求编号用于计划与验收追踪。每条"验收要点"必须能在 `04_ACCEPTANCE.md` 找到对应检查。

### A. 规则包（方案侧）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| R-A1 | **起草**：沿用现有官方 IN/EX 解构（`protocol_workbench_service` 生成步骤）。SAR 方案直接从本机数据库中已有的官方草稿 rev21（23 父规则：入选 7、排除 16；86 组件；141 条件；来源标识 `1153e25b…`，以数据库实际读回为准）继续，不重新跑 | 规则包页面显示 23 条父规则及子项，原文可展开 |
| R-A2 | **范围解析**：程序从 IN/EX 原文识别"见第 N.N 节／附录 X／表 N"等引用，自动匹配到方案结构中的章节；同时定位研究流程表和禁用药／合并用药章节。结果以"范围清单"呈现，MM 可增删（手工加入某段并写一句理由） | 范围清单列出每段的标题、页码、引用它的条款；MM 的增删留痕 |
| R-A3 | **研究流程表**：沿用 `app/protocols/procedure_catalog.py` 的确定性解析，产出当前节点及之前应完成的检验检查（REQ-xx）。MM 在审定页可：①把某项标为"不作为入组前必需"（保留但不判定，报告中列为"已由 MM 排除"）；②为某项指定"必需结果变量"（如血常规须有 EOS、WBC），用于判断"结果是否齐全" | REQ 条目与流程表的行列一一对应，可回看表格原格；排除与必需结果变量的设置留痕 |
| R-A4 | **禁用药清单**：AI 从 S4 章节提取"药物或类别＋洗脱窗＋方向（之前多久内不得使用／之后不得使用）＋原文"，MM 审定 | 每条有原文出处；洗脱窗可为固定时长或"N 个半衰期" |
| R-A5 | **变量绑定**：每个需要病例数据的条件绑定到变量字典中的一个变量（如 `age_years`、`blood_eos_count`、`serum_sige_specific`、`tnss_total`）。AI 建议绑定，MM 在审定时可改选；字典中没有的变量，MM 可新增（名称、类型、单位） | 发布时所有确定性条件都有 `variable_id`；新增变量随规则包版本保存 |
| R-A6 | **静态检查**（提示，不阻断）：原文中的数字／单位／比较方向与结构化条件是否一致、引用的章节是否已纳入、时间窗是否缺锚点等。结果作为每条规则旁的提示 | 提示可见、可忽略；忽略需 MM 点选"已核" |
| R-A7 | **逐条审定**：每条父规则（及 REQ、禁用药条目）有"审定通过"动作，记录审定人、审定人类型、时间、该条内容哈希和可选备注。审定按**该条内容哈希**认定：该条内容（含变量绑定）改动后其审定自动失效；其他未改动条目的审定在新草稿修订中继续有效。审定人类型分"医学经理"与"构建者验证"：含任一"构建者验证"审定的规则包只能发布为**验证用**，其工作稿顶部显示"规则包未经医学经理审定，仅供验证" | 审定记录可在历史中查看；验证用规则包有明显标识 |
| R-A8 | **发布条件**：①全部 IN/EX 父规则、REQ、禁用药条目已审定；②无结构性错误（编号重复、父子树断裂、逻辑表达式不合法、身份不一致）。不再要求跨章控制目录 | 满足条件即可发布；不满足时页面明确列出差哪几条 |
| R-A9 | **版本**：方案修订或规则改动产生新规则包版本；旧版本及基于旧版本的审核结果保留且可查看 | 新旧规则包版本并存 |

### B. 取证（资料侧）

| 编号 | 需求 | 验收要点 |
|---|---|---|
| R-B1 | **上传与 OCR**：沿用现有资料快照、去重增量上传和 OCR 管线（主 OCR＋可靠原生文字）。不恢复逐页双 VLM | 上传后每页有处理状态；读不了的页进系统问题栏 |
| R-B2 | **需求清单**：由"当前节点适用的规则包条件"推出本例需要的变量、REQ 检查项、需核对的用药史 | 需求清单可在调试视图中查看（MM 不需要看） |
| R-B3 | **定向抽取**：LLM 按需求清单在 OCR 文本中抽取：变量 ID（只能从清单中选）、原值、单位、日期及其角色（采样日／报告日／就诊日）、页码、原文摘录。用药抽取药名、剂量、起止日期、是否持续 | 抽取结果每条带 `variable_id`（或空）及页码、摘录 |
| R-B4 | **逐字核对与归属核对**：程序验证①摘录在该页有效文字（OCR＋已保存更正）中逐字存在；②数值出现在摘录中；③检验项名称（变量中文名或常见写法）与数值在同一行／同一表格行；④该数值不是参考范围的一部分（如"3.5–9.5"中的数字）。①②不通过→拒绝并记系统问题；③④不通过→仍采用但标低置信（"数值归属需核对"） | 编造摘录被拒；取到参考范围或邻行数值的情况被标出 |
| R-B5 | **风险标记**：对通过核对的事实打标记（§8 风险标记表），标记只影响置信，不阻止采用 | 临近阈值、手写、日期角色不清等能在判定详情看到 |
| R-B6 | **自动采用**（D5）：通过逐字核对的事实自动进入判定。不需要逐字段人工核实授权 | 无人工操作时，31001 的确定性条款能得出结论 |
| R-B7 | **多个值的选取与矛盾**：同一变量有多个值时，先按条款时间窗过滤；窗内取**距节点锚点最近且不晚于锚点**的一次作为判定值。只有**同一采样日（或同一份报告）出现不同值**才算"资料矛盾"，并列出全部来源、不自动择优。不同日期的多次结果不算矛盾；若窗内其他结果会导致不同结论，判定值照用但标低置信（"窗口内多次结果结论不一致"）。方案规定了复查规则（`repeat_scheme`）的条款按复查规则选取 | 复查、多次检验不会大量变成"资料矛盾"卡片 |

### C. 判定

| 编号 | 需求 | 验收要点 |
|---|---|---|
| R-C1 | **确定性条款**：用现有三值求值器 `app/domain/expression.py` 计算（比较、单位、时间窗、半衰期、ALL/ANY/NOT）。输入按 `variable_id` 选取事实 | IN-01 年龄、IN-05 EOS 等得出真实结论 |
| R-C2 | **研究流程表完成度**：REQ 条目按"已做且结果齐全／已做但结果不全／未见记录／未到期"判定，沿用 `app/projections/evidence_expectations.py` 的逻辑 | 31001 筛选期 REQ 列表有真实状态 |
| R-C3 | **禁用药**：用药史中最后一次使用日期（持续使用则视为到锚点日）与洗脱窗比较；药物类别归属用一张小的类别成员表（MM 可补充）。**只有同时满足**以下三条才可给"未触发"：①资料范围内有用药史来源（病历用药记录、合并用药记录等）；②本例全部用药均已归类（类别表中找不到的药名单列为"未能归类的用药"卡片）；③没有落入窗口的使用记录。只有开始日期、间断使用、持续状态不明的用药，相关结论最多为低置信 | 示例：近 4 周全身激素使用 → 已触发／未触发／低置信；未归类药名出现卡片 |
| R-C4 | **语义条款**（`semantic_proposition`，如"符合季节性过敏性鼻炎诊断"）：LLM 在本例资料中寻找支持或否定的原文，给出结论建议＋引用；程序逐字核对引用 | 结论附原文引用；无引用时不得给"满足" |
| R-C5 | **研究者判断条款**（`requires_professional_judgment`）：沿用现有判断检索（judgment_search）找研究者书面判断；找到且逐字核对通过→按其记录给结论并引用；未找到→"需研究者判断" | 判断引用可点回原件 |
| R-C6 | **"本次资料未见记录"政策**（沿用 2026-10-06 用户决定）：对已提供且已读取的资料范围，常规既往病史类排除条款未见记录→"未触发"，原因写明"本次资料（N 份）未见相关记录"。使用该政策前，程序先用条款关键词与变量常见写法对全部页有效文字做一次**确定性关键词扫描**：有命中→不适用该政策，改出卡片"资料中有相关字样，请核对"（低置信）。资料范围内没有病历／既往史类文件（按上传时选择的资料类型判断）→低置信。按此政策得出的结论在"其余已自动判定"中**单独成组**显示（"按本次资料未见记录判定 N 条"），评测时单独统计 | 报告写明资料范围；不伪造"原件明确否认"；关键词命中时不出"未触发" |
| R-C7 | **处方≠实际使用**（沿用 2026-10-06 用户决定）：处方、医嘱、购药记录可作为既往用药依据；实际剂量、连续使用、停药日期不得推断补造，不清时置低置信 | 示例卡片显示"停药日期不清" |
| R-C8 | **结论组装**：每条条款输出 §7 的六种结论之一＋置信（高／低）＋一句原因＋依据列表。父规则组合：入选父规则＝全部子项满足才"满足"，任一子项"不满足"即"不满足"；排除父规则＝任一子项"已触发"即"已触发"，全部子项"未触发"才"未触发"；其余情况取子项中需处理程度最高的状态（资料矛盾＞需研究者判断＞证据不足＞未到期）。尚未结构化的子项（`restricted_components`）按系统问题处理，父规则不得因此给出高置信"满足／未触发" | 工作台显示结论、置信、原因；父子结论一致 |
| R-C9 | **系统问题栏**：方法暂不支持、页读取失败、模型输出不合法、抽取摘录核对失败、子项尚未结构化等，单独列出，写明影响哪些条款、可用的替代路径（如"已列原文，请人工判断"）。受影响条款不显示六种结论词，显示"系统问题"（见 §7.3） | 系统问题不以临床结论词出现 |

## 7. 结论与置信（D8）

### 7.1 六种结论

| 结论（入选条款） | 结论（排除条款） | 含义 | 内部枚举（`ComponentDecision`） |
|---|---|---|---|
| 满足 | 未触发 | 有足够依据表明条件成立／排除情形不存在 | `inclusion_met` / `exclusion_not_triggered` / `requirement_met` |
| 不满足 | 已触发 | 有依据表明条件不成立／排除情形存在 | `inclusion_not_met` / `exclusion_triggered` / `requirement_not_met` |
| 证据不足 | 证据不足 | 判定所需资料在本次范围内没有找到 | `indeterminate` |
| 需研究者判断 | 需研究者判断 | 方案要求研究者专业判断，且未找到书面判断 | `professional_judgment` |
| 资料矛盾 | 资料矛盾 | 同一变量不同来源互相冲突 | `conflict` |
| 未到期 | 未到期 | 该要求属于后续节点 | `not_due` |

`not_applicable`（确有依据不适用，如男性受试者的妊娠检测）显示为"不适用"，归入"其余已自动判定"。

### 7.2 置信

"满足／不满足／未触发／已触发"四种结论带置信"高"或"低"。**满足以下任一条即为低置信**，并显示第一条命中的原因：

1. 决定该结论的任一事实带风险标记（§8）；
2. 语义条款的结论由 LLM 建议且未经 MM 已核；
3. 依据来自"本次资料未见记录"政策，且资料范围内没有病历／既往史类文件；
4. 时间计算用到了部分日期（如只有年月）；
5. 父规则的某个子项为证据不足或系统问题，但父规则仍按其余子项给出了结论（例如 ANY 分支）；
6. 时间窗内存在会导致不同结论的其他结果（R-B7）；
7. 禁用药条款不满足 R-C3 的三条"未触发"前提之一。

置信只用于"满足／不满足／未触发／已触发"四种结论；"证据不足""需研究者判断""资料矛盾""未到期"的置信字段为空。MM 对某条结论"标记已核"后置信改为高；只要该条的输入（所用事实及其修订、规则内容哈希）不变，已核状态在后续版本工作稿中继续有效。

### 7.3 系统问题不是结论

方法暂不支持、读取失败、模型输出不合法、子项尚未结构化等，不使用以上任何结论词。受影响条款的显示状态为"系统问题"（第七种显示状态，不是临床结论），原因写"系统暂不能……，已……（替代路径）"，并在系统问题栏列出一次。在问题卡片页，这类条款放在卡片列表末尾的"系统问题"分组，与临床问题卡片分开。

## 8. 风险标记

| 标记 | 触发条件 | 显示文案 |
|---|---|---|
| `NEAR_THRESHOLD` | 数值与方案阈值的相对差 ≤ 5%（可按变量配置） | 临近阈值 |
| `HANDWRITTEN` | 事实来自手写区域或手写批注 | 手写内容 |
| `LOW_OCR_CONFIDENCE` | 页／区域 OCR 风险标记为需核对，或页属于照片／翻拍且该区域未经局部复核 | 识别可能有误 |
| `DATE_ROLE_UNCLEAR` | 只有一个日期且无法判断是采样日、报告日还是就诊日，而条款对日期敏感 | 日期含义不清 |
| `UNIT_INFERRED` | 原文无单位，单位由程序或模型推定 | 单位为推定 |
| `PARTIAL_DATE` | 日期只有年或年月 | 日期不完整 |
| `PRESCRIPTION_ONLY` | 用药依据只有处方／医嘱／购药记录 | 仅有处方记录 |
| `SINGLE_WEAK_SOURCE` | 唯一来源为邮件、口述记录、屏幕翻拍 | 来源较弱 |
| `IMPLAUSIBLE_VALUE` | 换算后的数值超出变量字典中该变量的合理范围（防小数点、单位、数量级错读） | 数值不合理，请核对原件 |
| `ATTRIBUTION_UNCERTAIN` | 检验项名称与数值不在同一行／表格行，或数值可能取自参考范围（R-B4 ③④） | 数值归属需核对 |

标记由程序判定（不由模型自报）。0.1.x 中"同页存在未核实读数则该页所有带值候选一律阻断"的规则（`app/domain/gates/fact_evidence_closure.py:581-608, 646-655`）改为对相应事实打 `LOW_OCR_CONFIDENCE`。

## 9. 测试期评测与长期目标（D4）

- **测试期**：人工 IE 表、合格性讨论表、入组审核邮件为金标准。主要指标（初始建议值，0.2.0-M2 结束时由用户确认）：
  - **静默漏判 = 0**：人工判"不满足／已触发"的条款，系统给出"满足／未触发＋高置信"的次数；
  - **不合格提示率 ≥ 95%**：人工判"不满足／已触发"的条款中，系统给出"不满足／已触发"或任一需处理状态（低置信、证据不足、需研究者判断、资料矛盾）的比例；
  - **每例问题卡片中位数 ≤ 8**（筛选期）；
  - **有资料时确定性条款可判率 ≥ 80%**。
- **正式使用期**：不依赖金标准。系统的价值是把注意力引到真正的风险点：低置信与证据不足的提示要准，高置信结论要可靠。指标沿用"静默漏判"和"卡片数"，由 MM 的"标记已核"与更正记录持续回看。
