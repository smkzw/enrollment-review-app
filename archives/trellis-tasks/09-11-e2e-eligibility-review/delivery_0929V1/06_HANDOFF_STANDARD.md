# 0929V1｜Handoff撰写规范：让下一位审阅者能独立判断

适用于本轮及之后的阶段交付。它约束的是**报告事实和证据的方法**，不替产品增加临床门禁。不得把本文变成每次改一行代码都要写一份报告的新负担。

## 1. 只维护两份核心交接

**HANDOFF正文**：建议800–1800汉字加必要表格，复杂风险可放附录，不因字数删掉关键限制。目标是几分钟看清改了什么、能做什么、何处没做、依据在哪里。

**review_index.json**：存代码快照、变更与证据／测试索引。由现有任务、Git和测试日志整理；正文引用ID，不重复粘贴长日志。正式临床原答只留受控位置。

一个功能包或暂停／阶段交付写一次，不每个补丁写一份。维护一个 `HANDOFF.md` 索引指向最新文件；旧handoff原样留档但不并列成为现行指令。`implement.md` 保留一张当前状态表，历史在后，不持续插入互相矛盾的“最新”。

## 2. 正文按固定顺序写

### A. 审阅入口与代码边界

明确本轮、代码基线、实际测试代码、交付代码、分支、现场状态查询时间及时区。代码已提交与本机未提交分列；对只在本机的改动写“作者报告／本机结果，当前远端不可核”，不写“仓库已修”。

不要求在handoff写它自身最终提交哈希。先固定产品代码提交，文档随后提交；最终消息给出实际远端HEAD。测试后的文档-only变化列明即可，不要为追自己的哈希循环提交。

若测试使用脏工作树，以基础提交＋涉及执行的源码/测试/依赖配置清单及哈希标识；包含实际用到的未跟踪模块，不能只hash几份改动忽略其导入依赖。不要对整个含临床库的目录递归hash，既昂贵又可能泄露信息。

### B. 本轮用户能力增量

用可执行动作描述，最多3项。例如“某个完整有源受限包已能形成独立条款工作稿”“困难表格原件可核回目标列”。若只完成结构单元测试，直接写“本轮无新真实用户闭环”。

每项列生产、保存、消费、API/UI是否真实接通。不是所有修改都必须同时含4层；不适用说明原因，不能用“全链”概括尚未测试部分。

### C. 发现与修复：事实先于解释

每条主张给ID，使用如下状态：**已直接观察、已复现、仅静态定位、作者报告待核、推测、已反证、未验证**。状态表示证据层级，不表示严重性。

表述至少包含：预期、实际、触发条件、精确代码入口、证据ID、影响范围、是否到达最终消费者。局部函数反例不能写成“真实患者被误判”；模型返回200不能写成“医学理解正确”；有引文不能写成“完整覆盖”。

修复前失败和修复后验证可以引用同一缺陷ID，但必须标明不同代码快照。仍失败、未归因和跳过都保留，不只报最后绿色结果。旧测试可能过期，也可能暴露真回归；没有逐项依据不能一概归为夹具问题。

### D. 测试与真实运行

每项列代码快照、命令／产品入口、环境、执行时区时间、数据类别与版本、预期／实际、退出码、passed/failed/skipped/not_run及证据位置。摘要中的总数必须能对应日志，不能混加重复运行。

模型调用另列请求的／实际响应的模型、端点档案（不含凭据）、图像是否实际发送、调用次数及范围、用量（缺报null）、耗时分项、重试、结束状态、原答哈希与可访问性。/models清单、简单ping、支持JSON或一次stop都不等于真实图像读取通过。

真实浏览器记录页面入口、CSS视口、缩放、动作和结果；不能用编译通过或组件截图代替实际原件定位。正式签发／规则激活分别记录授权和运行，不用会商意见代替。

### E. 反思与方向建议——不得伪装成事实

独立成节。每个根因假设列：支持证据、反证／未知、合理替代解释、什么新证据能推翻它。证据不足写“未排除”，不是“根因必然是模型／图／数据”。

建议必须写收益、风险、验证办法和是否待用户裁定。普通设计取舍不写“唯一安全动作”；真正硬禁令须指明来源、身份或权限风险。允许审阅者不同意作者建议，不要求先接受作者诊断才能看证据。

### F. 当前缺口与下一步

最多3项可验证动作，写依赖、是否能并行、完成产物和停止条件。R1与B方向已批准，不重新列为待批准。真实医学歧义、软件缺口、资料缺失和授权缺失各归责任方；不能把技术工作推给研究者。

## 3. “已完成”用语的等级

| 说法 | 最低证据 | 不能替代 |
|---|---|---|
| 代码已修改 | 可访问代码快照／补丁及入口 | 运行通过 |
| 单元／合同已通过 | 对应快照的实际命令和原日志 | 产品集成、临床正确 |
| 已集成 | 实际生产→保存→消费／API的结果 | 真实病例和宽屏可用 |
| 来源引文已核 | 所引原文、身份和位置可核 | 含义、作用域、执行能力 |
| 有限视觉实验有收益 | 同任务终点对照、错误与未知、时间及局限 | 全资料通用、默认迁移 |
| 完整病例已核 | 授权真实材料、完整范围、来源与结果逐项验收 | 最终入组／签发授权 |
| 产品已交付 | R1正式验收所有必要结果成立 | 不能由本轮小样自动推出 |

禁止“完成95%”“已解析所以可发布”“阻断从21降到19所以质量提高”。若要报完成率，先提供固定分母和每项实证；当前默认报告能力清单而非百分比。

## 4. 可审阅证据，而不是仅存于本机的路径

审阅材料分四类：

- **reviewer_accessible**：当前审阅者有权且有方法取得的代码、净化技术回执、合成复现。
- **local_only**：存在于受控本机，但当前外部审阅者不可读取；不要称已被外部验证。
- **missing**：应该存在但已缺失。
- **not_provided**：本轮未提供或尚未整理。

数据敏感性与可访问性分开。真实病例、方案全文、密钥和原始模型回答默认不进普通GitHub交接包；确需共享按授权另走受控文件路径。保留原文件及哈希，审阅副本可净化，但净化处与不可推断的信息明确说明。哈希不是医学真实性证明。

仅有本机路径时，可补充合成同构夹具、允许公开的最小代码片段、输入字段结构与错误码；必须标明这些不能代替原件临床审核。不要为了外部可审而批量上传原始临床材料。

## 5. 最小交付索引，不另建系统

`review_index.json` 仅为审阅索引，非产品输入或临床授权。核心字段见模板：代码快照、声明、测试、证据、假设、建议、下一步。沿用现有日志即可，不要求再建数据库或新平台。

可选运行：

```bash
python3 tools/check_handoff.py path/to/review_index.json
```

未填写的模板不能当正式索引通过；只做结构检查时用 `--allow-template`。检查器不验证真实代码／日志内容、保密性、医学正确性或GitHub实际访问权限，不能作为临床门禁。无需为了使用检查器暂停产品工作。

## 6. 最终给用户的消息

先一句说明本轮新增的真实能力，再给可访问交接入口和代码版本，然后说明关键未完成与需要裁定的问题。没有方向性问题就不制造问题。不能末尾只贴一大段“下一安全动作”，让用户看不到实际结果和证据。
