# 1001V1深度复盘｜长期构建为何仍有错漏

日期：2026-10-04。性质：工程/产品复盘，不是临床批准或完整交付证明。
事实入口：`HANDOFF_20261004_1001V1_PAUSE.md`、`implement.md`文头、同日review_index。
本轮只读独立审阅及当前反例支持下述结论；没有重新检查所有历史临床原件，不把推测写成事实。

## 1. 先给结论

来源可追溯、状态可恢复、确定性数值/时间、追加更正、工作稿与签发分层需要保留。不能为了短时跑通去掉这些边界，也不能把“模型两次相同”升级成临床正确。

构建迟迟不能完整交付，不是单一模型慢或缺API。至少有四种耦合：来源准备不全、临床含义和工程装配混合、正确正例消费者不足、恢复与验证不能局部精确收口。它们让一次真实运行先暴露一个错误，修复后再暴露下一层。

目前实现了许多真实基础能力，却尚未证明最重要的一次完整用户动作：完整当前规则下审核一例，回原件、更正/补证、得到新报告而保留旧历史。批次数和通过测试数不能替代这个终点。

## 2. 战略层：什么正确，什么需改

| 方向 | 判断 | 来源支持与边界 |
|---|---|---|
| 内置前置方案Agent | 保留 | 官方、跨章、定义、例外及节点必须同源；另一份总结稿会制造真相分叉 |
| 可靠文字主读＋必要局部视觉 | 保留并真实验收 | 原生结构能给位置，纯文字OCR未必给数值行列和手写归属；不恢复全页双读 |
| graph engineering | 用于来源、依赖、状态与历史是合适的 | 不应把每个自然语言细节提前强迫进入固定图形/最终JSON；图不能证明医学含义 |
| 安全门禁 | 保留硬身份/来源/权限/确定性边界 | 语义启发式不是硬事实，不能机械扩展到正常正例全拒 |
| R1混合执行 | 按已批准目标继续 | 合法有源未决不必冻无关正确要求；错义、未读完和软件能力缺口仍不能伪装通过 |
| 固定workflow＋单语义主责 | 1001候选方向合理，未全面验证 | 短JSON、引用、速度不代表消费者可用；局部取证须由具体缺源触发 |
| 更换模型/增加平台 | 当前不作为前置 | 本轮发现明确工程首错；换模型同时换框架会失去归因能力 |

实质风险是目标置换：开发把“能拒绝越来越多坏结果”当成果，把“普通有据结果可安全进入报告”推迟。拒绝必要，但用户买的是能完成审评，不是只能看未决清单。

## 3. 战术层：本轮可复核的问题

### 3.1 来源准备的分母曾错

只从必做项目看访视集合，漏掉没有操作的筛选列。后果是错误推断同一访视，模型再怎么解释也救不了输入中不存在的结构。改为冻结完整物理表头，先判结构真实性，再判断语义节点。

教训：完整来源清单不能由模型返回或语义目录定义。原文空间图与语义关系分开，后者引用前者。共同标题、表格、脚注、零操作列都是来源，不因暂未生成规则消失。

替代解释：有些协议联合访视确实与筛选同义。反证因此必须包含真正独立筛选列，不应一律禁止别名。当前新反例正是为了区分这两种情况。

### 3.2 “两个模型/两次核对”不能弥补错误问题

IN04真实第一读把末尾注释归基线，但引用只有注释自身，没有明确节点。原先想沿最近小标题继承，是未经证明的假设。应保存已核清兄弟，明确注释需要什么依赖证明，不让一致投票制造依据。

核查机制本身有必要：关键范围可以改变医学判断。方向错误在让核查反复产完整工程包装、所有兄弟全通过才收口，或只看标签一致。应核关键维度、保留实际原答、按条目证明，不反复复写无关内容。

### 3.3 恢复是授权/状态问题，不仅缓存问题

请求保存发生在加入stream参数之前，预算计数却按实际wire。二者hash不同不是原答无效，更不是新调用许可。恢复必须证明实际消息/源/参数一致，并在原持久最新账本内续走。

同编号账本不等于同一授权状态。一个已发出后超时的调用已花次数；不能从早期快照复制一个同ID账本回来。独立审阅指出这项反例后，已补范围和总账本最新状态及前缀核验。

### 3.4 测试模拟曾与真实预约时机不同

之前合成恢复用例在得到回答后才预约；第二次超时发生在预约前。真实产品先预约，再发请求。这个用例虽绿，恰好漏掉本轮最重要边界。

改为真实产品传输和原文件账本，用离线流注入：第一答保存后宿主中断；第二答实际发出后超时；同ID截断；缺总账本；换模型/来源；损坏原答。检查不是次数多，而是它是否在相同因果位置失败。

### 3.5 测试错误也增加了不必要轮次

新增用例用非64位hash被正式缓存拒绝；一次命令猜了不存在的测试路径；旧测试只断言异常而没有看正式gate。这些是所有者构造/阅读不足，不应称旧夹具问题来掩盖。

改进：先读被测入口的真实合同和完整依赖；一个功能包集中运行相连消费者。已有测试重复计数不累加，测试后改源码应标旧证据范围。必要导入/危险写入校验不取消。

## 4. 为什么一两百批以后仍可能大量漏错

1. 来源覆盖、语义、装配、门禁、资格、报告是不同层；早期测试多在其中一个层，而最终临床链要求各层成立。
2. 强类型最终规则把时间/量词/例外/定义挤进有限字段；若作者Schema和实际消费者能力不匹配，格式通过仍不可用。
3. 共享父项让一个失败牵动所有兄弟；更长上下文增加成本，也增加无关修改机会。
4. 词面拒绝检查能发现已知错误，却可能误拒换说法的正确结果；缺少正例/等义变体/反事实/消费闭环时容易补一个又坏一个。
5. 成功缓存、失败答、实际已花额度、派生新输入和正式采用混在交接里时，接手者可能重复诊断、错误复用或退回整包重读。
6. 不同会商路线、输出身份和fallback也需要核实际回执，顾问报告或工具exit0不自动代表有效独立审阅。
7. 本机长期大量dirty使远端审阅与实际测试代码不同，重复交接增加归因成本。应交付明确相连源码和哈希，不扫描/打包临床数据。

以上不是完整统计归因：缺少每批耗时/首错统一数据，不能给百分比或声称所有慢调用都由Prompt导致。

## 5. harness耗时反思

本轮source读291.767秒，input5315/completion19618，厂商思考细分字段与实际输出矛盾，费用未知。不能以配置65536当实际输出，也不能把reasoning_tokens=0当无思考。

最后proposal读187.587秒、input16066/completion14534；两读总479.355秒，不含工程审阅/恢复/检查时间。实际消费者只确认四项对应关系；另三项被拒，其中一项是提案节点不一致，两项是注释范围无源证明。模型写agreement=true仍可能被真实合同反证。输入/生成量以及错误问题所带来的复核成本都要优化，不能只讨论模型标称速度。

输入并非本次唯一瓶颈：模型生成较长、任务要求复杂、工程形状与来源不确定共存；旧整父提案更长，但本轮局部仍不快。必须同时看首次正文、真实用量、一次失败后有没有重做无关部分。

更有效方向不是简单调低输出或截掉来源：

- 宿主保留完整结构与依赖，给当前语义单元足够且不重复的上下文；最终ID/包装由程序完成。
- 结构修复不重新作完整临床判断；来源不足才扩大读取，真实歧义停止自动消解。
- 已完成有据子项独立保存；同一预算恢复尚未发出的步骤，不重读成功来源。
- 高后果复核检查原文关键维度，不能成为完整答案第二次生产。

这四项需要同终点对照，不凭Prompt变短或一次速度快宣布默认迁移。

## 6. 后续只推荐三项

### 建议一：先交付一个垂直用户动作

在完整同源R1合同下选原件关系清楚的单值/日期，贯通工作稿、原件定位、更正后新结果。收益是尽早暴露资格/消费/UI实际缺口。代价是不能靠单个能力小样声称完整规则包；仍须完整覆盖和采用检查。

### 建议二：以错误家族收口，而非下一错误补丁

对来源功能、作用域、时间/数量、恢复四类分别给正常正例、等义变体、危险反事实、故障恢复和真实消费者。已知批次作为回归，不再称未见留出。收益是减少专用修复和整方案长跑；代价是需要一次准确选取最小代表性材料。

### 建议三：保持一个当前状态和可复查源码

文头一张表、一个handoff、一个索引；历史回执保留附录。源码提交、测试字节、运行库、模型路由和授权明确绑定。收益是接手不再花大量轮次发现“测试的不是远端代码”。不因此批量提交临床原答、删除失败或清理他人dirty。

## 7. 未来能否不再大量批次

不能有据承诺还需N批或几天完成。可以改变验收单位：以完整用户动作/错误家族为单位，不以每个提示、每个guard、每个模型调用为单位。若再出现相同故障无新证据，停止该分支，改变假设并推进独立用户链。

本次暂停应保留最后真实回执、不可采用的候选和原账本。下一Agent先看实际未决，而不是继续把所有条目“刷绿”。最重要教训是：**检查机制只有同时证明正常结果可用、危险结果不可用，并接到用户真实动作时，才成为产品质量；检查数量本身不是质量。**
