# 入排审核系统：多 Agent 协作、快速有源草稿与临床语义核对实施报告

> 日期：2026-09-17｜版本：3.0 真实方案对照与快速有源草稿增补版  
> **本版替代V1/V2的现行执行建议。** 保留内置前置方案Agent和受试者OCR/局部VLM/人工核对主线；只对方案候选交付、原编号映射、时间/例外核对和真实跨章依赖作增量优化，不再启动一轮全架构重构。  
> **最新已确认：产品采用多 Agent 职责协作，方案 Agent 必须集成在现有框架内；用户手工调用外部 AI 后导入 JSON 不作为主路径或首版必经步骤。**

## 0. 接手者五分钟入口

### 0.0 本轮增量：先读这一页，不重复读全部历史

用户提供了另一系统“三分钟”生成的SAR规则文字，以及真实`MG-K10-SAR-001 V2.1`方案。本轮已对照全部展示的入选/排除组及核心跨章来源；详见同目录 `SAR_PROTOCOL_THREE_MINUTE_COMPARATIVE_REVIEW_20260917.md`。比较对象只是展示文本，不是对方内部JSON或代码；三分钟未独立测量，洗脱表尾部粘贴不全。

**保留V2方向，只落实六项增量：**

1. 首个合法、有源的临床草稿尽早显示；它就是后续核对/编译所用的同一草稿，不新增一轮自由总结模型调用。
2. 模型只起草一份条件与例外；“判断点/通过/不通过/速查表”从同一对象投影，避免反向文字改变原条件。
3. 原编号检查从计数升级到`原研究部分+父编号+源父子范围+具体内容`对应。SAR对照证明16条对16条也可能映射错误；16不是通用常量。
4. 时间按原子明确锚点和用途；条件、例外、未知、N/A、未到期分别保留，禁止全局随机日覆盖。
5. 优先完成真实方案明确的跨章依赖；附录分类表不假装精确换算，编辑残留和源冲突不由模型代修。
6. 同时记录首次有源候选、完整候选、源核对、可发布和发布的时间，另计人工等待。不用“三分钟”硬超时，也不用复杂性为无谓耗时辩护。

**实施只改原P0.P三个条目和既有接点，不给每个发现建任务/Agent/表。**患者读取、事实/Profile、统一求值、原件与更正、P1–P5范围不变。对照中的SAR数值/药物只作本方案数据，不写进通用提示或求值器。研究者/用户不需要替开发者再次整理这份方案。

全文可按任务按需读；本页→第2.21–2.25节→P0.P→第12节Goal为本次增量入口。比较审阅不是自动批准新方案解释或修改历史规则。

### 0.1 本次目标不是重建系统，也不是取消前置 Agent

在现有 FastAPI / React / SQLite / JobRunner / 事实与规则体系内，打通：

**正式 DOCX → 内置方案 Agent 解构与核对 → 共同发布完整规则及跨章要求 → 一个受试者当前节点的全部资料 → OCR/局部视觉与事实整理 → 逐条审核及具体未决项 → 可回原件的报告 → 一次更正/补证后新审核。**

已有可验证完整的现行规则集，可以在开发期间复用来隔离资料侧问题；但**仅复用旧规则跑通病例，不再足以证明本轮全部完成**。最终交付必须包含优化后的内置方案入口真实运行、发布并被下游消费。

“完整”指实际规则和资料范围被完整处理，不要求把不可读/缺证内容强判为真或假。系统必须产生有依据的有效结果，不能以全 UNKNOWN 或全转人工凑完成。

### 0.2 接下来先做三件事

1. 在当前工作树核清两条实际调用链：方案上传→官方/跨章解构→共同发布；资料上传→读取来源→事实发布→审核报告。用一页列明已有能力和真实断点，不重新全仓研究。
2. 方案侧优先修现有装包、来源别名、作者Schema/水合一致，让同一合法候选尽早显示；核对原编号/源父子映射、时间/例外和跨章依赖，再有据局部修订；资料侧保留原图准备，接主 OCR/局部 VLM/人工核实的真实来源。两个方向都复用已有任务、存储与模型适配。
3. 尽早从正式入口运行“内置方案发布→一例完整节点→报告”。允许已有合格规则支持中途调试，但不把前置方案 Agent 无限后置；不等所有未来复杂表达式实现后才试跑。

## 1. 用户决定、未决事项和完成边界

| 决定 | 对工程的直接含义 |

取消双读不等于“所有单次 OCR 自动正确”。改变的是**证明和采信路径**，不是取消事实、来源、时间和医学语义的核实。

### 1.2 已决的方案入口选择

用户最新决定：**在目前框架内保留并强化前置方案解构/审核 Agent**。上一版外部方案作者入口的待确认提案不采用为本轮主线；不再追问是否外置，也不要求用户手工整理规则。

产品多 Agent 的职责边界与工程开发采用 Trellis inline 并不矛盾。方案 Agent 可有多个任务模式和不同模型配置；是否使用不同权重、是否并发属于部署选择，不是产品多 Agent 的成立条件。

剩余是工程现场问题：实际方案执行器、源文/Schema/修订/发布链怎样连接；当前哪些路线真实可执行。这些应先由本地 Agent 在已有工作树查清，不作为重新确认产品方向的理由。

### 1.3 三种“完成”分开记录

- **内置前置 + 当前节点闭环可用**：方案在产品内真实解构/核对并共同发布；一例全部当前资料和到期要求经过真实入口，产生有内容的工作底稿，能核原件并更正重算。
- **跨方案路径得到验证**：同一实现用于另一份具有不同实际规则结构的方案，而不是只更换名称或患者编号。
- **全产品交付**：原有后续节点、其他功能和集中验收完成。

第一项完成后应当立即交付可用成果；不能等待第三项才让用户使用，也不能把第一项冒称第三项。

## 2. 内置前置方案 Agent：在现有框架内精修 Harness

### 2.1 最新产品方向与本节的实施边界

**已确认方向：产品是多 Agent 协作的入排审核系统；方案解构与方案审核是产品内置、前置、相对独立的 Agent 流程。用户上传正式 DOCX 和现行修订，不必到其他 AI 手工起草 JSON 再返回。**

上一版“外部作者优先入口”建议不再进入本轮计划。不删除现有导入/导出能力，但也不为此前提案新建公共作者 Schema、外部工具编排或另一套规则发布入口。

本报告中的“方案审核”指入排及相关流程要求的完整性、忠实性和执行一致性核对，不新增整份方案科学性、统计设计或临床开发策略评审平台；发现原方案自相矛盾时提出有出处的澄清，不替作者改方案。

相对独立指：方案任务有自己的输入、状态、上下文、配置和可复用产物；不是独立部署一个服务，也不是另建任务队列。对下游交付已发布的规则修订、节点/证据要求和明确的未决状态，而非自由文本总结。

本节为设计与实施建议。补充包包含应用注册、配置和页读/事实链，但**没有完整的方案执行器、语义生成器及发布实现**。对方案侧已存在能力的判断须区分“本次读到的调用/配置”“历史运行记录”“待本地核实的实现”。不能把下列建议函数名当作已经存在的 API。[S13、P01]

### 2.2 产品多 Agent 与开发多 Agent 必须分开

| 层次 | 本轮选择 | 不代表什么 |
|---|---|---|
| 产品运行时 | 方案理解、资料读取、事实整理、语义核实等不同职责通过来源化产物协作 | 不是每个职责必须加载一套不同权重，也不是所有任务双模型投票 |
| 方案 Agent 内部 | 复用官方条款解构、跨章控制解构；以统一上下文和核对流程协调 | 不先造六个新的常驻 Agent 或自由讨论群 |
| 工程开发时 | 按本地 Trellis Codex inline，由当前所有者集成共享改动 | 不因为产品多 Agent，就越过项目开发派发规则 |
| 本机资源 | 复用当前模型服务及同一资源所有者，按实测能力调度 | 逻辑并行不等于多个大模型同时驻留 |

Ponytail 的简化对象是重复实现、重复推理和无依据抽象，**不是用户已明确需要的前置方案 Agent**。本地 Ponytail 规则同样强调，完成完整请求范围，不能以简化为由省略已要求的功能。[S11]

### 2.3 对外一个方案能力，对内优先复用三个有边界的职责

产品中的方案模块建议保持一个用户入口、一个总体进度和一个发布动作。

| 内部职责 | 首选现有落点 | 只负责的输出 | 不应负责 |
|---|---|---|---|
| 官方规则解构 | 现有 Protocol Deconstructor / deconstruction executor | 官方 IN/EX、父子语义、相应资料要求及节点草稿 | 编造正式 ID、患者判定、独立发布半份规则 |
| 跨章控制解构 | 现有 protocol-control executor / Agent | 合并用药、洗脱、导入、基线/随机前控制及其定义、例外、强度 | 复制一套官方 IN/EX；将建议升级为排除 |
| 方案核对 | 先查既有方案检查/定向修订能力；必要时只补一个语义核对角色 | 原文遗漏、逻辑/时间/证据含义错误、冲突与明确局部修改请求 | 再生成整份规则、按喜好润色、自动改研究方案 |

全文结构化、来源检索、批次装配、身份生成、Schema/引用校验、编译、状态转换与发布由代码完成。不要把这些确定性步骤都包装成模型 Agent。

现有应用 `app/api/v2/app.py` 已注册两类方案执行器，`app/config.py` 已区分 `DECONSTRUCT_*` 与 `PROTOCOL_CONTROL_*`；这支持沿现有两条生产链收敛，不需要再设计一个通用 Agent 注册中心。它只证明入口/配置存在，不证明当前方案能成功运行。[S13]

### 2.4 目标执行链

```text
正式 DOCX / 当前修订 / 已登记解释材料
    ↓
既有结构解析与来源冻结                         [代码；复用]
    ↓
方案全局语境 + 全文来源处置 + 依赖关系          [复用既有 Agent / 规划器]
    ↓
按完整语义单元装配任务包                       [代码；按需补上下文]
    ├─ 官方规则解构                            [现有职责 A]
    └─ 跨章控制解构                            [现有职责 B]
    ↓
结构/来源检查与草稿装配→即时可读预览             [代码；同一候选，不另调总结模型]
    ↓
原文→要求、要求→原文双向核对                    [一个方案核对职责]
    ↓
仅对具体问题做局部取文/修订/复核                [有限循环]
    ↓
原文旁展示明确的待解释事项与规则变化             [既有方案工作台]
    ↓
共同发布 RuleSet / RuleModelRevision / 控制目录  [既有发布事务]
    ↓
下游资料需求、谓词绑定、确定性求值与报告
```

这是职责图，不要求每个框对应一个新类、一个 Job 或一次模型调用。已有步骤可以同时产出全局语境和来源处置；已有执行器可以处理多个完整条款。是否新增对象必须由真实调用链决定。

### 2.5 先核实已经实现的分包、局部恢复和 Schema 修复

本轮不能重新把“实现分包”“实现失败段恢复”列为从零开始：

- 包内配置已存在大父条款分段、输入软预算、有限并发，以及跨章 adaptive batching、输入/输出估算和单元数上限。需要核配置是否被实际规划器消费，而不是重复新增开关。[S13]
- 历史记录显示成功段曾按来源与提示身份复用，缺失段只调用一次；因此局部恢复至少曾有真实路径。[P02]
- 但同一记录也显示局部修订曾把 6 项门禁问题扩大为 26 项，说明“具备修订入口”不等于“修订范围受控”。不得宣称再多修两轮必然改善。[P02]
- 2026-09-16 有约 2221 秒、13 次请求后失败的方案运行；记录指出生成 Schema 可省略而领域必填的字段不一致已经修过。后续还有 `source_ref` 被当作 `source_span_id` 的问题。当前工作应核查修复在所有实际生成/修复/紧凑路径是否一致，不盲目重跑整份长作业。[P03]

**第一项实作交付是短调用链与已存在/未接通清单，不是另一篇全仓审阅。**

### 2.6 全局语境：结构化共享，不用长总结代替原文

方案开始时，复用已有解析结果建立下列最小语境：

- 正式版本、修订关系、当前研究部分/队列；期别与审核节点分开。
- 真实 WorkflowStage、访视名称及其来源；筛选/导入/基线同阶段但不同节点不能只按名称合并。
- 定义、缩略语、命名时间锚点、流程表表头/脚注及相互引用。
- 当前支持的执行形态，以及确实尚不支持的能力；不能根据能力不足删除原要求。

每项必须有原文来源。模型生成的全局语境仍是有来源的解释草稿，**不能因所有工作者共享它就变成事实**。当某条原文与语境冲突，保留冲突并核对原文，不强迫条款迁就总结。

共享对象是持久化产物，不是跨 Agent 的自由文本聊天史；“共享”也不意味着服务免费缓存。每次实际请求中再次发送的文字仍要计入输入成本。

不要把每名受试者的病例或既往筛败结论送给方案 Agent。方案规则不能为当前病例倒推。

### 2.7 全面性：所有来源有处置，不等于所有段落都深度生成规则

保留现有 `ProtocolSectionCoverageManifest`，从完整可支持的 DOCX 结构清单出发。先核当前解析器是否覆盖正文、列表、表格及其脚注、文本框等真实出现的内容；存在未支持结构时标明，不把“正文读取成功”称为全文完整。

建议沿用既有处置类别，表达：官方条款、流程要求、其他控制、定义/补充、阶段/研究范围不适用、非受试者入排任务、待核实。**未被模型返回的单元不得自动归入“非相关”。**

可将相同处置的连续单元用短 ID 列表/范围紧凑表示，由程序展开校验全集；但只有模型确实读取了这些原文，且范围无缺口时才可合并。不得给每段都强制生成几百 token 的解释，也不得仅看标题/关键词就删除整章。

“全面”分开记录：

1. 结构来源清点完整；
2. 所有来源有明确处置；
3. 官方条款、跨章限制、流程及定义的语义覆盖已经核对；
4. 已发布的要求真实进入下游审核。

这四项不能相互代替。100% 单元被标记，并不证明没有遗漏一个条件或误解一个例外。[P01、P04]

### 2.8 任务包的单位是完整语义，不是固定页数或固定条款数量

复用现有父条款规划器和自适应装包，先修改必要的输入装配，不先更换执行器。

一个任务包应当含：

```text
本次任务/来源/草稿版本引用（程序保存）
模型可见的短任务编号和短来源编号
本包拥有的完整条款或控制来源
必须继承的引导语、定义、表头、脚注、例外和时间条件
涉及的最小全局语境
与本包直接有关的既有草稿（只在修订时需要）
当前任务专用 Schema 与明确未决返回方式
```

**拥有写入范围与可读取范围分开。**某条款可引用另章定义，不能因为定义属于另一任务就拒绝读取；同一来源也可支持多项不同要求。读取补充来源后，将真实新增依赖纳入本次冻结输入，不使用全仓任意引用。

仅当完整父条款超出实际预算时才分段。每段保留父限定语和自身来源范围；合并时必须恢复原有逻辑归属，不能默认把各段结果一律 AND 或一律 OR。来源未完整时，先请求缺少的定义/脚注，不拿短上下文生成残缺规则。

采用“少量完整普通规则一包，复杂父规则独立包，过大父规则保语义分段”的策略。具体 token 数从本机回执确定，不把固定 24/48 个单元或 8K/16K 当新的医学规则。

### 2.9 有界取文工具：给 Agent 找上下文的能力，不新建通用工具平台

在现有源文仓储上提供最少的一组能力。以下是职责名称，不是已存在接口：

| 能力 | 输入 | 返回的必要信息 |
|---|---|---|
| 读指定来源组 | 当前方案/范围 + 来源 ID 列表 | 完整原文、章节路径、同一来源版本 |
| 读表格上下文 | 表/行 ID | 表头、相关行、脚注、跨页延续关系 |
| 解析明确引用 | 当前单元 + 原文引用 | 目标来源或歧义/未找到，不自行猜最像章节 |
| 读取有关草稿 | 当前规则 ID 集合及修订 | 受影响对象，不返回整份运行日志 |

宿主尽量预装明确依赖，避免每个定义触发一次单独工具往返。模型发现缺上下文时可返回批量 `needs_context`，由宿主读回后继续本单元。

首版不必等待所有本地模型支持原生 tool calling：已经稳定的 JSON 通道可以返回结构化取文请求，由现有执行器完成同等的有限步骤。真正的函数调用和 JSON 请求是传输差异，不改变临床职责。

不得让 Agent 通过联网医学知识补齐方案没有规定的阈值、洗脱期、证据政策。外部医学解释仅按已登记解释材料的边界使用。

### 2.10 作者输出与执行对象分离：优先修现有 wire，不另造规则语言

模型生成**临床语义草稿**，代码生成正式 ID、哈希、数据库关系和可执行领域对象。

先检查现有官方 compact wire、跨章 wire、SemanticRule/Control 草稿和水合函数。能用已有语义表达式与局部引用表示的，不新建第二套 AST；不同来源族可以保留各自外壳，共享原子和校验函数。

必须统一检查：

- 首次生成、语法修复、局部内容修订、紧凑/普通输出采用同一版本的作者字段要求；
- 动态 Schema 允许的字段/必填项与实际水合和领域构造器一致；
- 不要求模型填写长哈希或凭空生成 `source_span_id`；短别名由程序映射到本次真实来源；
- 程序检查来源摘录在对应原文中，但不把逐字出现当成临床含义正确；
- 能未知的临床字段用明确未知表示，不能通过默认 false/0/空集合补齐；
- “原文没有规定”“本次上下文没找到”“尚未核清”保留差别。

JSON Schema 约束结构，不能单独验证临床语义。结构合法之后仍需要方案核对。[W4]

### 2.11 防止逻辑展开造成输入输出膨胀

检查当前 wire/水合/执行器是否在模型侧强制将嵌套表达式完全展开成 DNF。**目前材料只足以证明系统有 DNF 相关合同，不能证明所有性能问题由此导致。**

数学上，`(A1 OR B1) AND ... AND (Ak OR Bk)` 若完全展开，会有 `2^k` 个析取分支。必要时应由代码保留或转换逻辑，不要求模型反复抄写成指数级输出。

最小改法优先级：

1. 当前领域树已能表示时，让模型保留原嵌套结构，由现有水合器生成身份；
2. 某消费点确需规范化时，仅在该处做确定性转换，并记录实际展开量；
3. 现有表示不足时，明确记录尚未支持，别为了省 token 改原文逻辑；
4. 不在本轮升级成通用逻辑求解平台，也不假设语法树等价就证明自然语言解释正确。

### 2.12 方案核对：原文找遗漏，草稿找误解

核对不是“你觉得这份结果靠谱吗”，也不是再生成一份完整规则并求交。

**方向 A：原文 → 要求。**对来源处置全集逐批核查，特别是已标为非相关、定义/脚注、跨章限制和同一段中的多项要求。核对者先从原文识别本段可能承载的审核要求，再看对应草稿，避免只围绕主解构器已经列出的清单自检。缺失返回具体来源和遗漏内容，不写第二份完整规则模型。

**方向 B：要求 → 原文。**核每个发布候选的对象/条件、极性、AND/OR/例外、数值/单位、时间用途、锚点、取值规则、证据角色和义务强度是否忠实。常规项可按主题批量检查并只返回已核范围及问题；复杂条件再定向深核。

重点深入：否定和多重例外、其他章节改变适用范围、研究者判断、复查采用/次数、频次/半衰期、流程表脚注、同一期别中的不同审核节点。**风险提示决定深入程度，不决定某项规则能否完全跳过检查。**

核对角色与生成角色使用分开的任务上下文。同模型可承担不同角色，但只能称“职责分离核对”，不能称两个独立模型证明。无需为了角色不同强制装卸另一套权重。

方案是低频、纯文字为主的工作，可以有一次完整来源覆盖核对；这不等于恢复受试者全页、双 VLM、双完整输出。总成本仍需记录，不承诺增加核对天然提速。

### 2.13 核对返回具体发现，不返回分数或长篇评价

每个问题至少具有：`受影响规则/来源`、`问题维度`、`原文依据`、`当前草稿位置`、`具体差异`、`建议处理`。结构化问题可定位 JSON Pointer，但不让模型自己修改任意全局路径。

只接受这些有业务价值的发现：遗漏、错误对象/极性/逻辑、错误时间或来源政策、跨章矛盾、节点错位、未支持能力和确实缺少上下文。风格偏好、措辞润色、无原文依据的“更谨慎”建议不触发重生成。

核对意见也可能错误。主流程必须回源检查；不能把 Critic 自报高置信度、给出红色标签或“建议从严”直接变成新的方案要求。真假争议保留有出处的问题，由用户解决实质解释，而不是第三模型投票裁定。

### 2.14 局部修订：一个问题不能使整份草稿重新生成

每次修订只传：受影响的完整规则对象、必要来源、具体问题和本轮允许改动范围。优先返回**该完整小对象的新版本**，而不是让模型生成全份 JSON 或脆弱的字符级差异补丁。

代码在接收后：核基准对象版本 → 校验允许改动对象 → 检查新对象和全部直接依赖 → 保留未改变兄弟对象 → 记录新修订与问题处置。若修订改变全局定义/共享时间锚点，必须将其所有受影响依赖重新装包，不能以“局部修订”为由漏传播。

默认每个受影响语义单元最多两轮内容修订，**同一问题签名、同一输入、没有新增原文或改变处理方式时提前停止**。这个上限沿用有限修订思想，不是要求必跑两轮。传输恢复、上下文补取与语义修订分别记录，受同一工作预算约束，不能靠新建 Job 重置循环次数。

最终仍有问题时保存已有合法草稿，展示具体未决点；不抛弃所有已完成条款从头跑。若旧执行器只能整份候选回退，先补本次真实生产者/检查点/水合一致的局部提交边界，不仅修改错误提示。

### 2.15 三类“未完成”不能混同

| 情况 | 应如何处理 | 不得怎样处理 |
|---|---|---|
| 缺上下文或原文解释有歧义 | 自动补取有关来源；仍不清楚才集中问用户，保持受影响项未决 | 按默认值编译；多数投票；问用户重写全部规则 |
| 原文含义明确，但执行器尚不支持 | 保留有源的人工审核要求及能力说明；通过同一要求体系显式消费 | 删项；恒真/恒假占位；当成受试者缺资料 |
| JSON/引用/水合不一致等工程故障 | 定位并修代码或局部格式，不改变医学原文 | 把工程错误包装为“请研究者判断” |

原文或来源尚不闭合的草稿不因“人工模式”标签变成已批准完整规则。现有发布合同尚不能容纳已定义但人工执行的要求时，只做同一目录内必要的状态/投影扩展；不能绕过全局发布保护。

全文分析可以完成并留有少量方案澄清，**不等于可完整发布执行**。界面分别显示处理状态、规则完整性和可执行范围。

### 2.16 低频预处理与高频病例审核通过稳定产物隔离

前置方案 Agent 输出继续落在现有 `RuleSet`、`RuleModelRevision`、`WorkflowStage`、`EvidenceRequirement`、`PublishedProtocolControlCatalog`/实际同类目录中。正式状态和官方/跨章关系由现有发布事务管理。[P04]

下游按用途派生三种视图，不新增三套权威数据库：

1. **完整执行视图**：完整逻辑/例外/时间和来源政策，供求值与冻结；
2. **资料需求视图**：本节点需要什么事实、字段、文件或研究者记录，供整理和补证；
3. **局部核实视图**：某个待核命题、有关定义和允许来源，供语义核实。

视觉转录仍不携整份 ClausePack，也不接收期望入组阈值。结构化字段提取可接收中性的字段说明，但不得用目标阈值诱导读数。

同一方案修订服务多个受试者，病例上传不重解构方案。方案更新只触发有关规则与绑定重算，不重新 OCR 未变化原件。病例意外结果只能触发规则核查，不能自动反改规则。

### 2.17 资源与预算：按职责配置，不为多个角色复制整个运行环境

- 方案任务使用现有独立 `DECONSTRUCT_*` / `PROTOCOL_CONTROL_*` 配置，不继承受试者双主读身份。
- 先选择用户已有、当前后端可执行的本地模型完成纯文字结构任务；不要暗中恢复收费远端、已耗尽额度路线或个人 Agent 会话。需要新远端路线时另行明确确认。
- 同一套权重可以承担生成与核对；角色提示、任务输入和回执分别记录，权重装载可在已有所有者允许范围内复用。
- 只有资源所有者确认同服务并发受支持且本机实测有收益时才增加并发；初始可串行执行各批，避免多大模型共驻留。不要重复实现已经存在的装卸保护。
- 全文处置/简单规则用短结构化输出；复杂逻辑保留必要推理预算；不把所有任务都设最高思考或 65K 最低输出，也不以统一低额度制造截断。
- 在请求前同时核实际输入量、Schema、工具内容、输出预算和后端物理限制。没有真实 tokenizer 时标记估算，不把字符数称为 token 数。

分开计量：`方案首次解构`、`方案局部修订`、`已发布规则下单例审核`。30 分钟目标来自用户的单例审核期望，不能擅自变成整份方案硬上限；第一次端到端总等待应另外显示，不能隐藏方案耗时。

### 2.18 缓存与修订：复用真实未变化工作，不续接不兼容旧作业

优先复用已有 ArtifactStore、检查点和来源身份。一个语义任务的复用依据包括：本单元原文、确实读取的依赖内容、研究范围、角色/提示、Schema、模型配置以及实际输入版本。

- 仅显示名称变化不作废全部来源解析；
- 一个条款局部修订不重做无依赖的其他条款；
- 共享定义改变时，通过实际依赖反向传播；
- 原方案修改后，旧提取只有在来源对应明确验证并新建引用时才可复用，不把旧来源哈希改成新版本；
- 每个原子语义任务不拼接不同模型的半段输出；不同已定义职责的完整产物可以按共同来源/发布合同汇合；
- 当前已有“整候选同模型”历史政策不得无提示放宽，若本次改变合并粒度，须更新相应合同与真实来源校验，旧记录仍按旧身份读取。

先核实际运行是否存在重复工作再优化。不要新增一套缓存服务器、全局依赖图数据库或“永久 Agent 记忆”服务。

### 2.19 用户交互：只集中问真正需要解释的内容

用户看到的应该是：读取结构 → 有源候选逐步可读 → 核对原文 → 修订问题 → 可发布/有待解释；而不是二十几个后台模型节点和内部版本串。候选预览与正式发布明确区分；不是等所有内部证明完成后才给用户看到第一项结果，也不能把草稿数量当临床完成率。

每个方案问题卡包含：原文位置、当前解释、实质差异、影响节点/条件、需要确认的一个问题。同一全局歧义影响多条要求时合并成一个问题，保留全部影响关系。

默认不要求用户逐条重新填写 JSON、不逐项确认明显正确的每个检验阈值，也不要求为“模型调用失败”作医学签字。方案级正常发布确认和少量真正歧义可继续沿用既有工作台。

没有疑问时自动推进至可查看的完整候选；正式发布沿当前明确用户动作与版本规则执行。用户修改后只处理受影响范围。

### 2.20 本地 Agent 实施前要读的最小方案调用链

以下由已见应用 imports/config 或历史设计定位；完整实现未包含于本次补充包，不声称已逐行审过。由本地 Agent 在指定工作树读取实际文件，不要求用户再次收集整仓：

| 入口/范围 | 本次可确认的事实 | 实作前必须查清 |
|---|---|---|
| `app/api/v2/protocols.py`、`protocol_control.py` | 已见应用注册引用 | 上传、生成、恢复、发布和工作台各调用哪个服务 |
| `app/services/protocol_workbench_service.py` | 应用引用服务及 Job 类型 | 是否重复创建两条任务，发布如何等待共同目录 |
| `app/services/protocol_deconstruction_executor.py` | 应用注册创建函数 | 实际拆包、消息装配、局部修订与 checkpoints |
| `app/services/protocol_control_executor.py`、`protocol_control_job_service.py` | 应用注册与服务引用 | adaptive 配置实际消费、覆盖/批次/汇合 |
| `app/agents/protocol_semantic_model_router.py`、`protocol_semantic_route_preflight.py` | 应用及配置直接引用 | 角色配置与本地服务能力、无意远端依赖 |
| 上述 executor 实际引用的 prompt/wire/semantic builder | 补充包未提供完整定义 | 原生/紧凑/修复字段一致、短来源映射、输出膨胀 |
| 现有语义草稿、水合、规则合同与发布服务 | 设计和历史记录明确存在 | 可复用作者层、严格完整性、控制共同发布 |
| 对应前端方案工作台及 HTTP 客户端 | 设计已有，代码不在本包 | 原文/候选/未决/继续处理/发布真实可操作 |

只读跟踪可从 `rg` 搜上表中的实际调用者开始；不要在未读完整受影响函数和调用者前按旧行号写补丁。补充包中没有文件，不等于本地仓库没有功能。


### 2.21 快速有源草稿与可发布规则：两个里程碑，同一条加工链

**外部示例真正值得吸收的不是其未知后台，而是用户很早就看到了可理解的结果。**我们的首个可读产物应来自当前结构化草稿，不要求先完成全部来源核对、复杂表达式编译和所有发布依赖才显示。

最小改动：在现有草稿/checkpoint成功保存后增加或复用只读投影，展示原条款/主题、候选条件、来源、适用部分、待核状态和具体未决。原样复用该草稿进入核对/装配/发布，不能另生成一个自由Markdown版本再让另一模型把Markdown翻回JSON。

- 第一批必须包含完整语义，不为了首屏速度只输出标题或半句条件。
- 未闭合JSON、输入/输出截断、缺原文引用不能标成合法候选；保留已完成的其他批和真实未读范围。
- 预览可逐批出现，不意味着完整方案已经处理或允许病例据此作明确结论。
- 对同一来源的摘要/正文重复，已证明相同的内容可复用语义候选并保留两个来源；文本相近不自动等价，期别/版本/脚注差异须核。
- 不为预览新增第二个RuleSet权威、发布入口、总任务或Agent服务。

“三分钟有源草稿”可作为本机优化的学习方向；目前没有同配置实测，不作为SLA。最终仍要缩短`可发布`时间，不能只改善动画或隐藏后台等待。[CMP]

### 2.22 一份语义，多种显示：减少输出，也消除互相矛盾

复用现有作者wire和规则草稿，以一份规范语义保存对象、条件、例外、时间用途、适用性、来源及必要证据。不要要求模型分别自由生成“判断点”“通过”“不通过”三份等价文字。

**程序可派生：**简洁规则卡、临床状态说明、原文对照、洗脱/检查速查、节点资料清单。复杂逻辑难以用短句忠实展示时，显示结构化条件和原文，不强行造一段更漂亮的补集描述。

例如排除触发是A或B，不能因另一个分支阴性就把已经成立的A抵消。没有证据不是假；不适用不是已经满足；未到期不是不满足。现有状态/求值器已经有相应概念，优先修投影和作者输出，不新增逻辑语言。

原文例外与普通条件分别保存；完整检测集下看似等价的简写，不自动在缺证或冲突场景下当作等价。标题、速查表不能引入正文没有的时间或适用范围。[CMP F03/F07/F08/F10/F11]

### 2.23 方案核对增加六项高收益约束，不增加六个Agent

沿第2.12节既有双向核对一次合并以下维度：

| 维度 | 必须核什么 | 最小工程落点 |
|---|---|---|
| 原身份 | 原编号、研究部分、父子关系和源内容相符，不能只比总条数 | 既有Rule/RuleComponent与来源树；模型只写本任务拥有的对象 |
| 时间 | 随机/筛选/ICF/检查/给药等明确锚；临床回溯与报告有效期不同 | 原子时间与资料来源政策，拒绝全局静默覆盖 |
| 逻辑及未知 | OR/AND、否定、例外的作用范围；缺证不当阴性 | 现有表达式与缺口计算；语义错误回源修草稿 |
| 判断归属 | 病情稳定不等于剂量稳定；研究者要求不扩散至所有兄弟项 | 既有predicate/requirement关系 |
| 测量与聚合 | 绝对数/比例、AST或ALT/AST除ALT、天/时点、总分/单项均值不同 | 作者值/单位/取值规则及现有计算输入 |
| 依赖效力 | 引用表格是否真支持换算、是否缺中心实验室/有效期/复测规则 | 既有Source/EvidenceRequirement/Control及有界取文 |

核对先尊重真实来源。候选中的“最多缺失1个评分”在SAR日程脚注有依据，不可因主条款没有相同句子就删掉；附录的编辑残留或重叠区间属于源问题，不是直接修候选数字。[CMP]

廉价数字、比较符和锚词清点可用于提示核对者关注，但不是自然语言含义的自动证明。不能为此先建一个通用NLP形式化检查平台。格式/映射的确定性错误由宿主修，真正语义差异做有限内容修订；无发现时允许返回无发现，不要求Critic制造问题。

### 2.24 跨章依赖优先表：先完成现有源文要求，不穷举未来需求

本次真实方案提供了可用于检验通用能力的依赖类别：检测方法与机构、历史结果有效期、操作前限制、实际背景用药、特定复测/复筛、评分时点/聚合/缺失、育龄及避孕定义。具体事实在比较附件C01–C11和Q索引。[PC01、CMP]

实现时由当前方案数据驱动这些要求，不把SAR的中心实验室、7天、3天、药名或阈值当通用常量。官方条款、附加要求、推荐、许可与例外保留不同角色；“要求做过检查”不是“检查结果达标”，反之亦然。

实际原文中发现的三个问题值得用来核对本系统的行为：附录9分类表不是唯一精确剂量换算；FSH段存在可选阈值编辑语；INCS/吸入性表述须与允许ICS的段落对照。应形成少量源绑定澄清，不自行改正确答案，不扩展成审查整份方案科学性的产品。

对源歧义与明确但暂未自动实现的要求分开处理；已有支持的清楚条款要继续完成并可预览。整份当前规则的发布继续遵守来源和要求全集，不以草稿预览绕过。病例审核范围不得偷偷缩成只有容易算的项目。

### 2.25 计量和实际价值：首次可读、可发布及人工返工都要看

复用Job/Checkpoint记录以下事件时间，不另建监控平台：

| 事件 | 定义 |
|---|---|
| `source_ready` | 本次输入完成实际源结构清点 |
| `first_source_linked_draft` | 首个完整语义候选已保存、能显示条件与真实出处；不是第一token |
| `draft_complete` | 当前要求范围的候选全部有处置，仍可能有歧义或待核 |
| `source_review_complete` | 本次约定范围已核查，问题及未决如实保存 |
| `ready_to_publish` | 既有完整性与临床语义问题处理满足发布条件 |
| `published` | 明确发布动作完成，下游实际读取同一修订 |

事件名称为逻辑计量建议，先映射到已有事件，不强制新增相同名称的数据库枚举。人工解释等待单独列出；无原始回执不能把时间补为0。另记模型调用、重试和主要输入/输出量；比较同等完成定义下的总时间与人工改动，不只比较预览速度。

对方“3分钟”没有完整回执，不能推断其只读摘要、使用云模型、跳过核对或命中缓存。我们自己的冗余工程也不能因为对方发现了错误而被豁免。先削减已证实的重复生成/工程字段/无用重试，再决定是否增加并发或换模型。

## 4. 目标架构：保留原图摄入，替换读取来源这一段

### 4.1 推荐主线

```text
前置：内置方案 Agent → 已共同发布的完整规则/资料要求 【见第2节】

正式资料上传 / 完整资料版本 / 原始页图准备          【复用】
    ↓
新读取作业：原生文字核查或 OCR 主读取               【替换读法】
    ↓
报告/段落/必要区域识别 + 结构与关键字段风险
    ↓
只对有理由的区域：一个本地 VLM 或人工核对           【有限升级】
    ↓
来源可回放的读取清单 + 可用字段 + 明确未决项         【一个边界对象】
    ↓
现有事实候选 / 事实更正 / 门禁 / 事务发布             【适配来源】
    ↓
累计 Profile / 明确谓词绑定 / 现有确定性求值         【复用，修真实阻塞】
    ↓
现有工作台 / 原件 / 行动 / 冻结报告 / 新审核          【贯通】
```

完整方案规则留在规则层。视觉读取不携阈值和预期判定；之后按有关条款组织证据。方案 Agent 与资料/事实/审核 Agent 通过明确版本的产物交接，不互传长自由讨论记录。报告投影仍是代码，不为多 Agent 的数量新增报告模型。

### 4.2 为什么不先恢复旧“上传阶段强制 OCR”

新摄入已将“资料可用的原图版本”与 OCR 成功分开。立即将其改回 OCR 必须成功才能激活，会重新引入任一不可读页阻塞资料准备的问题，并触动基础修订、继承、重新识别和批量上传的多个消费者。

**优先保留 `original-page-images/v1` 的来源语义，将 OCR 作为已准备资料的读取工作。**历史文字型处理修订仍可读取；新读取结果引用冻结原图与资料版本，不回写旧清单。

这不是新建第二套摄入链。只有本地源码证明现有重处理入口已能以更少改动产生同样合法结果时，才选用该入口；必须在同一真实调用链上说明差异，不能把“恢复一个布尔值”当作证据。

### 4.3 只新增必要的数据边界，不先建平台

逻辑上需要一个 `ReadingManifest`（名称为建议，先查代码中的等价对象）：

- 读取策略版本、父资料版本/页图清单、实际来源引用；
- 已处理的页/区域与未完成原因；
- 原始读取结果、局部视觉核对与人工修订的引用；
- 哪些字段可供事实整理，哪些字段仍不确定；
- 本次生成的来源定位和采信依据。

优先以现有 ArtifactStore + Job 检查点保存不可变内容，在规范化运行载荷中冻结其引用；需要查询的少数索引复用既有存储模式。**不要预先为每个维度建一张表，也不要创建全局“证据认证平台”。**

原始转录、采信状态、临床事实不是同一对象，但可在一个有清晰字段的读取清单中表达。只有真实查询/引用约束证明需要独立实体时再拆。

### 4.4 同一公共事实体系，多个真实来源种类

来源采用明确的判别联合，概念如下：

```text
existing_legacy_dual_read
native_text_read
ocr_read
local_visual_read
human_source_confirmation
```

这不是声明旧枚举已经支持上述名字。实现者需检查来源合同、locator 验证及存储枚举的实际限制后做最小扩展。

新记录必须说明“来源是什么、读了什么、为什么字段可用”；不能将单 OCR 同时写成 A/B，也不能将人工核对伪装成模型返回。

**临床来源数量与模型读取次数分开。**同一张报告被 OCR 和 VLM 读两次，仍是一份临床来源；相同报告重打印也不自动等于第二次检查。

### 4.5 新旧兼容方式

- 旧双读作业和结果按原版本回看，不原地更换 prompt/规则/哈希。
- 新建处理使用一个明确的新策略版本；旧 `r3_page_review` 不再是新单主路径的必经依赖。
- 新读取作业复用同一 JobRunner 注册、事务及恢复机制；不同 job type/strategy 不等于新增队列。
- 不通过 `model_construct`、伪造空覆盖、假 Gate ACCEPTED 或补一份虚构模型记录绕开验证。
- 来源适配层处理差异；共同事实发布、Profile 和求值继续只消费有来源的领域对象。
- 原图版本不变时，读取修订在运行输入范围中冻结；不要一开始就扩展全部 FactAuthority 身份字段。确需新增身份时，限定到无法由现有运行范围表达的部分。

### 4.6 固定步骤的 JobRunner 也能实现选择性核对

不要为了“先 OCR 才知道哪些区域需要 VLM”重写整个调度框架。允许 Agent 在受限范围请求补充工具/上下文；分支、版本、完成与发布仍由既有持久任务管理。

优先使用现有任务能力：第一段完成读取与风险清单；第二段从冻结清单合并相同报告/区域的核对请求，由已有父工作流幂等创建核对作业；完成后再进入事实发布/求值。两段仍使用同一 JobRunner、队列和产物存储。

如果现有 Runner 已支持动态步骤，直接复用；不支持时采用顺序作业衔接，不新建调度器。状态中分别显示“常规读取结束”“局部核对结束”“本次工作底稿已生成”，不能用第一个状态充当最后一个。

## 5. 资料读取：按这批真实材料确定首轮必须完成的能力

### 5.1 最小能力集，不等于“只支持一个固定模板”

| 真实材料中的形态 | 首轮必须正确处理的事情 | 不应展开的工程 |
|---|---|---|
| 同页上下两份报告、每份左右分栏 | 分清报告、表头、行和结果；报告头只向明确所属行共享 | 不按某一病例固定“上半页血常规、下半页尿常规” |
| 检验结果旁另有解释/等级表 | 区分患者结果与通用解释、参考范围 | 不把解释表中的所有数字生成患者事实 |
| 90°横放报告、心电报告 | 自动方向候选与必要的人工更正；读取文字和批注 | 不以长宽比推断正确阅读方向；不分析波形 |
| 手写 CS/NCS、QTc 便签 | 读取内容、限定对象、保留无法确认的指向 | 不识别人名签字作为首轮前置；不由颜色决定便签性质 |
| 跨页病历断句、药名被页边界切开 | 同一逻辑文档保留连续上下文，并保存多段来源 | 不任意拼接不同文件或不同段落来组成药名 |
| 实际评分填在印刷评分说明旁 | 读取已记录的实际分项/总分和时间 | 不把 0–3 分说明当实际得分，不替研究者重评分 |
| 肺功能预测值、实测值、百分比、多次动作 | 保留列的角色；方案要求哪一项才使用哪一项 | 不选看起来最有利的列，不把 %预测值当绝对值 |
| 病历明确提及尚未返回的检查 | 形成被引用但未提供/未返回的具体事项 | 不把开了医嘱或抽过血当结果已存在 |
| 姓名被遮盖、人口学留空 | 接受用户指定的资料归档关系；所缺临床属性逐项处理 | 不为恢复姓名反复 OCR，不把遮盖直接解释为不符合入排 |

31001 和 31010 是这次已查看的工程例证，不再被称为完全未见的盲测资料。它们也不能证明跨方案泛化。[S00]

### 5.2 建议的第一版读取顺序

```text
全部页面清点
  → 方向及可读性准备
  → 一个主 OCR / 合格原生文本解析
  → 保存原始输出和页/报告级位置
  → 从文字与可用表格结构整理候选事实
  → 针对结构问题和将用于明确判断的关键字段安排局部核对
  → 更新可用字段与未决项
  → 统一发布事实、绑定规则和生成报告
```

不要先为每页运行一个通用大 VLM 来“判断是否需要 VLM”。已有 OCR 文字、版面元数据、图像方向模块和确定性检查优先；无法确定的页保持明确处理状态。

**所有页要进入范围，不代表所有页都需要高成本识别。**没有找到关键词不能自动证明该页无关；含手写、未识别正文或结构异常的页面不能被静默跳过。

### 5.3 OCR 先使用已有接口，不先启动完整 OCR 平台替换

当前 text-only 接口可以作为第一条正式来源：保存真实文字、实际输入图像和来源精度。先让它合法进入新读取清单与事实链，别等“完美的单元格坐标”才开始集成。

对返回 HTML/Markdown 表格或清晰行文本，优先复用已有解析方式保留行/列关系；解析不到结构时明确降级为文字候选。**没有物理坐标仍可提供页级或文字范围来源，但不能将其显示为已核实的精确红框。**

如果现有 GLM/Paddle 完整流水线已在本机可直接调用，且能少改代码返回版面结构，应使用其现成能力。GLM-OCR 官方自托管流程包含布局与区域识别；Paddle 的 Apple 部署也区分完整解析流程和单独 VLM 服务。[W1、W2]

但不要因外部文档存在这些能力，就认定你当前的 `message.content` 接口已经支持；也不要先迁移整个平台。做一次短的能力核对：**现有安装、实际入口、输出对象、在这类页面上的可用性**。只能返回文字就如实用文字，并给关键区域提供 VLM/人工路径。

### 5.4 方向、裁切与图像细节

**方向处理。**复用现有 EXIF 与 `ReadingView`。扫描 PDF 的内容方向需额外判向；优先检查本地已有轻量方向模型。没有可靠判向时，将该页作为待更正项，用户可在查看器点击“按此方向重新识别”，不需要填写角度 JSON 或先处理原文件。

**显示图和识别图分工。**保留当前显示页和历史渲染身份；密集区域确有需要时，从原始 PDF 的可见页面组合重新渲染相应区域。不要一律全页改 300 DPI，也不要从 PDF 中盲取最大内嵌图：页面可能还包含覆盖、文字或其他组成部分，内嵌底图不一定等于最终可见原件。

**裁切粒度。**优先一份报告、完整表格行组或便签加所指区域；不要只裁一个数字使项目和单位丢失。没有可信报告边界时，保留整页上下文，不能固定切半后假设各半独立。

**定位链。**保存源文件页、显示图、阅读方向、裁切矩形、实际模型输入尺寸和变换关系。原有直角逆变换可以复用；新增裁切/缩放要明确加入变换。矩形落在图内只证明几何合法，不证明包含了所声称的文字。

**OCR 缓存身份。**现有 OCR 层使用实际输入图像哈希。旋转、裁切或分辨率变化后的输入不得仍冒用原页图哈希；若旧 OCRPage 合同仅允许原页图，应在新读取产物中记录派生输入，不能为复用接口伪造旧关联。[S04、S05]

### 5.5 检验单：报告头、检验行、批注分开

至少保留如下信息，能由报告头共享的内容只保存一次：

```text
报告：来源区域、机构/报告标识（可空）、标本、采样时间、报告时间、归档受试者
  检验行：原始项目名、结果、比较符号、单位、参考范围、异常标记、列角色
  批注：原始内容、位置、明确所指对象或指向未知、判断类别、日期（可空）
```

关键要求：

- 结果与参考范围分别保存；参考范围中的上下限不是患者结果。
- 绝对计数与百分比是不同属性；同项目的不同测量也不能只按名称合并。
- `<`、`>`、“未检出”、数值加阴阳性、单位和检测方法不在清洗中丢失。截断/限值结果不能一律按边界数值当作精确测量。
- 采样、接收和报告日期分别有角色；是否满足窗口由已发布规则决定。
- 页眉日期只向其实际所属报告共享；同页另一个报告不能默认继承。
- 有初查、复查或同报告续页时保留各自关系；不能按 PDF 页序或上传时间推断临床先后。
- 对同一报告已有手写 QTc 和打印 QTc，不先假定两者采用相同校正方法，也不因数字不同直接报临床来源冲突。

数值范围和医学常识只用于提示检查，不可自动把异常值修成“更合理的值”。

### 5.6 手写批注：真实性已确认，所指范围仍需核实

用户已确认这类便签来自研究者，不需要每个病例再次询问“是不是测试标注”。但是：

**“读取到 NCS”不等于“所有检验项目都 NCS”；“读取到 CS 与研究疾病相关”不等于“触发所有有临床意义异常的排除条款”。**

处理时分别保留：文字、对象、方向/引线或相邻上下文、可见日期，以及是否能明确对应某项要求。所指范围不明时，只留下对应的待核问题，不抹掉清楚的客观检验值。

不要求读取无法辨认的个人签名作为每项事实发布前置；方案确实要求特定判断，而材料不足以建立该判断时，才在相应条款保留未决。

### 5.7 病历：利用已有逻辑文档分组，修复跨页来源而非重新建解析器

现有规范化已支持连续页组成逻辑文档，不能误写成“目前只会单页抽取”。问题是页读、来源验证和候选生成之间的连续语义还没有完全衔接。[S08]

首版优先对同一份可放入预算的病历文字做一次文档级整理；长文档再按完整段落/章节切组。表格报告不和叙述病历无区分地合并。

跨页处理步骤：

1. 保留每页原文和原偏移，不直接删原始页眉页脚。
2. 在模型阅读视图中标出页边界；确认为重复页眉/页脚的内容可以作为版式上下文移出连续正文，但须保留可回原件关系。
3. 对页尾—次页页首的延续，建立一个小的连续来源说明，列出各段来源及次序。缺页、不同文档、存在实质插入或关系不明时，不自动连为一句。
4. 候选事实引用这些真实片段；引文校验允许沿**已证明的连续关系**还原断词，不再要求一个跨页药名必须完整出现在某一个 locator 内。
5. 不能全局删除 `␟` 后允许任意多个 locator 拼词。旧分隔保护有其正确用途，只对已建立的连续段落提供分支。
6. 若为长文档添加前后页少量只读上下文，不把上下文页再次计为当前调用拥有的输出页；复用现有唯一页覆盖要求，避免重复事实。

“否认”跨页时，必须保留其实际限定的对象和时间。模型无法确定范围就返回未知，不能补成一串预期排除项的阴性答案。

### 5.8 常规遮盖：资料归档与临床人口学证据分开

用户在某项目、受试者、节点中上传资料，是**资料归档声明**。系统可据此整理这批材料，不必先从遮盖处恢复姓名。

但归档声明不证明被遮盖的年龄、性别、出生日期或采样时点。具体做法：

- 不为姓名遮盖产生重复 OCR、全例失败或“姓名不符合”提示。
- 可读取的受试者编号/节点标识作为额外对应证据；没有这些字段时明确显示“按用户归档”，不宣称图内身份已核实。
- 明确出现其他受试者编号或相互矛盾的来源时，才提示具体归属问题。
- 年龄等确实影响某条标准而所有可用材料均未提供时，仅该条保留缺证；不能从病历年代、外观、其他病例或登记默认值推断。
- 产品已有人工录入人口学功能可复用，但录入值须标明来源方式；是否足以支持规则取决于方案的证据要求，不等同于原件核实值。

## 6. 从“读到”到“可用”：用一个清楚的采信边界替代全量双读

### 6.1 不新增庞大的置信度平台

首版使用可解释的规则与明确来源状态，不建立训练、校准、模型投票和新评分服务。

读取清单至少区分下列维度；它们可以是一个对象的字段，不必拆成多个服务：

| 维度 | 要保存什么 | 不允许的替代 |
|---|---|---|
| 原文 | 原始字符串、字段、单位/日期、来源 | 用模型规范化值覆盖原文 |
| 结构 | 属于哪份报告/哪行/哪列或哪段 | 仅凭字段同名猜配 |
| 核实 | 原生解析、OCR 候选、局部视觉、人工确认及其实际记录 | `confidence=0.99` 或“两个模型都这么说”作为唯一证明 |
| 可用范围 | 哪些属性已可用，哪些仍未知 | 药名正确便默认剂量/频次/起止正确 |
| 问题 | 不可读、结构不明、来源冲突、缺证、系统未处理等 | 全部映射成“病历未记录” |

当前 OCR 无可用置信度就保留未知；不能将非空字符串或格式通过换成虚构分数。[S04]

### 6.2 最小采信政策建议

**原生明确字段。**确认为可靠数字原生文字、对象与结构明确、相关校验通过时，可由已配置政策进入可用事实；隐藏 OCR 文字层不能仅因可复制就按原生来源采信。

**普通打印文字。**主 OCR 形成来源绑定候选；结构与语义检查通过后可用于资料整理。模型提取引用必须能对应原文，不能自行补事实。

**影响明确判断的扫描关键字段。**数值/比较符、阴阳性、否定词、事件/采样日期、关键剂量等，在当前来源没有可靠结构证明或存在风险时，安排报告/区域级视觉核对或人工确认。初次上线应偏向核对这些决定性字段，不能只看乱码、是否正常或是否接近阈值。

**研究者判断与疑难手写。**局部 VLM 读取并核对所指对象；不清楚时转人工。它们不再要求两套完整主读，但仍必须有直接可见的实际依据。

**人工有据确认。**是正式的可用路径，不需要再补两次模型同意。人工确认不能替研究者新增其未写下的意见，也不能替原方案设定未规定的规则。

具体哪些打印字段允许单次 OCR 政策采用，应在首个真实闭环的结果中列明，而不是由模型自行宣布。取消双读已获批准；对新方式的质量结论仍须由实际结果支持。

### 6.3 核对按区域批量完成，不变成字段数量倍增的模型链

同一报告的多个关键字段共享一个局部视觉任务。输入是完整行组、表头和必要上下文；首次独立核对不提供 OCR 候选值或“达到何值可入组”的目标。

第一次核对输出与 OCR 不一致时：

- 先定位是否是行列/项目关联错误；结构性问题应核整份相关表，不连续发几十个数字裁片。
- 明确看清原件后可更正候选，但保存原候选与修订依据。
- 仍不清楚则转人工，不能再调用第三个模型来强选赢家。

可执行的默认停止规则：**一次常规读取、一次有针对性的核对；只有出现新的图像处理/方向/来源信息，才允许再读受影响区域。**用户后续补原件属于新证据，不算无进展重试。

传输失败可按现有有限重试恢复；结构失败、内容不清楚、资料缺失分别计数，不能在不同层反复领取新的内容重试额度。

### 6.4 四种失败必须有不同处理

| 情况 | 处理 | 是否影响无关事实 |
|---|---|---|
| 某行字符/批注读不清 | 保留该区域，发内部核对任务 | 不自动使整份报告所有值无效 |
| 该报告行列/来源归属不清 | 暂缓采用受影响的报告字段，核结构 | 影响这份报告，不应蔓延至别的文件 |
| 检查/判断材料确实缺少 | 依据当前已读范围和方案生成具体补证项 | 只影响相关要求 |
| 来源标识/哈希/引用自相矛盾，或程序异常 | 明确系统错误，禁止使用受损对象；保留已完成结果 | 不能把损坏当成“没有异常”；依赖范围内停止 |

一个页面未完成读取，不能由其他页面成功覆盖成“全资料已读完”；但可生成**明确标识部分未完成**的工作底稿，展示其他已有证据及每项受影响要求。

### 6.5 事实发布接线：改一处来源分派，贯通所有必要消费者

本地 Agent 按下列顺序检查和改动，名称以实际代码为准：

1. **读取产物落盘。**保存 `ReadingManifest` 及原始请求/结果引用；每个可用字段能回到对应页/区域和核对依据。
2. **规范化输入选择。**在 `FactNormalizationCommandService` / `fact_normalization_source_adapter` 引入明确的读取来源选择。旧双读与新读取分别验证，不能仅把 `require_page_review` 从 True 改为 False。
3. **输入合同与定位。**新来源能够被 `EvidenceNormalizerInput` 和 locator 表达。优先扩展必要的可选判别字段；旧对象序列化保持原样，不能让旧结果自动获得新核实身份。
4. **提示与修复提示。**`_model_input_payload`、`verified_evidence_prompt` 的正文和修复路径同时按来源类型投影；新路径不再写“仅双读才可用”，旧路径仍保留其原约束。
5. **实际候选验证。**原文、数值、日期、极性和对象可回源；新增来源分支验证真实读取/确认记录，不虚构 `VisualFactSource.readings` 两项。
6. **事务发布。**复用 `FactPublicationService.publish` 及已有候选接受、引用完整性、事实/事件/暴露/冲突与来源继承机制。
7. **读取与重建。**运行冻结输入、恢复、历史加载、Profile、规则绑定和报告均能解析新来源；不能只完成首次发布而无法打开历史。

先用一份真实资料贯通上述完整链，再扩大批量。不能单独交付“新合同已经写好，消费者以后再接”。[S06—S09]

### 6.6 不要求先完成“无 LLM 的全部临床事实映射”

检验行已经结构化时，数值和单位规范化可以直接由代码做；但临床事实类型、事件和用药映射应优先复用现有 normalizer 的成熟能力，缩小其输入和职责，而不是先另写一个完整医学映射引擎。

之后若实测证明某类确定性检验事实仍被重复模型生成，可增加窄的快捷路径。快捷路径只处理其明确能表达的项目，不用大类别 alias 把无关疾病、检查或例外关联起来。

### 6.7 后续语义核实收敛：保留维度，减少调用

现有 runtime 同时装配多类双路核实任务；必须跟踪当前节点实际走到的调用链，列出每个任务“输入了什么、解决哪一种剩余不确定性”。[S02]

处理优先级：

- 原始数值、单位、日期明确，谓词对象已经绑定：进入确定性运算，不再由大模型重复判断阈值真假。
- 同一原文与同一条件的对象、极性、时间角色、来源适用性，可以在一次有界语义核对中分字段返回；不因逻辑上有五个维度就发五次请求。
- 同一事实支持多个合法谓词时复用读取与来源核对；每个谓词仍保留自己的语义对应与用途。
- 复杂复查/频次功能已有实现就使用；实际未支持的规则保留原文并转人工，不为了消灭所有 UNKNOWN 继续新增抽象。
- 不把双读取消等同于删除“来源是否支持这个特定谓词”的要求；也不把来源校验和一次语义任务称为两份独立临床证据。

新读取路径的运行配置/采信方式需在当前任务中一次明确；不要继续为每种普通材料建立一套方法申请、许可签发与候选审批子工程。必要的配置身份与方法来源保留，不能伪造旧双模型方法批准来满足历史消费者。

### 6.8 人工更正与增量

复用已有更正对象和追加修订机制。一次更正至少记录原字段、确认后的字段、原件位置、确认方式及影响范围。

更正一个剂量不能顺便补起止时间；更正方向应使该页对应读取失效，但其他页继续复用；更正一个结果只使使用该结果或依赖关系的事实/条件重新计算。

新审核可说明与前次相比的变化。旧审核结果、原始 OCR 和原件保持不变；行动的“已办理”与“临床条件已满足”分开。

## 7. Harness 与本地运行：减掉无必要的工作，而不是削减信息

### 7.1 任务职责及输入上限按工作内容设计

| 任务 | 输入 | 输出 | 默认处理方式 |
|---|---|---|---|
| 方案解构/核对 | 当前方案的有界来源包、定义/脚注、任务专用 Schema | 语义草稿/来源覆盖/具体核对问题 | 第2节内置角色；项目级复用，不向其提供病例答案 |
| 主 OCR | 已准备页/报告区域、专用转录提示 | 原始转录及工具实际能提供的结构 | 当前本地主 OCR；不携方案 |
| 文字整理 | 同一逻辑文档或有界段落组、来源引用、必要字段定义 | 临床事实/事件/用药候选及未决项 | 一个本地常用 Qwen；不做最终入排判定 |
| 局部视觉核对 | 一个报告/行组/批注及上下文 | 实际可见内容、对应范围、不确定性 | 同一常用 Qwen 的视觉能力，按需调用 |
| 语义绑定 | 有关原子条件、定义/例外、已提取候选及其原文 | 具体支持关系及未决原因 | 一次有限任务；只对需要理解的部分 |
| 求值、资料缺口、报告 | 已核实领域对象与当前规则 | 状态、原因、行动、冻结结果 | 现有确定性代码；不额外调用报告模型 |

一次输入不重复携带全部病例、全部规则、全部定位原文和内部哈希。保留必要原文与引用，将程序才需要的身份、证明和执行簿记留在冻结运行对象中。

### 7.2 角色配置独立，先采用已有稳定本地模型，不强制多权重

建议资料侧首轮固定一个现已能稳定接入的 27B/35B 级 Qwen，分别承担文本整理和局部视觉任务。方案解构/核对通过自己的角色配置，可以复用同一权重，不必另起一个常驻进程。具体选择由现有可执行配置和少量实际任务决定，不做新一轮全模型矩阵。

Flash-Next 保留可选，但不为所有页、所有字段或所有条件自动加载。模型名称仍只出现在部署配置/适配层；不出现在临床规则分支中。

复用现有本地资源所有者、取消与装卸保护。不要因为 128GB 就假设多个模型同时驻留一定更快，也不要重复建设已完成的互斥机制。

### 7.3 关闭思考是按任务的技术设置，不是提示里写一句话

对转录、明确字段提取和简单整理，优先验证非思考模式。复杂方案起草和真正的医学语义歧义可能仍需要推理。

Qwen 官方模型卡给出了非思考调用方式，但本地 MTPLX/oMLX 是否接受并正确执行相应参数，要由实际适配与短调用核对。不能将 `reasoning_effort=low` 等同于关闭思考，也不能把其他后端的参数直接塞进当前服务后宣称生效。[W3]

新任务预算应按区域、输出对象数量和实际服务上限配置，不继承所有角色最少 65536 的旧约束。密集表格以完整行组切分，叙述文档以完整语义段切分；不能在模型结果中途截断事实列表后标成功。

### 7.4 保留既有传输兼容，不将业务策略变化变成后端回归

当前 MTPLX 适配对带图与纯文字 JSON 使用不同解码处理。新任务需要复用或明确调用同样的传输适配，不能统一改为 AR、统一取消 JSON 约束或一律删除额外参数。[S03]

新提示/Schema 若改变输入结构，检查适配器当前如何查找 JSON Schema；不能只改消息文本，导致真正提交时没有带上所需约束。

结构化输出必须允许 null/partial/unreadable/未关联等情况。要求每个字段必须是有效数值，会把不可辨认内容逼成猜测。

### 7.5 两段可以直接复用的任务提示骨架

**局部视觉核对：**

```text
你只负责读取本次提供的原始图像区域，不判断受试者是否符合入排。
保留项目与结果的行列对应，以及小数点、比较符、阴阳性、否定、单位和日期。
区分实际结果、参考范围、评分说明和研究者批注。
无法直接辨认的字段返回 partial/unreadable，不根据常识、正常范围或期望结果补全。
批注没有明确所指对象时说明指向未明，不扩展至整页。
只能引用本次输入提供的来源编号。
```

**叙述性资料整理：**

```text
从给定、有来源的文字和已核对观察中整理临床事实，不修正原始记录。
每项事实引用实际来源；区分本人/家族史，肯定/否定/疑似，既往/当前/计划。
区分处方、购买、实际使用；药名、剂量、途径、频次和时间分别提取。
页间延续只使用输入中明确提供的连续来源关系；未明字段保留未知。
研究者意见照原文记录，不生成新的 CS/NCS、诊断或评分。
不补人口学信息，不依据入排目标反推事实，不输出最终符合/排除结论。
```

这是任务骨架，不是未经检查即可替换现有完整 Schema 的成品。实际输出复用已存在的领域字段，并删去不再属于该任务的职责。

### 7.6 识别缓存、事实缓存和规则缓存分开

| 产物 | 主要失效条件 | 不应导致失效的事情 |
|---|---|---|
| 原件/页准备 | 原文件、对应渲染或解码变化 | 修改条款显示名 |
| OCR/区域读取 | 实际输入图像、方向、裁切、模型/识别配置变化 | 同资料更换审核条件或查看报告 |
| 事实整理 | 对应转录/核对/人工更正、事实整理逻辑变化 | 页面筛选、排序 |
| 谓词绑定 | 对应事实、条件、来源政策、节点语境变化 | 无关报告新增 |
| 求值与报告 | 被消费对象、规则、节点与计算版本变化 | 打开旧报告 |

使用现有 ArtifactStore 和冻结运行输入即可，不先新增缓存服务。缓存要同时包含真实内容与相关处理版本；相似图片只能提示疑似重复，不能直接复用结果。

### 7.7 30 分钟目标的计量口径

对一例当前节点记录：页数、报告/逻辑文档数、首次或增量、OCR 用时、模型装载/排队、文字整理、局部核对、绑定、求值/存储和重试。

**机器处理时间包含本次模型装载和实际重试。**人工等待单独列示；内置方案首次解构、方案局部修订的低频项目级耗时单独列示。首次“导入方案→病例报告”的总等待还须单列，不要隐藏方案成本后宣称整个首次流程不到 30 分钟。

只维护一份简洁运行摘要，优先复用已有回执。无返回的 usage 或缓存命中保留未知。不要先建设耗时预测模型、成本仪表盘或复杂性能基准套件。

超过 30 分钟不是自动失败或截断条件，应先查看实际大头。若发现每个区域都重新装卸同一模型，先确认已有会话/批处理作用域是否可复用；只有真实调用链证明存在重复装载才改，不提前重写生命周期。

### 7.8 重试政策

- 传输临时失败：使用现有可取消、有界恢复；不无限延长。
- JSON 包裹/语法问题：优先确定性解析；确需模型格式修复时只处理受影响小输出，保留全部原合法观察。
- 结果被截断：重组更小的完整处理单元，或按明确任务预算补读，不静默接受残缺列表。
- 看不清/关联不明：一次有目的核对后进入人工，不进入“再想一想”循环。
- 资料未提供、来源日期缺失、研究者判断未见：生成明确事项，不重读到模型“找到”一个答案。

## 8. 工作台与报告：只补真实核对动作，不重做全站

### 8.1 保留页面结构，替换不再准确的业务描述

现有方案工作台、受试者/节点、资料页、Profile、审核工作台和报告继续复用。不要为了新的读取方式再建一个“OCR 工作站”。

默认呈现围绕四个问题：**当前有什么明确障碍、哪些还不能判断、证据在哪里、下一步做什么。**

页面上的“两个主读均成功”“双源一致才可采信”应仅用于旧双读记录。新处理显示实际方式，例如“文字读取已完成，3 个区域待核对”，不把单模型改名为“两次独立识别”。

### 8.2 内部核对与临床补证分开

| 内部问题 | 对用户显示 | 不应直接发出的临床要求 |
|---|---|---|
| 字符/行列读不清 | 核对这份报告的某项字段 | “受试者未做该检查” |
| 模型未完成或返回格式错误 | 系统处理未完成，可继续/重试受影响部分 | “病历未记录” |
| 当前规则自动化不支持 | 本项需人工审核，显示原文和已有证据 | “受试者不符合” |
| 原文确实缺少所需信息 | 待补充指定信息和可接受依据 | 无关的一整套材料 |
| 已核实触发排除 | 明确障碍并展示依据 | 用“待补资料”掩盖已有明确不符合 |

内部核对可以使用现有更正/问题对象投影，不必再创建新全局待办中心。临床 ActionRequest 继续只针对实际临床资料或判断缺口。

### 8.3 人工动作保持最少

在原件旁完成：**确认该字段、修正转录、标为不可辨认、修改关联对象、按当前方向重新识别。**

一次确认可以作用于明确圈定的报告行组，但必须列明确认范围；不能“确认此页”就将所有未展示字段和批注一并采信。

采用已有输入/保存组件，不要求用户填 JSON、查任务 ID 或复制日志。保存后给出受影响条款和重算结果。

### 8.4 合并共同根因，不合并医学结论

一份报告的采样日期缺失影响五个条件时，显示一项“该报告采样日期待核实，影响 5 项要求”，下钻可见五项依赖。

这只是问题展示和办理的合并，不把五个谓词合成一个真值；补充日期后仍分别计算。

### 8.5 报告状态与执行状态分别显示

“后台任务结束”不等于“所有条件通过”；“报告已保存”不等于“证据全部充分”。

报告必须清楚包含：本次方案/节点/资料范围、已采用事实、明确结论、具体未决原因、系统尚未完成或不支持部分，以及原件入口。系统处理问题和研究者待办分别呈现。

报告读取已有冻结结果，不再调用大模型重新写出另一套医学结论。补证或更正生成新审核；旧报告固定，行动当前办理情况单列。

本地 workflow 中有以下命令示例；执行前以现场脚本 `--help` 和实际会话身份为准：

```bash
python3 ./.trellis/scripts/task.py --help
python3 ./.trellis/scripts/task.py current --source
python3 ./.trellis/scripts/task.py start 09-11-e2e-eligibility-review
```

不要伪造不存在的会话上下文绕过启动错误。`task.py finish` 在当前 workflow 中只是清理活动指针，不等于任务完成；`archive` 才会标完成并移动归档。未交付本任务就不 archive。[S11]

内置方案子流程与资料链沿同一端到端父任务推进。只有当前任务管理确实需要独立交付/依赖管理时才建立一个方案子任务；不为每个 Agent、函数、小检查和合同建任务。

## 10. 具体实施顺序：六个有限工作包，沿现有任务连续推进

> 以下是同一当前任务中的工作清单，不是另一套 Phase，也不是每包都要求一轮庞大测试。允许将相邻包合并为一个完整提交；不得把一个完整消费者拆到无限后续。

### P0. 核实两条主链，打通前置方案的最小完整增量

**目标：**一页实际调用图，同时确认方案和资料链的真实接点；不能将“有旧规则”当作前置 Agent 已完成。

**动作：**

1. 核当前工作树/任务、未提交改动和实际可执行配置。不恢复历史失败作业，不按旧 PID 操作。
2. 读第2.20节的实际方案上传、两类执行器、生成/修复、水合和共同发布链；标明已有自适应分包/局部恢复是否在当前路径生效。
3. 核有无完整可验证的现行 RuleSet/规则修订/跨章目录/节点要求。已有合格规则可供资料侧先接线；没有则优先完成下面 P0.P，不用精简假规则替代。
4. 核资料侧原图准备、新来源→规范化→事实发布最短链，固定本轮已有可用本地角色配置。
5. 更新 Goal/PRD/design/implement，明确本轮交付包含内置方案入口。普通技术接点由本地 Agent 核实，不再询问已确定的产品方向。

**P0.P：同一任务内的前置方案工作包，不是新 Phase。**

- **P0.P1 输入与作者合同：**复用结构解析/覆盖/分包，修实际Schema/水合/修复不一致。源编号和父子身份由现有结构绑定；以真实完整父条款及跨章依赖跑通生产→保存→即时有源预览。同一候选继续核对，不另调Markdown总结。该切片不得作为完整方案发布。
- **P0.P2 全范围与核对：**沿既有官方/跨章执行器处理当前范围全部来源；同一核对职责同时核第2.23节的身份、时间、逻辑/未知、判断归属、测量/聚合和依赖。不能只数条款；候选补充细节先查脚注。源歧义和模型错误分开，有据局部修订，不再重生整份草稿。
- **P0.P3 共同发布与使用：**原文旁解决真正需要解释的问题，沿现有发布器保存完整官方、跨章、节点与证据要求。规则卡/速查/病例要求从同一内容派生，下游读取同一修订；分别记录首次可读、核对、可发布和发布时间，不虚构三分钟承诺。

**退出：**方案正式入口能产生来源完整、可查看核对、可共同发布并被下游消费的规则；运行/语义核对/发布状态分开记录。不得仅交付 prompt 文件或新增 Agent 类。

**调度：**已有合格规则时，P1/P2资料改造可先行或交错，不必等前置所有复杂分支完美；P0.P必须在P3最终端到端交付前接通。共享源码由同一所有者协调，本机模型任务不因逻辑并行而多权重共驻留。

**真阻塞：**缺正式方案或必要现行修订、真实语义冲突需用户裁定、用户要求之外的新模型服务不可用。已有本地仓库文件未读或历史任务失败不自动构成必须再问用户的阻塞。

**不做：**外部作者 UI、通用 Agent平台、第二队列、全部旧测试修复、全模型档位矩阵或所有未来规则形态。

### P1. 单份资料从真实读取到事实发布的闭环

**目标：**不是只获得 OCR 文本，而是让真实来源在正式链中产生可查看、可回源的事实。

**主要落点：**`page_review_runtime.py`、任务规划/执行接点、`ocr_adapter.py`/`omlx_gate.py` 的调用复用、新读取清单、`fact_normalization_command_service.py`、`fact_normalization_source_adapter.py`、必要来源合同/门禁、现有事实发布。

**动作：**

1. 保留原图上传准备；在既有 JobRunner 注册一个明确的新读取策略/任务，不创建新调度器。
2. 真实调用已有主 OCR，保存原始文字、实际输入身份和处理状态；无坐标则保持实际定位等级。
3. 新读取产物通过第 6.5 节完整接线，贯通提示、候选验证、事务发布和历史读取。
4. 对决定性扫描字段接入一次局部视觉核实或有据人工确认，不让“只有 OCR 候选”无提示成为确定结论。
5. 通过现有资料页/Profile/原件查看器显示结果；至少完成一次有来源的确认或修正。

**退出：**从正式资料入口读取一份真实报告，事实实际保存并可打开原件；没有伪 A/B、没有手工插入临床结果、没有只存在于脚本的旁路。

**必要检查：**相关类型/导入/构建检查，以及源引用真实存在、旧双读可回看、新来源不冒充旧记录。不要为本包新建测试平台。

### P2. 扩展到一例全部当前资料，覆盖关键版式与跨页

**目标：**从“一份报告可用”扩展为“当前节点全部提交资料均有处置”。

**主要落点：**读取计划、`reading_view.py`、现有解析/分段、normalizer 逻辑文档组与连续引文验证、原件更正操作。

**动作：**

1. 对全部页处理方向与主 OCR；按实际文本量分组，不逐条标准重复读资料。
2. 处理同页多报告、双栏结果、实际值/参考说明、手写批注、已有评分、检验时间角色。
3. 修复同一病历跨页否定与断词的来源表示；不通过删除全部分隔符放开任意拼接。
4. 为结构异常和实际决定性字段汇总区域核对队列，按报告批次调用本地 VLM，不做两个全页读道。
5. 未读清、缺信息、未关联和真实冲突分别保留；姓名遮盖不触发无限识别。
6. 累计事实/事件/用药/Profile 来自完整有效集合，不被最后一轮局部核对覆盖成小档案。

**退出：**本例所有页有明确处置；清楚内容成为可用事实；不清楚内容有具体待核位置；关键已知版式不再导致静默错配。

**不做：**覆盖所有医院的模板平台、识别手写签名身份、独立心电或影像诊断、所有复杂历史事件表达式。

### P3. 当前节点规则求值、行动与报告全部贯通

**目标：**生成一份真正有内容的当前节点审核工作底稿，而不是只有候选或全部 UNKNOWN。

**主要落点：**当前实际谓词绑定链、共同组件求值、冻结上下文/发布服务、Action/报告与现有工作台。完整源码不全在补充包内，先在工作树定位现存实现，不重建第二套。

**动作：**

1. 使用P0.P由内置方案入口真实生成/核对/共同发布的完整当前规则集，对可用事实做候选检索与显式谓词绑定。开发阶段的旧合格规则可作对照，不替代这次前置运行。
2. 结构明确的数值/时间条件复用确定性计算；语义问题按第 6.7 节收敛，旧双路绑定的必经门禁改为真实新方法接入，不能假造旧批准。
3. 官方规则、例外、跨章控制和资料义务均进入同一冻结范围；不以“官方条款都输出了”替代全节点覆盖。
4. 修复实际遇到的共同阻塞：类型误匹配、时间选择、判断缺口、来源/组件定位。不要预先重写所有算法。
5. 已核实判断能够正向消费；未查完/候选未核实/本次未见/确有判断分别表达。
6. 复用 ReviewRun/FinalAssessment/ActionRequest 及冻结报告；页面、打印/导出读取同一结果，不另调报告模型。
7. 立即从正式界面跑本例当前节点，记录真实结果和未决事项。

**退出：**DOCX→内置方案发布→本例完整当前节点→报告真实连通；足够证据的受支持规则能形成明确结果，缺证/判断缺失/系统未支持各有具体原因；结果能回原件，报告可再次打开。

**不得用来凑完成：**手工填预期判定、全部设未知、只做报告空状态、删除难处理的规则、把研究者总体“初步符合”作为全部条款证据。

### P4. 更正/补证后重算，不破坏前次审核

**目标：**证明系统可持续工作，而不只是一次性演示。

**动作：**

1. 在原件旁更正一个真正需要核对的字段，或提交一份真实补充材料；没有合适的真实更正时，用隔离非临床样例验证操作，不改真实原件制造错误。
2. 新增更正/资料修订，重新选择完整有效事实集合。
3. 只重跑必要读取、绑定和计算；未变原件不重新 OCR。
4. 保存新审核与差异，旧报告仍按原方案、原资料和原结论读取。
5. 行动“已办理”不直接改判；有充分新证据时通过新审核反映变化。

**退出：**一次完整更正或补证闭环真实可操作；累计用药/事件不丢失；新旧来源和结果能区分。

### P5. 集中检查泛化、质量与时间，然后交付

**目标：**验证本轮路径，而不是重新进入无止境研究。

**动作：**

1. 汇总第 11 节少数关键检查和真实结果，修复能造成错误明确结论或不可操作的缺陷。
2. 使用另一受试者资料检查模板/个案依赖；31010 属于已经查看的材料，可作回归，不称盲测。
3. 有另一份具有不同规则结构的真实方案时，经同一内置方案入口处理、核对并供下游使用；不是仅导入一份手工写好的第二RuleSet。没有材料则明确“跨方案验证未完成”，不声称泛化已证实。
4. 记录该例真实机器处理时间、局部核对数量和人工操作负担。先优化已测得的大头；30 分钟不是质量让步条件。
5. 在主用宽屏完成完整路径；其余已有 1080P/2K/4K 要求集中检查，不为每个小按钮反复跑三轮。
6. 交付可启动的当前节点链、实际报告和剩余问题清单。尚未完成的总体范围保持在原计划，不把项目整体归档。

**退出：**本轮当前节点链真实可用，已知严重错配关闭或明确阻断；泛化/性能/剩余能力如实说明；用户无需终端操作完成普通审核。

## 11. 验收：一份短清单，证明“正确且能完成工作”

### 11.1 开发期间只做必要检查

修改 Python 后检查相关导入/语法和实际行为；修改 TypeScript 后使用项目真实应用配置检查，不把只有 references 的根配置成功退出当全应用通过。

复用已有可覆盖当前风险的检查。没有覆盖时补一个能暴露真实缺陷的最小检查，不新增平行测试框架，不为了数量批量生成相似测试。

**首次正式入口试跑不需要等待全部遗留测试全绿。**与当前改动相关的明显回归必须修；无关旧失败登记来源，集中处理，不能无限阻塞业务闭环。实际运行成功也不能豁免来源错配和错误明确结论。

方案侧的有限核对例子见比较附件第7节：父数相同但映射错误、多锚点、例外/未知、正确脚注、机构/有效期以及原文编辑残留。作为既有集中检查中的少数反例，不另建测试项目。

以上是功能验收，不要求每项再衍生十个测试文件。优先复用现有样例和真实使用路径，将关键失败的最小反例留在已有测试体系。

### 11.3 必须同时看“错误采用”和“有效产出”

报告至少列出：

- 方案来源处置、关键语义核对与下游真实消费分别怎样完成，不能只报条款数量；
- 本次用于明确判断的关键事实，经原件核对是否存在静默错读/错配；
- 清楚且现有能力支持的关键事实，有多少实际进入结果，而不是全部转人工；
- 需要人工核对的区域/问题数量，以及是否因同一根因重复生成；
- 确定性规则和需要语义/研究者判断的规则，各自哪些完成、哪些未决；
- 实际机器处理总时长与主要耗时步骤；方案侧另列首次有源候选、完整候选、核对、可发布、发布及人工等待，不把它们合成一个“解构用时”。

沿用旧“双模型并集事实召回”的指标会与新机制错位：并集里存在一个正确值，不代表最终采用了正确值。新验收优先看**实际被使用的事实和结论**。

有限例子中没有发现错误，只能说明本次检查未发现，不可表述为系统真实错误率为零。没有合格金标时，写明原件核对范围，不制造百分比。

### 11.4 上线工作底稿与最终临床决定分离

系统可以交付含真实未决项的辅助审核工作底稿，不必等待所有临床补证完成才保存报告。但是，不能将临床未决事项自动判成符合，也不能用人工确认按钮替研究者书写判断。

内置前置与第一例闭环完成后，应把可用路径交给用户，不再以其他未实现扩展持续延迟交付；仅旧规则支撑的病例中间成果可以展示，但不能冒称最新全部范围已完成。原项目剩余范围继续保留。

## 13. 本轮最终取舍与停止条件

### 13.1 保留多 Agent 产品，减少重复生成与无用工程

**前置方案 Agent 是产品必需能力，不外置给用户。**用现有官方/跨章解构和同一发布体系完成，补明确的核对与有限取文，不引入 Agent 平台。

**资料侧继续取消全量双读。**主 OCR/原生解析、局部视觉和人工确认合法进入现有事实链；职责协作不等于多个模型反复输出同一份病例。

**既有内置能力先查再补。**自适应分包、局部恢复、源文结构、语义草稿、水合和发布已有基础，不能因为新报告提到这些名词就全部再写一次。

**产物交接，不共享自由讨论。**方案发布供不同受试者重复使用；材料读取不带完整规则执行包；报告复用结构化结果。

**先完整实跑，再集中检查。**少量结构与关键行为检查保留，不用长会商/测试数量代替正式入口结果。

## 附录 B. 内置方案 Agent 的提示、响应和局部修订骨架

> 本附录定义任务行为，不是一个新公共 JSON 协议，更不是可直接导入的已批准规则。实际字段优先复用当前 SemanticRule/Control/wire；只有现有合同表达不了的必要状态才增加。所有数值/药物/节点例子必须来自当次方案，不在公共提示中固化当前病例答案。

### B.1 共用系统指令：各方案角色只加载一次职责基线

```text
你是入排审核系统的前置方案 Agent。本任务只理解正式方案和当前生效修订，不判断具体受试者。

事实依据：只使用本次来源工具/任务包提供的原文。解释材料只能在已登记的适用范围内澄清，不能修改方案。
输出：有来源的规则/控制草稿，或具体的缺上下文/解释问题；不得宣称已经发布。

临床语义必须保留：
研究部分和审核节点；对象和属性；肯定/否定；AND/OR/NOT；触发、例外和替代；
阈值原文和单位；事件回溯、检查有效期、间隔、持续时间的差别；
时间锚点与端点；复查采用/次数/观察选择；必须/建议的强度；
所需证据的具体用途；研究者判断是否由原文明示。

不得把诊断/评分本身需要专业理解，自动改成另需一份研究者声明。
不得从“未提及”推断“允许/不要求”，不得按医学常识补阈值、默认时点或例外。
来源编号可用不代表某种解释必然正确；引用要直接支持所写内容。
完整上下文不足时请求补取，不要根据上一份方案或已有病例猜测。

使用本次短来源编号和任务专用 Schema。不要自行生成正式 ID、哈希、数据库关系或模型回执。
只在本次允许的草稿对象范围内生成或修订。不得改写不相关条款。
不返回长篇过程思考；保留必要的简短判读依据、来源和未决原因。
```

宿主应区分“来源原文”“已验证结构信息”“模型候选”“用户解释”；不要把它们拼成一段无类型背景。共同基线保持短而稳定，具体 schema/能力及本次临床风险另行按职责装配。

### B.2 全文处置/全局语境任务

```text
本次职责：为输入的全部来源单元建立处置，并识别研究范围、节点、定义和依赖。

逐项处理 owner_sources，不能遗漏，也不能把未输出项默认为无关。
context_sources 仅作解释上下文；不得重复生成属于其他包的主条款。
同一段含多个不同用途时保留多个关系，不能只给一个标签后丢失另一项要求。

对每个单元说明它属于官方入排、流程要求、其他控制、定义/补充、当前范围不涉及或待核实。
与入排无关的研究管理事项保持其真实类别，不制造受试者义务。
表头、脚注、引导语和跨章定义必须与受影响来源关联。
关键词可以帮助查找，但不能作为“无关键词即无要求”的依据。

需要来源工具补取时，一次提出有关的来源组/表格/明确引用，不逐个字发工具请求。
只输出本任务所需的紧凑处置、语境来源、关系和疑问，不生成完整执行规则。
```

复用现有发现/覆盖步骤。若当前第一生成步骤已能完成这些任务，不额外强加一轮同内容模型调用。

### B.3 官方规则 / 跨章控制解构任务

```text
本次职责：根据完整 owner_sources 和必要 context_sources，生成指定类型的语义草稿。

role=official：保留官方 IN/EX 编号、父限定语、子条件及例外。不得把跨章控制伪造成新的官方条款。
role=control：保留适用、触发、义务和例外，以及强度、节点、时间、最低证据和它支持的原子用途。

用现有语义树表示原文逻辑，不为迎合格式主动展开大量重复分支。
一项证据支持多个条件时分别关联；用来查明触发条件的资料，不能因触发尚不明确就省略。
不同时间用途单独表示；取值规则和复查采用只按明文，不默认最新、最佳、ANY或ALL。

语境明确但执行器暂不支持时，完整记录原要求及不支持原因。
语境或原文有歧义时，返回具体问题、来源和受影响对象，不能选对受试者有利/不利的一种解释。

只输出指定作者字段。不生成 published=true，不决定病例结论。
```

参数 `role` 是职责示意，不能代替两个现有来源族的不同必填 Schema；保留原有不同外壳和通用内核。

### B.4 方案核对任务

```text
你负责检查方案草稿对原文的完整性与忠实性，不负责再起草一份完整方案。

先看本次原文来源组，辨认其中应形成/补充的审核要求，再与草稿对应；
不要只从草稿已经列出的标题反向寻找支持。

做两方向核对：
A. 原文中的要求、限定语、定义、脚注、例外是否都有正确去向；“不涉及”的来源是否被误排除。
B. 草稿的对象、逻辑、极性、阈值/单位、时间/锚点、证据政策、判断责任和节点是否得到原文支持。

相同词出现在原文、引用合法、父条款数一致，都不能单独证明语义正确。
重复表述、补充、例外和真正矛盾分开；不要自动选“更严格”的解释。

仅返回：实际核查的来源/规则范围，以及有原文依据的问题。
每个问题指出受影响对象、原文位置、问题维度、草稿位置、具体差异和必要的修订/取文请求。
没有问题时返回明确已核范围和空问题表；不编造正确率，不发表长篇好评。
不要提出措辞美化、风格统一或与执行无关的优化。
```

若采用两步实现核对：第一步来源先行的简短期望记录属于本次核对产物；第二步才能看到相关草稿。也可在现有一次有界核对中以字段区分，但不要声称这相当于互盲独立模型评测。

**V3核对增量：**在同一个既有核对请求中加入以下约束；不是新建第二位Critic。

```text
不因候选简短或产生快就预设其错误。候选包含主条款以外细节时，先查有关脚注/定义。
核原编号与源父子/期别映射，不只比条数。
核每个时间条件的锚点和用途，不让全局随机日覆盖局部原文。
核条件、例外和反向展示的一致性；缺证不是不存在，不适用不是已满足。
核研究者判断只作用于对应对象；病情稳定不等于剂量稳定。
核附录是真正等效映射还是分类表；不按常识修原文编辑残留或矛盾。
只返回有来源的差异、遗漏、待解释及已核范围；无问题时允许无发现。
不重生整份规则，不为风格润色、无依据从严或额外检查发起修订。
```

### B.5 局部修订任务

```text
你只修订本次指定的规则/控制对象。输入含基准草稿、相关原文和逐项问题。

优先解决具体根因，不重生成整份规则集。
返回完整的受影响小对象，而不是重写未涉及对象或生成字符级差异补丁。
保留原有未受影响的临床字段、来源和逻辑。

若问题实际来自缺上下文，先请求补取。
若需要改变共享定义或影响未获准修改的对象，报告影响范围，交由宿主重新规划。
若核对意见本身不符合原文，返回有来源的异议，不迎合核对者强行修改。
只声称问题得到修订，不声称已经通过核对或发布。
```

### B.6 统一响应外壳的最低行为要求

优先沿用现有结构，只增加缺失的状态字段。可用下述**概念外壳**讨论宿主行为，不将它直接作为生产 Schema：

```json
{
  "task_ref": "宿主提供",
  "base_revision_ref": "宿主提供",
  "state": "done | needs_context | needs_clarification",
  "processed_source_refs": ["本次短来源编号"],
  "drafts": [],
  "context_requests": [],
  "issues": []
}
```

这里 `state` 的竖线仅解释允许选项，实际 Schema 必须是 enum。`done` 仅表示该次模型回答任务结束，不表示草稿被接受、规则完整或可以入组。示意空数组不能通过真实发布。

具体问题对象应能够表达：

```text
finding_id              宿主分配或本次局部短编号
source_refs             原文依据，包含直接相关的上下文引用
draft_ref / json_pointer 受影响的真实草稿字段；不得指向未获准对象
dimension               coverage / scope / logic / polarity / numeric_unit /
                        time / exception / evidence / judgment / capability
current_reading         当前草稿如何表示
source_supported_issue  原文与草稿的具体差异，或确实未明之处
requested_action        fetch_context / revise_object / user_clarification
```

问题号、来源和 JSON Pointer 都由程序复核。不得仅凭模型给出 pointer 就任意更新对象；最终按整对象版本与允许字段进行验证和提交。

### B.7 四个可复用的错误处理准则

| 错误 | 宿主动作 | 重试边界 |
|---|---|---|
| 合法字段缺失/Schema冲突 | 核本次生成Schema与实际构造器，能修宿主就不再问模型 | 不用相同不一致Schema反复调用 |
| 引用混淆 | 明确短引用映射与类型，局部还原后严格核原文 | 不用模糊匹配猜 source_span_id |
| 真实语义遗漏/误解 | 给受影响对象和源文，有限局部修订 | 同问题无新增信息提前停止 |
| 额度/服务不可用 | 保存已完成合法批次并显示真实恢复方式 | 不静默换收费模型，不把服务失败当医学歧义 |

### B.8 方案功能的精简验收清单

- 正式 DOCX 上传后，内置任务真实产生新候选并经共同发布进入下游；不能仅复用一份旧 RuleSet 证明本轮前置 Agent 成功。
- 所有实际来源单元有处置，官方条款、跨章限制、流程表脚注与定义能回源；处理范围与可执行范围分开。
- 高影响规则的对象/否定/逻辑/时间/例外/证据责任经原文核对；正常可执行要求不能全返回未知。
- 一项局部真实问题或隔离反例能定向修订，不抹掉无关草稿，也不重解构全方案。
- 来源不足、解释不明、系统能力不支持和服务故障有不同状态，不能统一转“缺研究者判断”。
- 同一发布规则供多个受试者复用；方案的首次成本和单例成本分别显示，首次全流程总成本不隐去。
- 另一份具有不同规则结构的真实方案通过相同入口处理；缺少该材料时明确泛化未验证，不伪造完成。

不要求为本清单新建完整测试平台；复用既有调用、原文核对、失败回执和少量必要行为检查。
