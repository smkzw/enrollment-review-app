## 四、为什么这么久：机制必要，但用法有偏差

### H1：修复节奏仍是局部错误驱动，完整用户动作验证过晚

支持：16次新控制作业均止于首批；成功发现复用节省分类成本，却没有消除首次完整 wire 与逐来源核对耦合。每次补一个错误后，长作业才揭示下一层问题。完整病例、补证更正、当前报告仍未完成。

反证／未知：不是所有修复无价值；候选权限、否定、数值及来源的错误确实危险，不能取消保护换通过。尚无同预算 B 路线接相同消费者的完成对照。

替代解释：真实方案结构和模型随机性可能带来本来就需要的多轮处理；新来源身份也造成合法失效。这解释部分运行成本，不能解释大量源码微修与相同首批重复。

可推翻条件：冻结同一失败来源，通用家族修复一次进入正式保存／消费者，在等义、反事实、恢复变体中稳定闭合，并减少新长作业数量且不降来源要求。

建议：停止再以“让当前整批变绿”为唯一下一目标。先选择现有能力能支持的一个有源独立要求，贯通当前规则采用、事实资格、工作稿、原件和更正；完整覆盖保留，其他未支持要求准确列技术或原文未决。最终共同发布合同仍不得绕开。

### H2：提示包装和返回结构有固定负担，但不只是模型慢

支持：远端 compact=false；3条理论上限受16K估算阈值压成23个单条批次。1／2／3条实际提示64814／66010／67074字符，固定41流程目录和23128字符 Schema 占大部分。不存在选择条目的诊断对照仍有31471字符 payload；该对照不是合法请求。删除纯 title/default 可省5120字符，不能使整包落到16K，更不能宣称已经提速。

反证：工程审阅把本地 strict decoder 的6个 anyOf误当远端提示开销；所有者源码反证远端原子0 anyOf，拒绝错误归因。上下文删减不能依据标签或摘录不相交证明无跨章关系。

替代解释：传输、思考输出、厂商吞吐和重新生成完整结果也是耗时来源。字符估算不等于实际 token；无费用实报就未知。

建议：以真实完成回执测固定头、每条增量和恢复成本，再决定有界分包／Schema 无语义元数据清理。改变分包估算与父条目恢复属于行为变更，要版本化；不要直接切 compact 或删跨章上下文。原始来源可全文供理解，最终提交仍限授权目标与依赖。

### H3：来源图正确，但被当作语义与资格证明的风险仍在

支持：candidate_linked 只说明同段引用，不证明每个定义被表达；同页／同文／观察 ref 数不证明独立采集；像素框有 hash 不证明它覆盖了正确检验行。图在身份、依赖与更正失效上有价值，但不能自己理解义务、对象和例外。

反证：没有必要推翻现有图关系、引入另一图数据库或自由 Agent 真相；已有来源／事实／规则／计算实体足够承载这些证据。

替代解释：问题可能不是图设计，而是来源解释、短编译与下游生产者没有正确接通。

建议：结构图回答“在哪里／来自哪次”；语义依赖回答“作用于谁／何时／哪个条件”；资格生产者回答“是否足以被这个消费者采用”。三者分别验证，不用任何单个数量或 policy 字符串代替证明。

### H4：会商和测试有用，但数量未变成完整覆盖

实际31个工程任务目录、50个去重终态轮次，runner累计25971.716秒（约7.2小时）是调用耗时总和，不是日历耗时：Grok24、ZCode GLM14、CodeBuddy DeepSeek11、pi/default1。default不能宣称已验证精确模型身份。部分 top-level route 与实际 fallback不同，按真实轮次记录。审阅不读临床原件，不能替代医学核对；一轮越界运行合成测试的限制已有记录。

支持：独立审阅发现范围授权、恢复覆写、源数字等重要风险，也存在“六重远端 Schema”等错误；上下文非常宽的源码扫描耗费大量缓存输入，尚未提供对应临床消费者闭环。

反证：高后果语义改动确需独立质疑，删除会商或把全库绿色当替代同样错误。

建议：以相连故障家族为冻结审阅单位，只向一个独立审阅者提供来源关系、当前产物、消费者及危险反例；所有者先复现核心假设。 routine 格式／记录改动不追加会议。完成一个功能包集中验证一次，再用一次真实运行挑战整个包；失败两次无新信息时停止该分支，改 decomposition，不再补提示后长跑。

## 五、所有者自身执行教训

- 多次先猜脚本字段／导入，再从报错回查实际定义，导致无模型的驱动失败和额外重跑。今后先读完整真实合同、方法签名和稳定入口；先 dry-run 到禁止发布边界，输出 schema 与停止条件验证后才领取不可逆 Job。
- 新官方首次7ca任务因驱动对确认值比较、恢复汇总领取错误而终败，实际0模型调用；不能写模型不可靠，不能偷偷复活。后继驱动先检查已有冻结结果，新的afa任务才合法开始。
- “最后原答”和“被核验整批装配”常不是同一件事。每次错误必须同时保存实际 raw response identity 与 rejected assembled identity；没有原答不能按hash补造。
- 失败类型要在技术、合同、含义、来源、能力、真实资料缺件之间分开。无效 JSON 不是研究者判断；标题／框错不是患者没提供；模型没读清 NCS 不是研究者没有写。
- 局部修订不能无意丢旧流程目标、旧来源或正确兄弟。先冻结授权前基线，逐目标一次修改，整包最终重新验证，不让共享源扩大权限。
- 测试失败要具体归因：产品真实 RED、夹具缺字段、测试路径不存在、补丁落错异常分支、环境、外部服务。不能统称旧测试；不能删反例／放门禁追绿。重复全包检查也有浪费，集中窗口需先等前次终态。
- 本机未提交源码不能归到 GitHub HEAD。本轮发布明确源文件 hash清单和代码提交；继承改动不冒领作者身份，旧测试仅属于其旧快照。
- 清理采用可恢复冷存档，不删除不可重复的失败证据。旧库恢复后方可打开，防止 SQLite在旧路径造空库造成假“丢资料”。

## 六、下一阶段怎样更高效，不再无界扩批

1. **一个闭合功能包。** 消费当前新 DOCX官方草稿的真实终态与失败家族，选择已有原文和消费者可以支持的语义点；完成来源解释→正式构造→混合采用→工作稿的生产／保存／读回／API入口。其它来源逐项保留处置。失败可在冻结小样局部重算，不每改一个点重建68批。
2. **一个病例动作。** 利用已上传24页及可证明的来源资格，建立一个真实当前节点结果，明确正常、风险、技术和资料未决，做一次补证或更正及受影响重算，旧报告 hash不变。数字位置正式自动采用仍需先达标并获得用户确认；不能借上传归属责任代替读数验证。
3. **一次候选交付窗口。** 同源完整发布、正式工作稿／报告、更正，随后未参与调优的留出、1080P/2K/4K实际操作、缩放、启动停止及备份恢复。直接检验用户能否完成动作，不用空页面、Mock、测试数量或全部未知报告代替。

效率的检验不是“这次少用了几秒”，而是在同一来源、预算与真实性标准下，正确结果更多、未决更准确、恢复范围更小，并且实际到达用户入口。若轻语义固定流程已经够用，不强求更自治的框架；没有同终点对照不宣布哪条路线胜出。
