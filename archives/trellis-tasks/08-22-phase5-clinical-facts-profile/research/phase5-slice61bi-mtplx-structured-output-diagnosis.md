# MTPLX 严格结构化输出故障诊断与系统修复

日期：2026-08-29

## 结论

此前连续 HTTP 500 不是方案文本长度、Schema 大小或缓存容量单独造成。服务端对思考前导设置 4000 字符上限，同时 MTP 推测解码在严格语法边界附近可能先推进草稿词元、后同步主词元；当思考越过边界时，语法状态与生成状态失步，最终抛出约束解码错误并返回 500。

工作者提出的提高或取消服务端前导上限可以缓解一类边界，但不是本系统采用的恢复路径。为了不依赖服务重启、守护进程环境或临床提示词缩短，本系统对 MTPLX 的严格 JSON Schema 请求统一使用请求级自回归解码：`extra_body={"generation_mode": "ar"}`。普通文本或非严格结构化请求不受影响。

## 修复范围

- 方案解构传输
- 跨章节方案控制传输
- 期别适用性传输
- 证据规范化传输中的严格 JSON Schema 路径

DeepSeek 和 oMLX 的请求参数保持原样。修复不改变提示词、方案来源、临床规则、Schema 严格性、模型或推理强度。

## 证据边界

- 服务日志与直接语法步进复现支持“4000字符边界后约束状态失步”的机制。
- 非临床矩阵中的 HTTP 200 只有在正文非空且可按目标 Schema 解析时才算成功；单纯 200 或空正文不能证明可用。
- 产品四条严格结构传输均有请求参数回归，聚焦测试为 `45 passed, 5 warnings`。
- `tests/v2/protocols` 与 `tests/v2/agents` 完整组合回归为 `1189 passed, 58 warnings`。
- 同一冻结来源、临床问题和父级检查清单下，v14 真实运行不再出现 500；三次同会话有界响应依次为结构错误、发布错误和成功解析，最终得到 1 个候选和 1 个控制，技术门禁通过。

## 未采纳意见

- 不以永久修改 `MTPLX_THINK_PRELUDE_MAX_CHARS` 作为应用运行前提。该配置属于外部服务状态，重启后可能漂移，也不能消除 MTP 与严格语法边界的同步风险。
- 不缩短临床推理、放宽 JSON Schema 或改回自由文本，这些做法会降低可验证性。
- 不把 HTTP 200、服务健康或非空模型响应单独写成通过；必须同时验证非空正文、Schema 解析和产品门禁。

## 后续约束

若未来 MTPLX 在服务端修复推测解码与严格语法状态同步，可在独立非临床基准中重新比较 MTP 与 AR 的速度和质量；在该证据完成前，所有 MTPLX 严格结构化输出继续使用 AR。该决定不限制系统内置模型的上下文长度。
