# Worker 01 同会话返修：用户可见期别、实质标题与候选/正式身份边界

父级在真实 D001 工件验收中发现三个通用契约缺陷。请仅修改你原获授权的五个路径，并使用同一会话修复；不得写 D001 工件。

## 1. 独立期别项目的可见表达

矩阵内部必须继续保留 `selected_phase_applicable` 与 `cross_phase_shared` 的差异，来源校验也必须继续严格。但用户选择 II 或 III 期后，这已经是独立项目，面向医学监查人员的 Markdown 不得逐条显示“跨期共享”“选定期别适用”等底层投影术语。

- 对 `SELECTED_PHASE_APPLICABLE` 和 `CROSS_PHASE_SHARED`，可见正文统一显示“本项目适用”。
- 对不应进入可发布矩阵的对侧/未决状态，保留清晰中文阻断表达，但严格校验仍应拒绝。
- 索引列名和详情标签使用自然中文，例如“本项目适用性”，不要用“期别处置”。
- JSON 不能丢失内部真实 disposition。

## 2. 拒绝无信息的机械标题

真实 D001 工件把标题写成“官方入选 IN-01”“官方排除 EX-01”，只是机械重复编号，无法让监查人员浏览。合同应通用拒绝这类标题：规范化后若仅由“官方/入选/排除/标准/条件/条款/规则”等空泛词加当前官方编号组成，则拒绝；不要硬编码 D001 文本。真实标题必须概括该条核心控制，例如“知情同意与沟通遵从能力”“签署知情同意时年龄范围”。补充反例测试。

## 3. 候选身份不得伪装为正式目录身份

当前流程行强制 `required_procedure_catalog_item_id`，其他章节行强制 `protocol_control_id`；但真实 D001 的正式流程目录因定位缺失尚未构建，后续跨章节人工基线也尚未发布为 `ProtocolReviewControl`。现合同因此诱导使用看似正式但无法对权威集合验证的 ID。

请为盲前/人工核对矩阵增加明确的“来源候选身份”（字段名自定，但须清晰、稳定、非正式身份），并满足：

- 官方入排行仍只绑定官方父/子编号，不得使用候选身份。
- 流程行必须且只能二选一：正式 `required_procedure_catalog_item_id`，或稳定的候选身份。
- 其他章节控制行必须且只能二选一：正式 `protocol_control_id`，或稳定的候选身份。
- 候选身份进入稳定矩阵行 ID 的派生来源，但不得在可见 Markdown 中泄露。
- 任一行使用候选身份时，`claims_complete=true` 必须被拒绝。
- `claims_complete=true` 时，正式流程行必须提供非空权威流程目录集合并逐项命中；正式其他章节行必须提供非空已发布 `ProtocolReviewControl` 集合并逐项命中。不得因调用方省略权威集合而静默放过。
- `claims_complete=false` 时，正式身份若提供了相应权威集合仍需校验；候选身份可以在来源闭包和处置闭包成立时用于人工基线。
- 冻结覆盖清单 disposition 对候选流程行应能与候选身份闭合，不得假装链接到正式目录字段。若现有 `ProtocolStructureDisposition` 没有候选字段，不要修改其合同；在矩阵校验中要求 disposition 明确处置为流程相关且来源闭包一致，并避免把候选 ID 填进正式 linked 字段。请根据现有 disposition 枚举选择最小、可解释的实现，并写反例测试。若无法无损表达，明确阻断而非绕过。
