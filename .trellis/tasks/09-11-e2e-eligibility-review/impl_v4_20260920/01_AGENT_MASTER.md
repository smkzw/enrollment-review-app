# 开发 Agent 实施主指令

## 任务与目标

在 `smkzw/enrollment-review-app` 现有代码与当前工作树上，落实已经确定的 V3 产品方向及 2026-09-20 用户补充决定，完成“内置方案发布 → 一例当前节点资料 → 来源化事实/病程 → 逐条审核 → 例外工作台 → 一次更正/补证后新审核”的可运行闭环，并对几十页至一百余页混合低清资料建立质量与性能证据。

保留 Graph engineering + Loop engineering 的产品架构；保留已有持久任务、checkpoint、来源定位、事实与规则发布及历史体系。不要新建 Phase、重做数据库或换整个编排框架。

## 已决定，不重复询问

1. 云端使用无限制。原件图像、文字和结构化资料均不受先前“只本地”产品约束；无需逐次请求云端许可。使用产品显式配置的可用服务与凭据；不凭空假设账户/模型能力，不创建付费订阅，不把凭据或病例上传到公开仓库。云端无限制不表示免除能力核查、审计、限流与失败恢复，也不意味着必须扩大调用量。
2. 工作台默认让医学经理处理风险、冲突和未决；全部条款、正常事实、过程和原件随时可查。不能为了“少数”隐藏真实问题或设置问题条数上限；通过自动消解、关联聚合减少重复劳动。
3. 主场景为几十页至一百余页扫描检验单（常带手写批注、未必高清）、病历扫描、手机照片、屏幕翻拍。不得仅用清晰 PDF 验收。
4. 内置前置的方案解构/审核 Agent 是正式路径；不能改为用户手工解构 JSON。系统跨方案通用，不针对某一受试者或某一试验硬编码。
5. 取消固定全量双 VLM、每页完整 ClausePack、全部语义角色统一 65K 下限。保留真实 OCR、单视觉、独立针对性核实、有源人工修订；不能伪造 A/B 记录满足旧门禁。
6. 批注 CS/NCS/QTc 是可用原始资料，但必须保留对象、日期、作者/来源可确认范围。遮盖可正常接受，不猜姓名，不重新诊断波形、影像，不重新评分。
7. 应用仍为本地单 Mac、单用户、中文宽屏工作台；不增登录、多人审批、手机界面或外部流转作为本轮依赖。

读取当前 AGENTS、现行 PRD/design/implement、V3 分工及最新 checkpoint；文档中旧“暂停/全量双读/只本地”段落不覆盖已知新决定。只修改相关现行要求，不抹掉历史。

对 R01–R14 创建 `仍存在 / 已解决 / 部分存在 / 不成立 / 未验证` 表。已解决项保留回归，不重复重构。R12 云端边界现已解决为用户决定，不再等待授权。

## 1. 先解除已有审核链阻塞，保留其真实证据

读取当前已发布事实，不用预期入排结论反推候选。将 `predicate_binding_candidates` 的逐谓词×逐事实长解释合同改为有源候选边、关键反证和明确未决；保证官方、例外、触发、跨章条件逐项有处置。采用输入覆盖清单、分面检索、补查与紧凑审计，不删除来源/时间资格。

统一 role/task 预算与 provider 能力核查；不要仅将 262144 改到更多地方。截断时按可重放语义单元拆分，而不是原样无限重发。记录请求、实际响应模型、输入范围、输出完整性和成本。

修复控制模板仅写日志消失、错误版本标签、合法测试 fixture 不匹配等明确问题。保留正常事实可保存与要求未决可见两条边界。

尽快使用已有已发布规则与事实跑出一个有实际判定、有来源、有具体未决的当前节点审核；全 UNKNOWN 不能算闭环。该步骤先验证 C 链，不冒称新资料读取策略已完成。

## 2. 完成新的读取策略，而不是停在新 prompt

主路径为：不可变原件/页清单 → 原生文字或主 OCR + 可见内容覆盖 → 原件观察 → 针对性视觉核实 → 来源化事实/病程 → 候选/资格 → 确定性判断 → 例外工作台。

所有页面都有处置；未读到不等于没有。正常检验结果仍记录。手写覆盖检查不依赖 OCR 是否先发现批注；低清和翻拍可按页/区域自适应加强，不强制每页两个完整 VLM。

每个调用只给职责所需上下文：常规原件读取不含整套方案阈值；针对性核实首次不看另一路期待答案；关联器看具体规则和必要纵向来源；Critic 寻找矛盾、遗漏和不成立的推断，而不是再抄一遍全部事实。

将政策接通到**生产、持久化、消费、API/UI**四层。尤其更新 `fact_normalization_source_adapter` 中对已完成双读的依赖；新 source policy 必须真实建模，不能绕过 FactAuthority 或仅改 `require_page_review=False`。

## 3. 将“少数风险处理”做成真实主流程

上传后自动完成有据的文档分组、类型识别、可自动解决的元数据及页级处理。保留真实来源证据，不能将 `is_auto_suggestion=False` 伪装成人工确认。不能要求每份扫描都先人工确认元数据后才能开始整例处理。

对象/时点/出处确实歧义，且影响当前要求时，生成具体 issue。相同根因关联多个要求，合并为一个操作入口，保留所有受影响条款。不读得清、缺原始依据、需研究者判断、系统不支持和检查未做分别表示。

正常项可折叠、全量可下钻。未处理页、失败任务和未核实关键事实必须可见，不允许显示成“无问题”。保存报告不要求逐条确认，问题关闭不自动改资格。

## 4. 增量与历史

新补证、更正、规则修订生成新审核；旧原件、旧事实版本及旧报告不覆盖。原件观察缓存与当前规则/节点关联缓存分离。不能把旧的方案依赖双读结果直接改标签为协议无关结果。

重算传递依赖闭包，包括“在已提供范围未发现”的否定检索结论；新增资料即使未链接到旧事实，也可能使这些结论失效。证明不受影响后才复用，并冻结复用依据。

## 5. 协作与实施顺序

先 WP00；WP01 打通 C 链；WP02–WP04 共同完成新来源合同、harness 与 B 链；WP05 对齐资格/覆盖/控制；WP06 接入例外工作台；WP07 增量；WP08 综合验收。独立可并行的任务按当前开发调度规范执行，不擅自启用外部未批准 spawn 路径。

一个合同一个写入负责人；其他 Agent 通过版本化产物接口协作。不要让多个 Agent 同时改共享合同/迁移/公共配置。独立只读 reviewer 检查真实 diff、测试和来源边界，不以口头“通过”替代结果。

## 6. 禁止的捷径

禁止病例/方案特判、改真实原件、全量“通过/未知”填充、丢弃正常结果、阈值反向指导读数、置信分替代证据、只有高置信就自动入组、关闭 issue 即更改结论、缺失转阴性、近重复图像自动删掉批注、只截前若干页/事实/条款、生成式修图补数字、继续用两模型名字代替独立核实。

禁止一次性拆掉所有旧读取器；保留旧报告可读，不将旧 pipeline 同时作为新默认重复执行。无调用图/回归证据不删旧文件。不上新 SaaS、向量库或大模型横评平台作为首例闭环前置。

## 7. 验收与回交

按 `05_ACCEPTANCE_AND_BENCHMARK.md`，至少覆盖：全页/全条件清单、低清+手写+多报告同页、同词异位置、阈值与单位/日期、矛盾与否定、跨章要求、一次补证和一次更正、取消/崩溃/重试、30/60/120/150 页规模与 1080P/2K/4K。

真实病例在用户本机现有产品配置中跑；原始病例不进公开 GitHub。性能目标是已发布规则下尽量达到单例约 30 分钟，**不是硬超时、质量折扣或用户对所有页数的保证**。分开报告首次有用结果、自动处理全程、人工操作及外部补证等待；没有测量就不写达标。

回交：当前 SHA/dirty 范围、逐项发现处置、修改合同与文件、实际命令/退出码/测试结果、新链四层接通表、质量与耗时账本、原件可回看证据、增量及旧结果不变证据、剩余缺口/回退方案。先交真实单例闭环，再交规模/跨方案验证。未完成项明确列出，不提前 archive 当前任务或 claims_complete=true。
