# Phase 3 技术设计

## 1. 设计原则

1. 方案文档结构、Agent 语义候选、确定性校验、用户确认和正式发布是五个独立边界。
2. 现有 `Rule`、`RuleComponent`、`RuleExpression`、`WorkflowStage`、`EvidenceRequirement`、`ProtocolAuthorityRecord` 和持久 Job 继续作为基座，不创建平行真相。
3. 旧 `app/deconstructor.py` 只作为回归参照；V2 新写路径不继续加入正则或项目特异文本补丁。
4. “没有提取到”是失败，不是空结果；所有成功都必须有非 LLM 完整性证据。
5. 正式发布对象追加写入；草稿可修订，但不能原地覆盖已发布规则。

## 2. 端到端数据流

```text
原始方案文件
  -> 不可变文件登记与哈希
  -> DOCX结构提取 + 可复现PDF渲染
  -> 元信息候选与期别候选
  -> 用户确认期别（需要时）
  -> Protocol Deconstructor结构化草稿
  -> 确定性方案完整性检查
  -> 用户审阅/编辑/反馈修订/差异比较
  -> 再次确定性检查
  -> 用户发布确认
  -> ProtocolAuthorityRecord + RuleSet revision + WorkflowStage
  -> 新项目或现有项目的新规则版本
```

每个箭头都有显式输入输出契约；API 不拼接规则，前端不解析模型自由文本。

## 3. 新增领域契约

### 3.1 文档与来源

- `ProtocolSourceArtifact`：原始文件身份、SHA-256、MIME、大小、存储引用、上传时间。
- `ProtocolRenderArtifact`：原始文件哈希、LibreOffice 版本、渲染参数、PDF 哈希、页数和状态。
- `ProtocolSourceSpan`：`source_ref`、文档部件、section、块顺序、表格/行列、渲染页、文本范围、原文摘录、定位精度和对齐状态。
- `ProtocolExtractionSnapshot`：一次结构提取的不可变结果、解析器版本、覆盖统计、异常和派生物引用。
- `FrozenProtocolCatalog`：Agent 调用前冻结的官方父规则目录和按期别、访视实例拆分的基线及以前必做项目录；目录项包含稳定 ID、原文范围和来源片段。

DOCX 分页不稳定时，用户界面显示“本次渲染第 N 页”，同时保留 OOXML 段落/表格定位。渲染失败不得删除结构通道来源；但需要页级定位的发布门槛会明确提示降级。

### 3.2 元信息与期别

- `ProtocolMetadataCandidate`：字段、候选值、来源、优先级、置信依据和冲突组。
- `StudyPhaseCandidate`：期别、设计类型（独立/无缝候选）、适用章节、来源和是否需要确认。
- `ProtocolIdentityDecision`：用户确认后的项目名称、方案编号、版本、日期和期别；保存确认来源与时间。

元信息排序规则由确定性代码负责：明确标签的页眉/页脚 > 第一页明确标签 > 签署页明确标签 > 正文摘要 > 文件名。文件标题、项目名称、方案编号/版本和模板编号/版本是不同字段类别，不靠项目名称黑名单过滤；项目代号若只有通用标题或文件名兜底候选，必须要求用户确认。

### 3.3 草稿与解释材料

- 扩展 `ProtocolDeconstructionInput`：加入已确认期别、提取快照 ID、允许的 source_ref 范围和目标父规则目录。
- 扩展 `ProtocolDeconstructionDraft`：加入草稿 revision、父规则目录覆盖、规则/流程来源覆盖、结构警告和前序草稿引用。
- `InterpretationSource`：类型、文件哈希、版本/日期、来源定位、适用规则、说明文本和权威级别。
- `InterpretationConflict`：解释材料与方案原文冲突的规则组件、两侧来源、影响和处理状态。
- `ProtocolDraftRevision`：每次 Agent 输出、已保存的手工编辑或反馈修订形成新 revision；记录原因、操作者、前序 revision、生命周期状态和差异摘要。未保存编辑留在前端局部状态，取消时明确询问是否丢弃；已保存 revision 只标记为已取消/可恢复，不物理删除审计历史。

解释材料不能直接成为 `Rule.source_text`，也不能更改官方编号、方案阈值、逻辑、流程节点或到期访视。它只可附着在模糊组件的说明层；冲突时确定性检查拒绝发布相关修改。用户指出解构错误时必须引用当前方案来源片段；同一方案内的来源忠实纠错可以修正表达式和流程映射，不要求伪造新的方案版本。

### 3.4 发布边界

发布继续使用 `ProtocolAuthorityRecord`、`ProtocolIntegrityManifest`、`ProtocolAuthorityConfirmation` 和 `RuleSet`。发布服务一次事务中：

1. 锁定草稿 revision 和用户确认的协议身份；
2. 若为重新解构，校验方案编号谱系和研究期别属于当前项目；版本、日期和哈希可随合法新版本变化，但跨方案或跨期文件不得发布到当前项目；
3. 复跑完整性检查；
4. 写入来源记录、权威记录、规则集和流程节点；
5. 创建新项目，或把现有项目追加到新规则 revision；同一方案编号与期别已有正式项目时，首次解构不得再创建平行项目；
6. 写入发布确认和幂等记录。

任一步失败全部回滚；旧正式版本保持可读。

## 4. 文档提取器

### 4.1 结构提取

V2 新模块放在 `app/protocols/` 或等价明确边界内：

- `ingestion.py`：文件登记、哈希、格式检查；
- `docx_structure.py`：段落、表格、嵌套表格、编号、页眉页脚、section、修订标记和字段；
- `rendering.py`：LibreOffice 派生 PDF 与 manifest；
- `source_alignment.py`：结构块到渲染页/文本范围对齐；
- `metadata.py`：候选提取与冲突；
- `phase_detection.py`：期别和无缝设计候选；
- `section_index.py`：入排章节、流程表和基线及以前相关章节索引。

`section_index` 使用标题、表格结构、访视列、检查项行和正文引用等多信号识别流程表。低置信度、未接受修订、嵌套表缺失或自动编号断裂时进入“需要核对”，不能把“未检测到流程表”当成“方案没有流程表”。结构提取完成后即冻结两份目录；其完整性独立于 Agent 草稿。

`.doc` 先经受控 LibreOffice 转换为 `.docx`/PDF 派生物；原始文件仍是权威源。PDF/TXT 可保留为后续兼容入口，但 Phase 3 正式验收以两份 DOCX 为主。

### 4.2 期别隔离

先建立整份文档的章节/表格适用期别图，再向 Agent 只发送所选期别相关块和明确共享块。共享条款复制为所选项目的正式规则，不在用户显示文本中加入跨期说明。另一研究期别必须通过另一次解构和发布产生独立项目。

真正无缝候选必须同时具备明确设计措辞和同一受试者队列连续跨期证据；仅标题含“II/III”、“操作无缝”、剂量选择衔接或 II 期后继续纳入新的 III 期受试者均不够。默认建立独立项目；合并候选必须展示支持和反对依据并二次确认。

## 5. Protocol Deconstructor Agent

### 5.1 输入

- 已确认方案身份与期别；
- 结构化章节块、表格网格和允许引用的 source_ref；
- 确定性识别出的官方父规则目录（编号、顺序、原文范围）；
- 冻结的按访视实例拆分的基线及以前必做项目录，以及对应研究流程表/正文块；
- 不冲突的解释材料；
- PromptVersion 和 JSON Schema 版本。

### 5.2 输出

Agent 只输出 `ProtocolDeconstructionDraft`：父规则语义拆分、组件表达式、例外、时间窗、证据要求、审核节点和待核对项。它不能增删两份冻结目录的成员，不能写正式 RuleSet，不能决定发布状态。

### 5.3 修复回路

结构校验失败后，Gate 返回稳定问题代码和局部修复范围。无法读取 JSON 或局部修订结构时，同一 AgentCall 会话最多进行两次结构重试；已形成完整草稿后的语义问题按官方父规则轮转修订，每轮最多处理 3 条父规则、最多进行 12 次语义修订，避免大方案中未被首轮选中的父规则长期得不到修正。两类预算分别计数，结构失败不消耗语义修订预算。

修订只能调整目录项的语义拆分和映射，不能靠删除目录项消除问题。达到预算、远端调用失败或仍有方案本身无法确定的锚点时，任务停止为“需要核对”，保留最后一份可解析草稿、确定性检查结果和同一会话记录；不切换模型，也不用自由文本正则补丁。12 次上限来自 MG-K10-SAR III 与 D001 II 全量父规则轮转试验：原两次统一上限无法覆盖 23/36 条父规则的独立问题，且会在尚未轮到后续父规则前提前停止。

来源定位允许一种不改变语义的确定性规范化：当 Agent 把同一句的共同前缀与后续分支误写成连续短句时，系统仅在该短句能够唯一拆成两个按原文顺序、逐字存在的片段时转换为 `source_clauses`。转换不增删字符；存在多个拆法或任一片段无法逐字定位时仍由 Gate 阻止，不进行模糊匹配或自由文本修补。

## 6. 确定性方案完整性检查

新增 `ProtocolDeconstructionGate`，至少包括：

1. `identity`：方案编号、版本、日期来源完整且冲突已确认；
2. `phase_scope`：所有规则、流程和来源均在所选期别或明确共享范围；
3. `parent_catalog`：父规则数量、顺序、编号与预先冻结目录完全一致；
4. `tree_integrity`：父子引用、组件编号、唯一 ID 和来源完整；
5. `boolean_logic`：ALL/ANY/NOT 元数、例外表达式、研究者复合判断；
6. `numeric_semantics`：指标、比较符、阈值和单位完整且不跨指标；
7. `temporal_semantics`：锚点、方向、边界和半衰期完整；
8. `workflow_coverage`：草稿逐项覆盖预先冻结的访视实例目录，不能用“非空”或笼统占位项代替完整覆盖；
9. `evidence_coverage`：每个组件至少有证据要求；同一操作在多个节点执行时形成多个访视实例，不得跨节点去重；
10. `source_coverage`：规则、组件、流程和要求均有块级来源定位，摘录是对应提取快照中的连续原文；通用标题、页眉和章首不能成为具体要求的唯一锚点；
11. `interpretation_authority`：解释材料未改写方案或修订案；
12. `diff_integrity`：重新解构的新增/删除/修改分类可由结构差异重建。

Gate 结果按 `阻止发布`、`需要核对`、`提醒` 分级；等级由确定性表映射。零规则、数量/编号不一致、空流程、逻辑无效和来源缺失均阻止发布。

## 7. EvidenceRequirement 与审核节点

证据要求有两个来源：

1. 规则组件自身需要的事实/判断；
2. 研究流程表、流程图和正文对基线及以前的必做检查、评分、病史收集、合并用药核查和再次入排核查。

去重使用“操作语义 + 研究期别 + 访视实例”结构键，不用文本相似度直接合并。相同操作在筛选和基线分别执行时保留两个 requirement 实例；同一访视实例若服务多个规则，可被多个组件引用。每个实例仍只有一个 `due_stage`，从而兼容现有领域模型而不丢失复核节点。Phase 3 发布 requirement；针对具体受试者的 `EvidenceExpectation` 在创建 ReviewEpisode 时投影，本阶段只实现无受试者的模板投影测试。

## 8. API 与持久任务

新增 V2 用例与 API：

- 上传方案并创建解构任务；
- 获取元信息/期别候选并提交确认；
- 获取任务状态和恢复点；
- 获取草稿、来源、完整性问题和差异；
- 手工修订草稿（revision 乐观锁）；
- 提交反馈并创建后继草稿 revision；
- 保存草稿、取消草稿；
- 发布首次项目或新规则版本。

Job 步骤建议：`登记文件 -> 提取结构 -> 渲染并对齐 -> 识别身份与期别 -> 等待确认 -> 生成草稿 -> 完整性检查 -> 等待审阅 -> 发布`。等待用户输入是持久状态，不占用 worker 租约。所有创建和发布接口使用幂等键。

## 9. 前端工作台

采用 `site` 设计轨，业务工作区内部使用响应式交互布局，不套固定 1280×720 画布。

### 9.1 入口

方案工作台首页提供两个清晰入口：

- `首次解构新方案`：上传后建立新草稿；
- `重新解构已有项目`：先选项目，再比较当前正式版本与新草稿。

### 9.2 草稿审阅

- 顶部固定显示方案身份、期别、“草稿第 N 稿”、完整性检查和主要下一步；
- 左侧为可筛选规则树，父规则明显高于子组件，逻辑组显示“全部满足/任一满足/例外”；
- 中间为结构化编辑和差异；
- 右侧为方案原文与来源定位；
- 窄窗口变为三个标签页，但共享同一选中规则和来源状态；
- 完整性问题直接链接到对应规则/流程来源；
- 反馈入口先让用户选择“指出原文理解错误”或“补充解释”；保存草稿允许未通过检查，发布按钮只有在全部阻止项清零后启用；
- 技术状态翻译为“正在读取方案”“需要确认研究期别”“有 3 项需要核对”“可以发布”等自然中文。

布局用 Grid/Flex、`minmax()`、`clamp()` 和容器查询；整页不横向滚动，专业长表只在组件内部滚动。浅底面积至少 80%，`#FF9900` 只用于主操作/识别，橙底使用深色文字，风险红仅表示阻止发布的问题。

## 10. 差异算法

1. 父规则按 `official_code` 对齐；
2. 子组件按稳定语义键和来源范围对齐，不依赖随机 ID；
3. 原文、表达式 AST、时间窗、例外、证据要求、到期阶段和来源分别比较；
4. 所有显示差异来自结构化 diff，不解析摘要文字；
5. 人工编辑和 Agent 修订都进入同一 diff 管道。

## 11. 测试策略

### 确定性测试

- 元信息优先级、模板版本干扰、文件名日期冲突；
- 官方编号目录、嵌套编号、断号、重复号和零规则；
- II/III 独立/共享/无缝候选；
- ALL/ANY/NOT、例外、单位、阈值、时间锚点和研究者复合判断；
- 流程表漏检、空结果、占位结果、跨访视误去重、必做检查和到期阶段；
- 来源摘录与提取快照不一致、只指向标题、渲染页变化和降级定位；
- 解释材料冲突、草稿 revision、发布幂等和回滚。

### 真实方案回归

- MG-K10-SAR III：IN 7、EX 16、方案 V2.1/2025-09-19、筛选/导入与基线核查节点；
- D001 II：IN 6、EX 30、方案 V1.0/2025-12-10、筛选和基线再次入排核查；
- 反向用例：MG-K10-SAR 的“操作无缝”不得合并受试者空间；错传另一方案或另一研究期别不得更新当前项目；
- 不使用旧规则输出作为输入，仅用于比较和定位异常。

### 界面与独立审评

- 组件和 Playwright 覆盖首次/重新解构、期别确认、来源联动、编辑、反馈修订、取消、发布、任务恢复和冲突；
- 1280/1440/1920/窄窗口及 100%/150%/200% 缩放截图；
- 中文词汇审计、axe、键盘焦点和无整页横向溢出；
- 完成实现后才派发独立视觉测试者，允许其在清洁数据目录创建/删除测试项目并走完整流程；任何零规则、空流程、错误计数或来源断裂都按系统根因回修，不接受“页面能打开”作为通过。

## 12. 兼容、回滚与清理

- V2 数据目录与 legacy 物理隔离；旧接口不承载新写路径。
- 新迁移只追加表；发布失败不改变旧 revision。
- 每个实施切片完成后删除本轮派生 PDF、临时数据库、Agent 原始临时文件和截图中间件，只保留被测试引用的最小固定夹具与验收证据。
- 若 Docling spike 无明显优势，删除隔离环境和缓存，不把试验依赖写入项目。
