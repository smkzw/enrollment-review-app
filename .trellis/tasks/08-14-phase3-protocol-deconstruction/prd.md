# Phase 3 方案解构 V2

## 目标

让一名不熟悉电脑和 AI 的资深医学监查员，仅上传正式研究方案并确认必要的研究期别，即可获得一套绑定方案版本、保留官方编号与父子逻辑、覆盖基线及以前必做工作的可审阅规则草稿；只有草稿通过确定性完整性检查并由用户确认后，才能建立或更新项目的正式规则版本。

本阶段不审核受试者资料，不把旧项目迁入 V2，也不让大语言模型直接发布正式规则。

## 权威来源与边界

1. 正式方案及当前修订案是唯一可改变规则的权威来源。
2. Q&A、澄清函、邮件和医学解释只能解释方案模糊处；与方案或当前修订案冲突时必须警示，不能改写正式规则。
3. 每个正式规则版本必须绑定方案文件哈希、方案编号、正式版本号、正式日期和研究期别。
4. 旧系统、旧项目和人工调过的规则只作为反例或回归锚点，不作为新项目的规则来源。
5. II 期、III 期默认是两个独立项目和两套受试者空间；只有方案明确说明为真正无缝或适应性 II/III，且同一受试者队列连续跨期时，系统才可提出合并候选，并必须让用户确认。“操作无缝”、剂量选择衔接或继续纳入新受试者不构成合并依据。

## 用户流程

### 首次解构

1. 用户从“方案解构工作台”选择“首次解构”，上传一份方案。
2. 系统自动提取项目名称、方案编号、版本号和版本日期；优先顺序为页眉/页脚、第一页明确字段、正文签署信息、文件名兜底。
3. 若识别到多个研究期别，系统先显示独立期别候选和依据，再让用户选择本次解构的期别；不能先把多个期别混合解构。
4. 系统展示解构进度和可恢复状态，完成后进入草稿审阅，不直接创建正式项目。
5. 用户逐条查看父规则、子条件、逻辑关系、时间窗、例外、所需证据、审核节点和方案原文定位。
6. 用户可手工修改草稿，或就某一条向系统说明修改要求并重新解构；修改时区分“指出原文理解错误”和“补充解释”。前者必须关联方案原文，后者只能进入解释说明层；每次变化保留差异。
7. 草稿通过完整性检查且用户确认后，才发布正式规则版本并创建相应研究期别的项目。

### 重新解构

1. 用户先选择现有项目，页面展示当前方案版本、研究期别和正式规则摘要。
2. 用户可上传新方案/修订案，或在不上传新方案时基于反馈修订当前草稿。
3. 当前正式版本与新草稿并列显示，按官方父规则编号对齐；新增、删除、原文变化、逻辑变化、时间窗变化、例外变化、证据要求变化和审核节点变化分别提示。
4. 用户可继续编辑、继续说明、再次解构、保存草稿、取消或发布。
5. 取消和保存草稿都不能覆盖当前正式版本。保存允许保留尚未通过完整性检查的草稿；取消仅退出本次编辑，未保存修改需明确提示是否丢弃，已保存草稿仍可恢复。发布后形成新的不可变规则版本，旧版本继续供历史审核追溯。
6. 重新解构上传的文件必须属于当前项目的同一方案谱系和研究期别；方案编号或期别不一致时拒绝发布。正式版本、日期和文件哈希允许随合法新版本变化。

## 结构化要求

1. 入选和排除父规则数量、顺序和官方编号必须与所选期别的方案原文完全一致。
2. 复杂父规则可拆为子组件，例如 `IN-04a`、`IN-04b`，但子组件不能被计为新增父规则。
3. 每个子组件必须明确 `全部满足`、`任一满足`、`不满足`、例外条件和专业判断条件，不得把“和”弱化为“或”。
4. 数值条件必须保留指标名称、比较符、阈值和单位；不同指标不得因同属实验室检查而混用。
5. 时间条件必须保留锚点、方向、上下界、半衰期条件和允许的日期精度；“随机前”“基线前”不能默认等同筛选日期。
6. 研究者复合判断必须保留其全部前提，例如“存在异常”与“研究者判断构成不可接受风险”必须同时满足时，不能拆成任一满足。
7. 在 Agent 解构前，系统必须从结构通道冻结两份只读目录：官方父规则目录，以及按访视实例拆分的基线及以前必做项目录。Agent、用户反馈和修复回路都不能增删目录成员。
8. 规则之外，研究流程表、流程图和正文中基线及以前的必做检查、检验、评分、病史收集、再次入排核查和时间点要求必须成为结构化证据要求，并归入正确审核节点。同一检查在筛选和基线均需执行时，必须保留两个访视实例，不能因名称相同而合并成一个到期节点。
9. 每个规则、子组件、流程节点和证据要求必须至少有一个方案来源定位；定位需包含方案版本、文档部件或渲染页、原文摘录及可用的文本范围。摘录必须能在该文件哈希对应的提取快照中逐字定位；通用标题、页眉或章标题不能作为具体必做项的唯一来源。
10. 选定单一期别后，展示层不显示“与 II 期相同”等跨期比较性噪声；共享条款直接作为该项目规则呈现。真正限定适用期别的原文和结构字段必须保留，不能为“去噪”而删除。

## 失败与恢复

1. 未找到任何入排规则、父规则数量为零、研究流程表应存在但解析为空或覆盖不全、官方编号断裂/重复、期别无法明确或来源定位缺失时，任务必须停在草稿前或“需要核对”状态，不能显示解构成功。用一条笼统占位要求代替多项流程工作同样视为覆盖不全。
2. Agent 输出不符合结构契约时允许在同一任务中有限次数修复；仍失败则保留已完成步骤、失败原因和可重试范围。
3. 浏览器关闭不取消任务；重复提交同一文件和期别不产生重复正式项目或规则版本。
4. 用户应看到自然中文的问题、影响和下一步，不看到模型名、内部字段、异常堆栈或运行日志。

## 界面与中文要求

1. 入口明确区分“首次解构”和“重新解构”，避免把覆盖旧方案的风险带入首次流程。
2. 草稿首屏优先显示方案身份、研究期别、完整性检查、规则总数和需要用户核对的项目。
3. 规则树必须用缩进、连线/分组和“全部满足/任一满足/例外”标签表现父子关系，父规则与子组件不能同层平铺。
4. 原文、结构化规则和修改说明之间可在不超过三次操作内往返；选择规则后原文定位保持同步。
5. 页面采用康哲站点式设计基线：浅色为主、橙色作为有限强调、风险红只用于真实风险；响应式布局不依赖固定屏幕宽高，整页不横向滚动。
6. 所有可见文字使用临床试验场景中的自然中文，不出现 `Agent`、`schema`、`pipeline`、`provider`、`gate`、`draft_id` 等内部词。

## 验收标准

- [ ] 从原始 MG-K10-SAR V2.1 方案新建 III 期项目，方案编号、版本号 V2.1、日期 2025-09-19 正确，项目代号不得识别成“临床研究方案”。
- [ ] MG-K10-SAR III 期父规则为 IN 7 条、EX 16 条，官方编号和顺序与方案一致；共享条款不会错误标记为“仅 III 期”；“操作无缝”不会触发合并受试者空间候选。
- [ ] 从原始 D001 V1.0 方案分别形成期别明确的解构流程；选择 II 期时父规则为 IN 6 条、EX 30 条，项目与 III 期受试者空间不共享。
- [ ] 两份方案在 Agent 前均形成冻结的官方父规则目录和按访视实例拆分的基线及以前必做项目录；草稿逐项覆盖，缺一项、只生成占位项或来源仅指向标题均阻止发布。
- [ ] 代表性复杂条款覆盖 ALL/ANY/NOT、阈值、单位、时间锚点、例外和研究者复合判断，并通过针对逻辑变异的测试。
- [ ] 首次解构和重新解构均可完成上传、期别确认、草稿审阅、手工编辑/反馈重解构、差异查看、保存草稿、取消和发布；取消不改变正式版本。
- [ ] 解释材料与方案冲突时明确警示且正式 RuleSet 不变；无冲突解释可作为来源明确的补充说明。
- [ ] 同一方案编号和研究期别已有正式项目时，“首次解构”引导用户进入“重新解构”，不得产生第二套并行正式项目；上传另一方案或另一研究期别时明确拒绝或另建独立项目。
- [ ] 每个正式 Rule/RuleComponent/WorkflowStage/EvidenceRequirement 均可回到方案版本和原文定位。
- [ ] 强制终止服务后任务可从检查点恢复；重复请求和重复发布不产生重复记录。
- [ ] 后端单元、契约、迁移、任务恢复、真实方案回归测试通过；前端组件测试、构建和真实浏览器端到端测试通过。
- [ ] 1280、1440、1920 和窄窗口，以及浏览器 100%、150%、200% 缩放下，无整页横向溢出、裁切、重叠或关键操作隐藏。
- [ ] 独立视觉测试者以医学监查员身份完成两份真实方案的端到端试用，并将问题按根因修正后再验收。

## 不在本阶段

- 受试者资料上传、OCR、ClinicalFact、Patient Profile 和实际入排判定在 Phase 4-6 实现。
- 报告导出、批量审核和行动闭环不在本阶段。
- 不实现登录、多用户权限或旧项目迁移。
