# Quality Guidelines

> 后端质量以临床逻辑正确、可追溯、可恢复和跨项目泛化为核心。

## Overview

V2 必须把方案事实、证据事实、候选解释、确定性判定和用户动作分开。质量门禁不能只证明流程能跑通，还要证明布尔逻辑、时间窗、单位、例外条件、证据完整性和阶段边界正确。

## Forbidden Patterns

- 在系统级代码写入特定项目、中心或受试者 ID 的修补规则。
- 让 LLM 直接产生最终总体结论、自动关闭待办或覆盖人工 override。
- 用正则或理由文本关键词修补“和/或”、实验室指标、梅毒例外等语义错误。
- 缺失条目、解析失败、冲突证据或未知值默认判为通过。
- 用 Markdown、mtime、缓存文件或单个 `overall_verdict` 作为事实源。
- API 路由直接访问多个存储实现并拼装领域结论。
- 捕获所有异常后返回成功或空数组。

## Required Patterns

- RuleExpression、EvidenceRequirement、EvidenceSpan、ReviewEpisode 和 ActionItem 均有版本化契约。
- Agent 只提出结构化候选；确定性 evaluator/gate 负责最终状态、rollup 和待办动作。
- 所有副作用节点幂等；长任务有 durable Job、检查点、重试范围和取消状态。
- 修改持久数据使用 revision/乐观锁；过期候选不能覆盖新状态。
- 证据必须指向文件、页码及可用的 bbox/text range/excerpt，定位能力降级要明确记录。
- 用户界面文案由稳定状态和结构化字段生成，不解析模型自由文本。
- 新 V2 写路径与 legacy 存储物理隔离；旧项目仅作为只读回归锚点。
- 草稿差异必须由前后完整结构快照确定性计算，覆盖规则、组件、资料要求、流程映射、来源绑定和解释层；发布不能信任调用方提交的局部差异声明。
- 冻结目录映射使用有序且不重复的来源集合；合同构造器与发布门禁都要独立拒绝重复、换绑、跨访视或跨期来源，防止低层复制绕过模型重验证。
- 官方父规则目录、基线及以前必做项目录和允许来源必须在语义模型调用前作为独立检查点落盘；模型失败或服务不可用时，来源与冻结目录仍必须可查。
- 局部修订的防回退比较同时检查问题数和问题指纹；即使总数减少，只要用新问题替换了旧问题也必须拒绝。默认语义修订器可将确定性拒绝原因回填后有界重试一次，不得无限重试或换模型。
- 父规则冻结原文中的实质性列举项、时间窗、阈值、例外和注释必须逐项进入子规则并保留来源；仅结构化“包括以下情况”等引导语不算覆盖。

## Testing Requirements

- 单元测试：领域值对象、四值逻辑、AND/OR/NOT、子规则 rollup、时间窗、单位换算、日期精度。
- 属性/变异测试：重点验证把 AND 改 OR、阈值运算符变化、未知值传播时测试必然失败。
- 契约测试：JSON Schema、API 请求/响应、Agent 输入输出、PromptVersion 与 SchemaVersion 匹配。
- 临床回归夹具：脱敏覆盖实验室不同指标、否定词、联合条件、例外条件、阶段锚点和溯源提醒。
- 恢复测试：节点重试、任务中断恢复、重复提交幂等、revision 冲突、过期结果拒绝。
- 存储反例：外键绕过、非空绕过、列/正文镜像漂移、创建时间篡改、列表过滤隐藏坏行和部分发布写入回滚。
- 集成测试使用系统实际运行时；当前 legacy 基线为 `/usr/bin/python3`，131 项通过、1 项跳过。

## Code Review Checklist

- 是否把临床语义放进结构契约，而不是项目特异文本规则？
- 未知、冲突和缺失是否仍保持不确定，而非被误判通过？
- Agent 是否越过 gate 直接写最终状态？
- 证据引用能否回到原文件具体位置？
- 重试、重复执行和并发修改是否幂等且不丢历史？
- 是否有针对根因的测试，并覆盖相邻共享逻辑？
- 是否在真实运行时执行测试，而非另一套缺依赖的 Python？

## 事件与证据归属

- Patient Profile 事件若声明 `fact_ids`，事件携带的每个 EvidenceSpan 必须属于这些事实之一；同一审核节点内存在证据不构成事件证据。
- 事件只与规则相关但无事实级定位时，应输出“关联规则资料”关系，不得伪造 `direct` 关系。
- 可点击事件的目标规则组件必须由当前审核节点内 EvidenceSpan 的 FinalAssessment 归属确定，并与前端深链参数一致。
- 回归测试至少包含：事件借用同节点其他事实证据时拒绝；无独立证据时前端无链接；汇总事件的 URL 组件、页面选中项和证据属主一致。

## 场景：证据风险汇总与关闭语义

### 1. 适用范围

- 当证据页、文件或处理修订需要展示风险总数、待核对数，或允许用户关闭风险时适用。

### 2. 接口与存储签名

- 证据快照响应必须提供 `risk_flag_count`、`pending_risk_flag_count` 和可为空的 `upload_job_id`。
- 风险、页审核、校对和页产物仓储必须提供按一组 ID 批量读取的方法；列表投影不得逐页或逐风险调用单条仓储。

### 3. 合同

- 汇总只使用同一证据处理修订内的风险、页审核和校对；其他修订的记录不得影响当前结果。
- `OUTPUT_REPETITION` 等必须整页校对才能消除的严重风险，不得因普通“已阅”记录而计为关闭。
- 校对命中采用半开区间 `[start, end)`；恰在 `start` 或 `end` 边界外插入文字不构成覆盖。
- 关键校对可用完整上下文判断语义，但持久化范围只保存实际变化的最小原文区间。

### 4. 校验与错误矩阵

| 情形 | 结果 |
|---|---|
| 同修订、可人工阅览关闭的风险已有有效页审核 | 计为已关闭 |
| 严重整页重复风险只有普通页审核 | 仍为待核对 |
| 校对与风险区间真实重叠且通过确认门禁 | 计为已关闭 |
| 校对仅触及半开区间边界 | 不关闭风险 |
| 审核或校对属于其他处理修订 | 忽略 |
| 不可变记录正文与镜像列不一致 | 拒绝投影，不得静默漏计 |

### 5. 正常、边界与反例

- 正常：两页风险使用一次批量加载得到与逐条计算相同的计数。
- 边界：空风险集合返回两个零值，不制造虚假待办。
- 反例：严重整页重复只有“已查看”时显示为已处理；这是错误实现。

### 6. 必需测试

- 一页与多页快照的 SQL 查询数保持常数级，并断言不超过既定上限。
- 覆盖严重整页重复、普通可阅风险、区间内部校对、左右边界插入和跨修订污染。
- 覆盖镜像漂移、原文哈希不一致和处理中快照 `upload_job_id` 的真实任务深链。

### 7. 错误与正确实现

- 错误：`resolved = reviewed or corrected`，把所有风险视为相同关闭条件。
- 正确：先由风险类型决定允许的关闭方式，再在当前处理修订内批量核对有效审核或真实重叠校对。
